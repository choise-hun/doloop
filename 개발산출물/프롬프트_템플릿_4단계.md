# 시니어 GPT ↔ 주니어 Gemini 4단계 프롬프트 템플릿

> 목적: 영향 범위가 격리된 작업에서 구현·일반 테스트 실행 토큰은 Gemini가 쓰고, 시니어 GPT는 명세와 독립적인 문제 탐지에 집중한다. 사이드 이펙트가 큰 작업은 §0 원스톱 템플릿으로 시니어가 직접 끝낸다. 사용자가 단계 흐름을 지정하면 아래 템플릿을 복사해 `<...>`만 실제 값으로 채운다. 기존 작업이 예상보다 커지면 진행 파일에 근거를 남기고 검증 가능한 경계에서 단계를 나눌 수 있다.

## 적용 판정 및 Step 분할 가이드라인 (먼저 확인)

[협업 설명서 §1.2](협업_시니어주니어.md)의 원칙에 따라 대기능을 적정 크기(골디락스)로 나누고 구현자를 배정한다.

### 1. 대기능(Feature) 단위의 Step 개수 가이드라인 (최우선 규칙)
- **최우선 원칙:** 상용 계획 상의 대기능(Feature: 예: CH-A, CH-B, CM-BE, PF, ST 등) 단위의 Step 수는 **3개 이하 권장(적을수록 좋다)**이며, **최대 4개**로 엄격히 제한한다.
- **4개 초과 시 조치:**
  1. 사소한 단편을 인접 Step과 병합(통합)하여 3개 이하로 압축한다.
  2. 축소 통합이 불가능할 정도로 작업 자체가 방대하다면 `계획/상용_서비스_계획.md` 상위 계획 수준에서 대기능을 둘로 정식 분리한다.
- **대기능(상위 단위)의 과도한 분할 방지 (초안·계획 단계 필수 검토):**
  - "Step 수를 3~4개 이하로 맞추라"는 규칙을 준수하겠다고, 상위 대기능(Feature) 자체를 자잘하게 쪼개버리는 꼼수(예: PF를 PF-A, PF-B, PF-C 같은 가짜 대기능으로 쪼개서 각 1~2 step씩 만드는 행위)를 **엄격히 금지**한다.
  - 대기능은 **"독립적으로 완성된 사용자 가치(End-to-End User Journey)를 온전히 품는 단위"**여야 한다. 초안 작성 및 계획 수립 시 기능이 파편화되지 않았는지 반드시 검토한다.

### 2. Step 적정 크기(골디락스) 상한선과 하한선
- **과대 뭉텅이 금지선 (Upper Bound — 하나라도 해당하면 Step 분할 필수):**
  - 신규/수정 파일 수 **7개 초과** (또는 핵심 로직 파일 5개 초과)
  - 예상 diff **600~700줄 초과**
  - 독립된 사용자 여정(동선)이 **2개 이상** 결합 시
- **과소 세분화 금지선 (Lower Bound — 하나라도 해당하면 인접 Step에 무조건 통합):**
  - **독립 검증 불가능성 (단편 분할 금지):** 브라우저에서 눈으로 보거나 단일 E2E로 통과를 증명할 수 없는 단편(화면에 안 붙는 빈 컴포넌트 1개, 단순 DTO 파일 1개, 단순 CSS 토큰 1개 등)은 단독 Step 분할 금지.
  - **명세 오버헤드 역전:** 주니어에게 줄 명세서 분량(150~200줄)이 실제 구현 코드량과 비슷하거나 더 긴 자잘한 작업은 단독 Step 금지.
  - 예상 diff **100~150줄 미만**인 작업은 인접 Step에 통합.

### 3. Step별 수행 방식 판정

대기능 전체를 뭉텅이로 볼 때는 시니어가 해야 했던 고위험 작업도, 위 골디락스 기준으로 쪼개놓고 보면 격리된 폼이나 스캐폴딩 등 60~70%는 주니어가 안전하고 저렴하게 구현할 수 있다.

| 판정 | 대상 Step 예 | 사용할 템플릿 |
| --- | --- | --- |
| **주니어 적합 Step** | 순수 계산 함수, DTO 변환기, 기계적 i18n 복사, 영향이 격리된 폼/스캐폴딩, 독립 백엔드 API, 기계적 스캐폴딩 | §1~§4 4단계 (명세 → 주니어 구현 → 시니어 핀포인트 검토 → 주니어 정리) |
| **시니어 직접 구현 Step** | 복잡한 상태/컴포넌트 리팩터링, 레거시 화면 공존, 비동기 캐시 무효화, 에러 응답 매핑 등 고위험 | §0 시니어 직접 구현 후 §4 주니어에게 전체 테스트/CI 인계 |
| **핀포인트 검증** | PR이 이미 CI 통과 후 특정 리뷰 결함만 남음 (파일·줄 특정) | §3-P 핀포인트 검증 |

4단계 분담의 비용 = 명세 작성 + 주니어 구현 + **시니어의 낯선 diff 재독**이다. Step을 적정 크기로 쪼개면 시니어 재독 비용이 급감하여 원래의 토큰 절약 구조가 작동한다.

## 0단계 — 시니어 직접 구현: 핵심 구현 + 주니어에게 테스트/CI 인계

```text
# <시니어 모델> (시니어) — <작업 ID> 핵심 구현 및 검증 인계

개발산출물/협업_시니어주니어.md §1.2에 따라 고위험 핵심 로직을 시니어가 직접 구현한다.
목표: <요구사항>
기준: <계획 ID·요구사항·서버 계약·관련 진행 파일>
선행 조건: <선행 PR 머지·브랜치·환경>
범위: <변경 파일·계약. 승인 밖 계약 변경은 사용자 결정>
Git 처리: 로컬 구현 및 표적 테스트 확인까지만. (전체 회귀 테스트·PR/CI는 주니어에게 인계)

진행 방법:
1. git 상태·브랜치·사용자 변경·활성 진행 파일·열린 PR을 확인하고 보존한다.
2. 도메인 규칙과 기존 코드(재사용 컴포넌트의 클래스·DOM·테스트 셀렉터, API 에러 객체 구조, 캐시·요청 경합 처리)를 file:line으로 확인한다.
3. 진행 파일에 결정·계약·배치 약속·검증 기준을 짧게 고정한다.
4. 기존 계약을 유지하며 핵심 로직을 구현하고, 표적 단위 테스트 1~2개로 정상 동작을 확인한다. 단언 완화·skip·임의 fallback 금지.
5. 대규모 전체 테스트 실행 및 CI 대기는 고가 토큰을 쓰지 않고 즉시 중단한다.
6. 진행 파일에 변경 diff, 핵심 검증 결과, 4단계 주니어가 실행할 전체 테스트 목록을 기록하고 인계한다.

완료 기준: 핵심 코드 구현 및 표적 테스트 통과 근거 기록 완료.
다음 담당: Gemini 주니어가 4단계에서 전체 회귀 테스트 실행 + PR 생성/push + CI 대기 + 결과 문서를 정리한다.
```

## 공통 원칙

- 네 단계는 역할 인계를 위한 기본 묶음이다. 작업의 모든 내부 활동을 별도 세션으로 만들지 않는다.
- 작업 시작 때 `git status --short`, 브랜치, 관련 진행 파일, 열린 PR을 확인한다. 미커밋·staged·untracked 사용자 변경과 다른 작업의 파일을 보존한다.
- 진행 파일은 단계와 다음 담당, 승인 범위, 파일 충돌, 검증 근거, 재개 지시를 기록한다. 결과 파일은 실제 명령·결과·미실행 범위·결함·판정을 기록한다.
- 역할은 이 템플릿에서 정한다. GPT는 저장소 규칙을 읽고 따르되, Gemini 전용 도구나 런타임을 쓸 수 있다고 가정하지 않는다. Gemini는 이 저장소의 AGENTS.md/GEMINI.md와 협업 설명서, 해당 도메인 규칙을 따른다.
- 명세·테스트·리뷰에서 실패를 숨기지 않는다. 단언 완화, 테스트 삭제·skip, 임의 fallback으로 통과시키지 않는다.
- 지정된 테스트 명령의 반복 실행, 결과 집계, 문서 반영처럼 절차가 명확한 일은 Gemini가 맡는다. GPT 시니어는 테스트 실행 자체보다 테스트 설계의 빈틈·실패 재현·실패 원인 판정에 집중한다. 독립 판단이 필요한 재현 또는 표적 회귀 테스트만 직접 실행하고, 테스트 실행만을 위한 고성능 모델 세션을 만들지 않는다.
- PR 머지는 사용자만 한다. 배포는 별도 승인이 없으면 수행하지 않는다.

## 1단계 — 시니어 GPT: 세부 명세 작성·검토

```text
# GPT-6.1 Sol (시니어) — <작업 ID> 세부 명세

목표: <요구사항을 구현 가능한 단위로 명세화>
기준: <계획·요구사항·기존 계약·관련 진행 파일>
선행 조건: <선행 PR 머지, 브랜치, 환경 등>
범위: 명세 작성과 실제 코드 근거 조사. 구현은 이번 단계 범위에 포함하지 않는다.
Git 처리: <로컬 문서 변경만 / 명시한 범위>

진행 방법:
1. git 상태·브랜치·기존 사용자 변경과 활성 진행 파일을 확인하고 보존한다.
1-1. 대기능(Feature)을 §1 가이드라인에 따라 3개 이하(최대 4개)의 골디락스 Step으로 세분화하고, 각 Step의 구현 담당자([주니어] vs [시니어])를 판정해 진행 파일에 기록한다.
2. 해당 도메인 규칙을 읽고 기존 함수·DTO·컬럼·경로·CSS 토큰을 실제 코드에서 확인해 file:line 근거를 남긴다. 재사용·이동 대상 컴포넌트의 클래스·DOM·테스트 셀렉터와 API 에러 객체 구조는 유지 계약으로 명세에 전수 열거한다.
3. 구현 파일, 계약, 필드, 오류·상태, 권한·소유권, 상태 전이, 실패 모드, 검증 명령과 수용 기준을 빠짐없이 명세한다.
4. 주니어가 설계 결정을 추측하지 않고 구현할 수 있는지, 테스트가 중요한 가드를 실제로 검증하는지 점검한다.
5. 명세와 진행 파일을 갱신하고, 검토할 파일·승인 범위·다음 주니어 담당 단계를 기록한다.

승인 경계:
- DB/API/시그니처/경로/공개 범위 계약 선택이나 명세 범위 밖 변경이 필요하면 임의 결정하지 말고 사용자 결정 항목으로 분리한다.
- 명세 단계에서 코드·테스트를 구현하거나 실행하지 않는다.

완료 기준: 세부 명세와 근거가 준비되고, 구현 승인 여부·주니어가 사용할 2단계 프롬프트의 입력값이 명확하다.
결과: 작성/수정 파일, 핵심 file:line 근거, 미확정 결정, Git 상태, 다음 단계 멘트를 보고한다.
```

## 2단계 — 주니어 Gemini: 1차 구현·검증·PR 업로드

```text
# Gemini(주니어) — <작업 ID> 1차 구현·검증·PR

개발산출물/협업_시니어주니어.md와 개발산출물/프롬프트_템플릿_4단계.md의 2단계를 따른다.
목표: 시니어 승인 명세대로 구현하고 1차 검증 후 PR을 올려 시니어 독립 검증을 요청한다.
명세: <상세 명세 경로와 절>
진행/결과: <진행 파일>, <결과 파일>
선행 조건: <선행 PR 머지·브랜치·환경>
승인 범위: <명세 범위와 구현·테스트 파일>
Git 처리: <브랜치·커밋·push·PR 생성/갱신 승인 범위>. 머지와 배포는 하지 않는다.

진행 방법:
1. git status·브랜치·origin/main·열린 PR을 확인하고 모든 기존 변경을 보존한다.
2. 명세와 도메인 규칙을 대조한다. 명세에 없는 제품·계약 결정을 추가하지 않는다.
3. 구현하고 명세에 지정된 테스트와 필요한 회귀 검증을 실행한다. 실패는 원인을 분류해 고친 뒤 재실행한다. 중요한 실패 조건을 잡지 못하면 테스트를 보강한다. 단언 완화·skip·테스트 삭제·임의 fallback은 금지한다.
5. 자기 diff와 변경 파일을 점검하고 진행/결과 파일에 명령·실제 결과·미실행 범위를 기록한다.
6. 승인된 Git 범위 안에서 작업 브랜치에 커밋·push하고 main 대상 PR을 생성/갱신한다. PR 번호와 head SHA를 기록한다.
7. PR의 테스트·CI 결과는 시니어가 독립 검증할 입력으로 명시한다. 이 단계는 시니어 검증을 대신 완료 처리하지 않는다.

명세와 코드가 다르거나 승인 밖 계약 변경이 필요한 경우 해당 부분만 멈추고 근거·선택지를 보고한다. 나머지 독립 작업은 계속한다.
완료 기준: 1차 구현·검증·PR 업로드 및 시니어가 재현 가능한 기록이 완료된다.
다음 담당: GPT-6.1 Sol 시니어의 3단계 독립 검증.
```

## 3단계 — 시니어 GPT: 독립 구현 검증·필요 최소 수정·테스트

```text
# GPT-6.1 Sol (시니어) — <작업 ID> PR 독립 검증·수정

목표: Gemini의 1차 구현을 승인 명세와 대조해 실제 결함과 검증 구멍을 찾고, 범위 안에서 필요한 수정·테스트를 한다.
입력: <상세 명세>, <진행 파일>, <결과 파일>, PR #<번호>, 대상 head <SHA>
선행 조건: PR head와 로컬 대상 커밋이 일치하는지 확인한다. 현재 브랜치와 git status에서 사용자 변경을 먼저 식별한다.
범위: 승인 명세의 구현·테스트 파일, 발견 문제의 재현·수정·회귀 테스트, 검증 결과 기록.
Git 처리: 기본은 로컬 검증·수정까지만. 별도 명시가 있으면 <허용된 커밋/push>. PR 머지와 배포는 하지 않는다.

검토 방법:
1. Gemini의 자체 검증 결과를 참고 자료로 보고, PR diff와 현행 코드를 직접 읽어 독립적으로 판단한다.
2. 명세의 각 수용 기준·실패 모드와 프로덕션 가드를 대응시키고, 테스트 단언이 가드 누락을 잡는지 확인한다.
3. 입력 경계, 권한·A/B 소유권, 데이터 무변경/트랜잭션, 동시성·취소·지연 응답, 공개 정보, 오류 형식 등 작업에 해당하는 실패 경로를 우선 점검한다.
4. 재현 가능한 문제는 실패를 확인하고 원인을 판정한다. 필요한 코드 수정과 회귀 테스트만 승인 범위 안에서 최소 수행한다. 반복적 전체 테스트 실행·결과 수집은 Gemini 4단계에 맡긴다. 문제 탐지와 증거에 집중하고 무관한 리팩터링은 하지 않는다.
5. 시니어 판단이 필요한 실패 재현이나 표적 검증은 직접 실행하고 정적 추적과 실제 실행 결과를 구별한다. 지정된 테스트 전체를 실행하지 않았다면 미실행으로 적어 Gemini가 이어서 수행하게 한다.
6. 수정이 있으면 변경 파일·정확한 diff·실행한 검증과 실제 결과·Gemini가 실행할 테스트·남은 제한을 기록해 4단계 Gemini에게 넘긴다. 충돌 파일과 미커밋 상태도 명시한다.

승인 밖 계약·명세 변경이 필요하면 구현을 임의 확대하지 말고 사용자 결정을 요청한다. 사용자 변경을 안전하게 보존할 수 없으면 해당 변경에 손대지 않는다.
완료 기준: 문제 없음 또는 문제별 재현·판정·수정·테스트 증거와 주니어의 다음 행동이 기록된다.
다음 담당: Gemini 주니어가 4단계에서 시니어 수정과 전체 최종 상태를 검증·정리한다.
```

## 3-P단계 — 시니어: 핀포인트 결함 검증·수정 (3단계 축소판)

최신 head CI가 통과했고 남은 것이 파일·줄이 특정된 리뷰 결함뿐일 때 3단계 대신 쓴다. 시니어 컨텍스트에 전체 PR diff를 넣지 않는다.

```text
# <시니어 모델> (시니어) — <작업 ID> PR #<번호> 핀포인트 결함 수정

목표: 아래 결함만 확인하고 수정한다. 전체 PR 재검증은 하지 않는다.
입력: PR #<번호>, head <SHA>, 최신 CI 결과 <통과 run 링크>
결함 목록:
1. <파일:줄> — <리뷰 지적 요지> (<리뷰 링크>)
2. <파일:줄> — <리뷰 지적 요지> (<리뷰 링크>)
읽기 범위: 위 파일의 해당 함수, 직접 호출부·피호출부, 관련 테스트만.
Git 처리: <기존 PR 브랜치 커밋·push·CI 확인 승인 범위>. 머지·배포는 하지 않는다.

진행 방법:
1. PR head와 로컬 커밋 일치, git status의 사용자 변경을 확인·보존한다.
2. 결함마다 타당성을 실제 코드로 판정한다(반영/미반영/이미 해소/범위 밖).
3. 타당한 결함은 실패하는 회귀 테스트 → 최소 수정 → 해당 테스트·관련 스위트 실행 순서로 처리한다.
4. 진행/결과 파일에 결함별 판정·수정·검증과 "읽지 않은 범위 = 미검증"을 기록한다.
5. 커밋·push 후 최신 head CI 종료와 새 리뷰를 확인한다.

결함 목록 밖 문제를 발견하면 고치지 말고 한 줄로 기록해 보고한다(권한·소유권·데이터 손상 위험이면 즉시 보고).
완료 기준: 목록의 결함별 판정·증거와 최신 head CI 결과가 기록된다. 4단계가 필요 없으면 docs/문서_운영.md §6 완료 보고로 끝낸다.
```

## 4단계 — 주니어 Gemini: 최종 테스트·문서·PR/CI 마무리

```text
# Gemini(주니어) — <작업 ID> 최종 검증·문서·PR 마무리

개발산출물/협업_시니어주니어.md와 개발산출물/프롬프트_템플릿_4단계.md의 4단계를 따른다.
목표: 시니어의 검증 결과와 수정을 확인하고 최종 테스트·문서·PR/CI 상태를 일치시킨다.
입력: <상세 명세>, <진행 파일>, <결과 파일>, PR #<번호>, 시니어 검증 기록·수정 diff, 최신 head SHA
선행 조건: 시니어 변경과 Gemini 변경의 파일 충돌·staged/unstaged 상태를 확인하고 보존한다.
범위: 승인 명세에 따른 시니어 수정 검토, 최종 회귀 테스트, 해당 작업 결과/진행 문서, 기존 PR 갱신.
Git 처리: <커밋·push·기존 PR 갱신·CI 확인 승인 범위>. 새 PR·머지·배포는 별도 승인 없이 하지 않는다.

진행 방법:
1. 시니어 수정이 문제 재현을 해결하고 승인 명세·기존 계약과 맞는지 확인한다. 추가 설계 판단은 하지 않는다.
2. 시니어 표적 검증 결과를 확인하고 명세상 지정된 테스트 및 수정 후 관련 회귀를 실행한다. 모든 결과가 최종 코드와 최신 head에 대응하는지 확인한다.
3. 진행/결과 파일의 파일 목록·명령·실제 결과·미실행 범위·시니어 리뷰 판단을 갱신한다. 시니어의 근거와 불일치하면 차이를 기록한다.
4. PR #<번호>의 기존 브랜치에 승인된 최종 변경을 반영하고 커밋·push한다. 다른 작업·사용자 변경은 커밋에서 제외한다.
5. 최신 head의 CI 종료 결과와 PR 리뷰를 확인한다. 코드가 바뀌면 이전 head의 CI를 최종 근거로 쓰지 않는다.
6. PR 머지는 사용자가 한다. CI나 필수 리뷰가 미완료면 차단/대기로 표시하고 완료라고 보고하지 않는다.

완료 기준: 최종 코드·검증 기록·PR diff가 일치하고 최신 head CI와 리뷰 확인 결과가 기록된다.
최종 보고: “현재 <작업> 작업은 구현부터 PR 검증까지 완료되었습니다. PR #<번호> 머지 후 다음 작업 단계 시작 멘트를 활용하세요.” 실제 CI·리뷰·테스트 근거와 미실행 범위를 함께 적는다.
```
