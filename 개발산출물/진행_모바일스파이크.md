# 진행 — M0-0 모바일 사전 확인(스파이크)

- **목표:** Capacitor 최소 앱에서 현재 웹 미디어 기능이 iOS·Android 실기기에서 쓸 수 있는지 확인하고, M0-1 정식 도입 여부를 결정한다.
- **근거:** `계획/상용_서비스_계획.md` §1 #5·§2, `계획/앱_명세.md` §1.1~1.3, `frontend/src/pages/PracticePage.tsx`, `frontend/src/lib/musicEngine.ts`
- **상태:** 설계 준비 완료. 임시 스파이크와 실기기 확인은 미착수. M0-0 완료 전에는 M0-1을 시작하지 않는다.
- **step ID:** `M0-0` (다른 진행 파일과 중복 없음)
- **원칙:** 검증 코드는 버리는 브랜치에서만 만든다. 앱 구현을 `main`에 반영하지 않는다. 최종 PR에는 `개발산출물/결과/M0-0_모바일스파이크.md`와 진행 파일 아카이브만 포함한다.

## 1. Pre-flight 5대 관문

| 관문 | 점검 | 결과와 증거 |
| --- | --- | --- |
| ① 앱 격리·API 오류 경계 | `app_id = 'ulevelp'` 격리와 `/api/v1` 에러 응답 경계 | 스파이크는 로그인·서버 API를 호출하지 않고 미디어 기능만 확인한다. API가 필요해지는 변경은 범위 밖이다. 기존 연동 API는 `src/main/kotlin/ulevelp/routes/IntegrationRoutes.kt:33-45`에서 기본 `appId`를 `ulevelp`로 처리하고, 저장 경계는 `docs/04-db-design.md:264-275`의 `(user_id, app_id, provider)`다. `/api/v1` 오류 DTO는 `docs/03-api-spec.md:17-42` 및 `src/main/kotlin/ulevelp/api/ApiError.kt:17-25`의 표준 구조(`ok`, `source`, `status`, `code`, `message`, `retryAfter`, 선택 `detail`)를 따른다. |
| ② 동시성·트랜잭션 | `suspendTx`, 취소 전파, 보상 트랜잭션 | 백엔드·DB 변경 없음. 확인 규칙은 `docs/rules/backend-kotlin.md:5-58`. 스파이크 결과 업로드를 추가하지 말고 결과 파일은 로컬에서 기록한다. 추후 서버 저장이 필요하면 새 범위·설계로 분리한다. |
| ③ 전제 실재성 | 실제 구현 파일·기능 앵커 확인 | YouTube IFrame 생성과 `playsinline`은 `frontend/src/pages/PracticePage.tsx:437-479`, A-B 구간·배속 로직은 `:574-610`, 마이크 권한·`MediaRecorder`는 `:817-858`, AudioContext 생성·resume은 `frontend/src/lib/musicEngine.ts:335-355`에서 확인했다. |
| ④ 작업 줄 충돌 | 진행 파일 및 열린 주니어 PR 확인 | 활성 `개발산출물/진행_*.md` 없음. 주니어 진행 파일은 `개발산출물/완료/진행_프론트기반.md`에 아카이브됐다. `gh pr list --state open --limit 30`은 `error connecting to api.github.com`으로 확인 실패. **스파이크 브랜치 생성 전 네트워크 복구 후 열린 `step/*` PR을 재확인한다.** |
| ⑤ 메뉴얼·승인 게이트 | 파일 경로·API·DB·시그니처 변경 또는 3개 이상 파일 변경 | 이번 준비는 진행 파일과 인수인계 메모 2개 문서만 변경한다. API·DB·함수 시그니처·기존 파일 경로 변경 없음. 스파이크에서 3개 이상 파일을 바꾸게 되면 실제 파일 목록과 이유를 사전 승인표로 제시한다. |

## 2. 범위와 판정

계획의 M0-0은 앱 전체를 만드는 일이 아니라, 아래 5개 동작의 실기기 적합성을 빠르게 가려 M0-1 진입 여부를 결정하는 단계다.

| ID | 확인 동작 | 통과 기준 |
| --- | --- | --- |
| M0-0-T1 | 앱 내부 YouTube IFrame 재생 | 외부 브라우저로 이탈하지 않고 영상이 인라인으로 재생된다. |
| M0-0-T2 | A-B 반복 및 배속 | A/B 지점 설정 후 3회 반복이 이어지고, 0.75배·1.5배 변경이 플레이어에 적용된다. |
| M0-0-T3 | Web Audio 발음 | 화면을 한 번 누른 뒤 음 합성이 들리고, 앱 복귀 후에도 다시 발음할 수 있다. |
| M0-0-T4 | 마이크 녹음과 YouTube 동시 실행 | 권한 허용 후 녹음이 시작되고 영상 소리가 계속 들리며, 녹음 파일이 재생된다. |
| M0-0-T5 | 다른 앱 왕복 | 다른 앱에서 30초 이상 있다가 복귀해도 앱이 재시작/새로고침되지 않고 영상·녹음 상태가 유지되거나 명시적으로 복구된다. |

- 기기 4종은 `계획/상용_서비스_계획.md:20`에 기록된 iPhone, iPad, 갤럭시 폰, 샤오미 태블릿이다.
- 각 결과는 `통과 / 실패 / 차단` 중 하나로 기록한다. 차단은 권한·테스트 환경·기기 미확보 등 앱 결함과 구별한다.
- 한 기기에서라도 T1~T5가 실패하면 M0-1로 넘어가지 않는다. 실패 기기·OS 버전·재현 단계·증거를 기록하고, Capacitor 보정 또는 PWA 등 앱 방식 재결정안을 사용자에게 제시한다.
- 계획 문서에는 OS 버전과 WebView 버전, 미디어 권한 설정, 테스트 영상, 로그·증거 기준이 정해져 있지 않다. 실행 직전 각 기기의 버전과 재현 가능한 테스트 영상/구간을 결과 양식에 기록한다. 성공률이나 지연 시간에 대한 임의 기준은 추가하지 않는다.

## 4. 실행·검증 안내

### M0-0-A 시작 시

1. `git status --short`로 작업 트리가 깨끗한지 확인한다.
2. `gh pr list --state open --limit 30`에서 열린 `step/*` PR이 없는지 확인한다. 확인할 수 없으면 소스 작업을 시작하지 않는다.
3. 공식 Capacitor 문서의 현재 설치·플랫폼 요구사항을 확인하고 정확한 버전을 정한다. 저장소의 `package.json`에는 현재 Capacitor 의존성이 없다.
4. 승인된 파일 목록과 함께 `spike/M0-0` 브랜치에서만 최소 실행 앱을 만든다. 기존 React 기능을 위해 필요한 설정만 추가하고 운영용 코드·인증·API 변경은 넣지 않는다.
5. 빌드·실행 명령은 선택한 버전의 공식 명령을 사용한다. 이 진행 파일은 아직 Capacitor CLI가 설치되지 않은 상태이므로 버전 의존 명령을 추정해 기록하지 않는다.
