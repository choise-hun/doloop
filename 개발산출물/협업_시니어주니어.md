# 시니어 AI ↔ 주니어 Gemini 협업 설명서

- **재개:** 2026-11-06 (win). 2026-11-03에 폐기했던 방식(원문: `git show 9c95a0e^:개발산출물/협업_시니어주니어.md`)을 지금 규칙(`CLAUDE.md`·`프론트_정렬규격.md`)에 맞게 고쳐 다시 쓴다
- **목적:** 영향 범위가 격리된 작업에서 시니어 AI가 명세와 독립 품질 검증을 맡고, Gemini 주니어가 1차 구현·검증과 PR 및 최종 정리를 맡아 구현 토큰을 절약한다. 사이드 이펙트가 큰 작업은 §1.2에 따라 시니어가 원스톱으로 수행한다. 시작 멘트는 [프롬프트 템플릿](프롬프트_템플릿_4단계.md)을 따른다. 협업·에이전트 규칙 변경 시 중앙 설정 저장소(https://github.com/choise-hun/config)와 상호 동기화한다.
- **주니어가 이 파일 하나만 읽고도 움직일 수 있게 쓴다.** step별 "무엇을"은 명세(`개발산출물/명세/<step>_구현명세.md`)에, "어떻게 일하나"는 이 파일에 있다

## 0. 주니어 세션 시작 (매번 이 순서)

1. `git status`·현재 브랜치와 인수인계 메모로 실제 작업 상태를 확인한다. 미커밋 변경을 보존하고 필요한 시점에 안전하게 main 전환·`git pull --ff-only`를 수행한다.
2. 읽기: **이 파일** → 현재 활성 주니어 진행 파일(인수인계 메모 §2와 실제 `개발산출물/진행_*.md` 목록으로 확인. 배정된 파일이 없으면 대기) → 지시받은 step의 명세 → `개발산출물/주니어_체크리스트.md`
3. 진행 파일 단계 표에서 그 step의 "선행"이 끝났는지 본다. 안 끝났으면 §8 관문 문구를 쓰고 멈춘다
4. 브랜치: `step/<step ID>` (예: `step/W-1`), base = main
5. 명세 §체크리스트 순서대로 구현 → 확인 명령 실행 → 결과 파일 → PR (§6)

## 1. 역할

| 역할 | 누가 | 하는 일 | 하지 않는 일 |
| --- | --- | --- | --- |
| **사용자** | 사람 | 메뉴얼 항목 결정, 승인, **머지** | — |
| **시니어** | GPT-6.1 Sol 등 사용자 지정 모델. Gemini 시니어 모드는 명시적으로 지정한 경우만 | 작업 배정 판정(§1.2), 사이드 이펙트가 큰 작업의 설계→구현→검증·PR 원스톱, 격리 작업의 상세 명세·주니어 PR 독립 검증·필요 최소 수정·테스트, 계약·범위 판단 | 승인 없는 계약 확대, PR 머지 |
| **주니어** | Gemini (Antigravity) | 1차 구현·검증·PR 업로드, 시니어 검증 결과 반영, 최종 테스트·문서·진행 상태·PR/CI 마무리 | 승인 명세 밖 설계 결정·계약 변경, PR 머지 |

**역할 판별(세션 시작 지시 첫 줄로 정한다):**
- 첫 줄 `# 시니어 (Gemini 임시 운용)` 또는 `# Claude(시니어)` ("명세 작성", "PR #n 리뷰", 설계 문서 수정, 백엔드 step) → **시니어**
- 첫 줄 `# Gemini(주니어)` 또는 별도 선언 없이 현재 배정된 주니어 진행 파일의 구현 step과 "PR #n 리뷰 반영" → **주니어**

4단계 시니어·주니어 방식으로 작업하면 이전의 “시니어는 구현하지 않는다”, “주니어는 시니어 검증을 하지 않는다”는 일반 역할 예시보다 사용자가 지정한 단계 템플릿과 범위가 우선한다. 실제 단계별 지시·산출물은 [4단계 프롬프트 템플릿](프롬프트_템플릿_4단계.md)을 따른다.

### 1.1 GPT 시니어 ↔ Gemini 주니어 4단계 운용

- 사용자가 4단계 방식을 지정하면 일반 역할 예시보다 [4단계 프롬프트 템플릿](프롬프트_템플릿_4단계.md)의 단계별 권한을 우선한다.
- 1단계 시니어는 명세를 작성한다. 2단계 주니어는 1차 구현·검증 후 PR을 올린다. 3단계 시니어는 독립적으로 문제를 찾고 승인 범위 안에서 직접 필요한 수정·테스트를 할 수 있다. 4단계 주니어는 시니어 변경을 확인하고 최종 테스트·문서·기존 PR/CI를 정리한다.
- 3단계에서 시니어가 코드를 수정했으면 4단계에서 해당 diff와 관련 테스트를 확인한다. 계약·범위 확대는 사용자 결정으로 남긴다.
- 주니어가 PR을 만들고 시니어가 검증하는 방식은 §1.2의 주니어 적합 작업에서 역할 인계를 위한 기본이며, 매 내부 작업마다 별도 세션을 강제하지 않는다. 작업이 예상보다 커지면 진행 파일에 이유와 재개 지점을 적고 검증 가능한 경계에서 나눈다.

- **주니어 결정 검토의 종료 경계:** 시니어는 승인 범위의 결함을 직접 해결하고 필요한 복잡한 경합·취소 회귀까지 확인한다. 단순 반복 테스트·커밋·push·PR·CI 대기는 주니어 4단계가 맡는다(`docs/문서_운영.md` §6). 검토만 하고 수정 전에 종료하지 않는다.

### 1.2 대기능 단위 Step 개수 가이드라인 및 Step별 적정 크기(골디락스)·배정 기준 (2026-11-09)

> 이 절이 Step 개수·크기·배정 규칙의 **원본**이다. `docs/문서_운영.md` §4.1, 4단계 템플릿, CLAUDE·AGENTS·GEMINI에는 요약과 이 절 링크만 둔다. 기준값을 바꿀 때는 여기만 고친다.

과거 M2-1 시절의 과도한 세분화(a, b, c, d, s로 쪼개져 명세·리뷰 왕복 오버헤드가 구현 비용을 압도)와 최근 CM-UI의 과대 뭉텅이(탭 4개·피드·카드·모달 2개를 한 Step에 묶어 4,800줄 diff 폭발 및 계약 파손)라는 **양극단(진자 운동)을 원천 차단**하기 위해 아래 3대 원칙을 강제한다.

#### 1. 대기능(Feature) 단위의 Step 개수 가이드라인 (최우선 규칙)
- **최우선 원칙:** 상용 계획 상의 대기능(Feature: 예: CH-A, CH-B, CM-BE, PF, ST 등) 단위의 Step 수는 **3개 이하 권장(적을수록 좋다)**이며, **최대 4개**로 엄격히 제한한다.
- **4개 초과 시 조치:**
  1. **인접 Step 통합 우선:** 사소한 단편(단순 DTO, 단일 폼 등)을 인접 Step과 병합하여 3개 이하로 압축한다.
  2. **상위 작업 자체 분리:** 축소 통합이 불가능할 정도로 작업 자체가 방대하다면, 이는 Step 문제가 아니라 기능 정의 자체가 너무 거대한 것이므로 `계획/상용_서비스_계획.md` 상위 수준에서 대기능을 둘로 정식 분리한다.
- **대기능(상위 단위)의 과도한 분할 방지 (초안·계획 단계 필수 검토):**
  - "Step 수를 3~4개 이하로 맞추라"는 규칙을 준수하겠다고, 상위 대기능(Feature) 자체를 자잘하게 쪼개버리는 꼼수(예: PF를 PF-A, PF-B, PF-C 같은 가짜 대기능으로 쪼개서 각 1~2 step씩 만드는 행위)를 **엄격히 금지**한다.
  - 대기능은 **"독립적으로 완성된 사용자 가치(End-to-End User Journey)를 온전히 품는 단위"**여야 한다. 초안 작성 및 계획 수립 시 기능이 파편화되지 않았는지 반드시 검토한다.

#### 2. Step 적정 크기(골디락스) 상한선과 하한선
- **과대 뭉텅이 금지선 (Upper Bound — 하나라도 해당하면 Step 분할 필수):**
  - 신규/수정 파일 수 **7개 초과** (또는 핵심 로직 파일 5개 초과)
  - 예상 diff **600~700줄 초과**
  - 독립된 사용자 여정(동선)이 **2개 이상** 결합된 경우 (예: "내비게이션 분리"와 "공유 피드 및 철회 모달"은 별개 목적이므로 1개 Step 불가)
- **과소 세분화 금지선 (Lower Bound — 하나라도 해당하면 인접 Step에 무조건 통합):**
  - **독립 검증 불가능성 (단편 분할 금지):** 브라우저에서 눈으로 보거나 단일 E2E로 통과를 증명할 수 없는 단편(화면에 안 붙는 빈 컴포넌트 1개, 단순 DTO 파일 1개, 단순 CSS 토큰 1개 등)은 단독 Step 분할 금지.
  - **명세 오버헤드 역전:** 주니어에게 줄 명세서 분량(150~200줄)이 실제 구현 코드량과 비슷하거나 더 긴 자잘한 작업은 단독 Step 금지.
  - 예상 diff **100~150줄 미만**인 작업은 별도 PR/세션으로 만들지 않고 인접 Step에 통합.

#### 3. Step별 구현 담당자(주니어 vs 시니어) 동적 배정 및 시니어 구현 시 노동 분리
대기능 전체를 뭉텅이로 볼 때는 시니어가 해야 했던 고위험 작업도, 위 골디락스 기준으로 쪼개놓고 보면 격리된 폼이나 스캐폴딩 등 60~70%는 주니어가 안전하고 저렴하게 구현할 수 있게 된다.

| 구분 | 해당 Step 작업 | 수행 방식 |
| --- | --- | --- |
| **주니어 적합 Step** | 독립된 순수 계산 함수, DTO 변환기, 기계적 i18n 사전 복사·키 추가, 격리된 폼/스캐폴딩, 기존 화면·공용 컴포넌트를 건드리지 않는 독립 백엔드 API 추가, 지정 테스트 반복 실행·결과 집계·문서 정리 | 4단계 분담 (시니어 명세 → 주니어 구현·PR → 시니어 독립 검증(조건 충족 시 §3-P 핀포인트) → 주니어 정리) |
| **시니어 직접 구현 Step** | 복잡한 상태/컴포넌트 리팩터링, 기존 레거시 화면과의 공존·하위 호환, 비동기 캐시 무효화·지연 응답 처리, API 에러 응답 매핑, 기존 테스트 셀렉터·CSS 모듈·DOM 구조에 민감하게 의존하는 고위험 변경 | **시니어 구현 + 주니어 테스트/CI 마무리** (시니어는 핵심 코드 작성 및 표적 단위 테스트 1~2개 확인 후 커밋·작업 브랜치 push까지 하고 종료 → 주니어가 전체 회귀 테스트 실행, 신규 PR 생성, PR/CI 대기, 결과 정리 전담) |

- **배정 판정 질문 (하나라도 예면 시니어 직접 구현 Step):** ① 기존 컴포넌트·화면의 DOM/클래스/테스트 셀렉터를 바꾸거나 옮기는가 ② 기존 화면과 새 화면이 같은 코드를 공유하며 공존해야 하는가 ③ 캐시 무효화·요청 경합·에러 응답 구조처럼 명세 표로 다 적기 어려운 암묵 계약에 의존하는가
- **배정 판정 시점:** 1단계(세부 명세 착수)에서 시니어가 각 Step의 구현 담당자를 [주니어] 또는 [시니어]로 판정하고 명세에 명시해 사용자 승인을 받는다.
- **시니어 구현 Step 시 노동 분리 (고가 토큰 낭비 원천 차단):** 시니어가 직접 구현하더라도 대규모 전체 회귀 테스트 실행, 신규 PR 생성, `gh pr checks --watch` 대기, 결과 파일 작성 등 단순 실행 노동은 고가 모델이 하지 않고 4단계 주니어(Gemini)에게 인계한다. 시니어는 커밋한 작업 브랜치를 push해 두고(다른 PC에서도 이어 받을 수 있게, PR은 만들지 않는다), 열린 PR이 없는 신규 Step이면 4단계 주니어가 그 브랜치를 받아 main 대상 PR 생성을 승인 범위 안에서 수행한다.
- 이미 주니어가 구현하고 CI가 통과한 PR에 핀포인트 리뷰 결함만 남았으면, 시니어 3단계를 전체 재검증으로 열지 않고 해당 결함만 확인·수정한다(§7-3, 템플릿 §3-P).

## 2. 두 줄로 나눈 작업

현재 담당과 진행 상태는 인수인계 메모 및 실제 `진행_*.md` 목록·내용으로 확인한다. 아래 완료 파일은 이력이며 활성 작업이 아니다.

| 줄 | 진행 파일 | 맡는 쪽 | 건드리는 곳 |
| --- | --- | --- | --- |
| 백엔드·인프라 줄 | `완료/진행_티어크레딧.md`(M1) · `완료/진행_운영화면.md`(M2-4) · `완료/진행_노트구간서버.md`(M2-1s·c) · `완료/진행_다국어.md`(LS-0~2·L1-1) · `완료/진행_레거시정리.md`(`LG-1`·`LG-2`) 완료 | 시니어 | `src/main/**`, `src/test/**`, `src/main/resources/db/migration/**`, 서버·배포·CI 및 레거시 정리 대상 |
| 프론트 기반 줄 | `완료/진행_프론트기반.md` (M4-1 → W-1 → L0, 소작업 J-1·J-2, M2-1a·M2-1bd, M2-23, L1-2a·L1-2b — 2026-11-07 마지막 PR #124로 전체 완료. 다음 주니어 묶음 대기) | 주니어 | `frontend/src/**`, `test/*.test.js`, `test/e2e/**` (명세 파일 목록 안만) |

- 두 줄은 파일이 겹치지 않는다. 겹치는 파일을 고쳐야 하면 주니어는 멈추고 묻는다
- 공유 문서는 쓰는 사람을 정한다: `인수인계_메모.md`·`계획/*`·`CLAUDE.md`·`GEMINI.md` = **시니어만**. 주니어는 자기 진행 파일·결과 파일·체크리스트만 고친다
- 주니어 PR이 머지되면 시니어는 **다음 작업 PR 안에서** 인수인계 메모를 맞춘다(머지 뒤 정리만 하는 PR·세션을 만들지 않는다)
- 서버와 딱 붙은 작은 화면 작업(예: M2-1c)과 §1.2의 주니어 부적합 작업은 주니어 명세를 쓰지 않고 시니어가 직접 구현한다 — 명세 비용 ≈ 구현 비용이거나 검증 비용 > 구현 비용이면 나누지 않는다

## 3. 문서 역할과 설계

문서 역할·갱신·완료 판정은 `docs/문서_운영.md`를 따른다. 인수인계는 현재 사실·최근 결정 요약, 계획은 작업 순서·선행·대기 목록, 요구사항은 제품 계약, 진행 파일은 착수한 작업의 실행·재개다. 공유 문서 담당 제한은 기존 역할 배정에 그대로 적용한다.

| 층 | 문서 | 세밀도 | 언제 쓰나 |
| --- | --- | --- | --- |
| 전체 순서 | `계획/상용_서비스_계획.md` §1 | 우선순위·선행·검수 관문 | 작업 선택·우선순위 변경 시 |
| 제품 요구 | `개발산출물/요구사항_명세_초안.md` · `계획/앱_명세.md` | 동작·정책·데이터/API 경계·수용 기준 | 제품 요구·정책 결정 시 |
| 현재 실행 | 배정된 `개발산출물/진행_<작업>.md` | 단계 상태·명령·결과·다음 행동 | 착수 후 실행·검증·인계 시 |
| 구현 명세 | `개발산출물/명세/<step ID>_구현명세.md` | 주니어가 **설계 판단 없이** 구현할 정도(결정·인터페이스·표). 코드는 §4.3 범위만 | 바로 다음 묶음만. 앞 step 결과를 본 뒤 고칠 수 있다 |

먼 step까지 세밀하게 쓰지 않는다. 앞 step 결과(실제 클래스 이름·마크업)에 따라 달라진다. 명세가 실제 코드와 맞지 않으면 주니어는 §6-2대로 멈추고 묻는다.

## 4. 시니어: 명세 작성 규칙

### 4.1 필수 항목 (step마다)
1. **파일 목록**: 경로, 신규/수정, 하는 일 한 줄. 목록에 없는 파일은 고치지 않는다
2. **시그니처**: 함수·컴포넌트(인자·반환 타입), export 이름. 기존 패턴 파일을 "이 파일처럼"으로 지정
3. **데이터·문구 표**: 화면 문구, 키 이름, 값. 화면이면 DOM 구조(태그·id·class·aria)와 상태(빈/로딩/에러/비로그인)
4. **검증·에러 표**: 조건 → 결과(화면 문구 또는 status/code)
5. **처리 순서·배치 약속**: 번호 단계. 화면이면 `프론트_정렬규격.md` §1의 배치 약속 표(상태·폭별 열·맞춤 그룹)를 명세에 미리 쓴다
6. **테스트 표**: 이름 / 준비 / 실행 / 기대 결과 / **잡아야 할 버그**(예: "늦게 온 응답이 덮어씀"). 실패 케이스 포함. 테스트 코드 본문은 주니어가 쓴다
7. **체크리스트**: `[ ]` 항목마다 확인 명령과 기대 출력. 다 채우면 완료
8. **금지 사항**: 이 step에서 하기 쉬운 잘못(§5 표에서 골라 쓴다)

### 4.2 이렇게 쓰면 주니어가 헤맨다 (금지)
- 응답·마크업을 생략(`{ ... }`) → 필드·요소를 모두 적는다
- 상태 코드·값을 둘 함께("200/201") → 조건별로 하나씩
- "적절히", "필요하면", "등" → 쓰지 않는다. 고를 일은 시니어가 고른다
- 기존 코드 전제를 확인 없이 쓴다 → 전제마다 직접 연 `file:line`을 붙인다
- 기존 파일을 "전체 코드"로 준다 → 바꿀 줄만 diff·전후 코드로. 전체 코드는 새 파일에만
- 화면 step 완료 기준이 소스 검사뿐 → 실제 빌드 + layout spec + 4개 폭 스크린샷을 넣는다

### 4.3 시니어가 쓰지 않는 것 — 명세는 구현이 아니다 (2026-11-07)

이 절은 §1.2의 **주니어 적합 작업**에만 적용한다. 두 줄로 나눈 목적은 **토큰 분담**이다. 시니어가 코드를 완성해 명세에 붙이면 구현 토큰이 시니어 쪽에서 나가 목적이 깨진다(M2-1a·b에서 실제로 일어남 — 명세 789줄, 시니어가 worktree 구현·e2e 234개·변이 검사까지 돌림).

| 시니어가 쓴다 | 시니어가 쓰지 않는다(주니어 몫) |
| --- | --- |
| 결정(D표), 파일 목록, 전제 `file:line`(직접 열어 읽은 것) | 마크업·JSX·CSS 본문 |
| 시그니처·export·API 필드·타입, 문구·i18n 키 표, id·`data-*` 이름 | 테스트 코드 본문(표의 이름·준비·기대·잡을 버그만) |
| 배치 약속 표, 검증·에러 표 | 명세를 쓰기 위한 빌드·e2e·layout 실행, 스크린샷, 변이 검사 |
| **비동기·동시성 핵심 흐름만** 의사코드(골격) — 한 흐름 20~40줄, step당 합계 80줄 이하 | worktree에 구현해 보고 그 코드를 붙이기 |
| 기존 파일은 바꿀 곳의 앵커(`file:line`·식별자)와 한 줄 설명 | 기존 파일의 바뀐 블록 통째(§4.2) |

- **분량:** 명세 하나 150~250줄을 권장한다. 넘으면 산문·중복을 줄인다. 결정·필드·오류·배치·검증 조건은 생략하지 않는다. 줄 수만을 이유로 step을 분할하지 않는다
- **step 크기:** 주니어 step = **PR 하나, 리뷰 1번으로 볼 수 있는 크기**. 시간(1시간)으로 쪼개지 않는다. 한 세션에 안 끝나면 같은 브랜치·PR에 이어서 쌓는다
- **확인 방법:** 실행 대신 **읽기**로 전제를 확인한다(기존 테스트가 무엇을 비교하는지, 검사 범위 등). 실행해 봐야 알 것 같은 위험은 명세 "주의" 줄로 적고, 주니어가 처음 돌릴 때 확인한다(§6-2)
- **품질은 리뷰에서:** "가드를 빼면 실패하는 테스트인가"는 시니어가 PR 리뷰에서 본다(§7)
- 예외: 다국어 사전 값 대조처럼 **값 자체가 명세**인 경우만 시니어가 스크립트로 확인한다(LS-1)

### 4.4 Gemini Argon High를 시니어로 임시 운용할 때의 보정 규칙 (Claude 대비 특성 차이 보완)

Gemini(Antigravity)를 시니어로 운용할 때는 Claude와 다른 모델 특성(도구 실행 편향, 표 압축·요약 경향, 암묵적 추론 시 엣지 케이스 누락, 동종 모델 간 맹점 공유)으로 인해 설계·리뷰 구멍이 생길 수 있으므로 다음 4가지를 강제한다:

| Gemini 특성 위험 | 시니어 보정 규칙 (강제) |
| --- | --- |
| **1. 실행/구현 편향 (Tool Execution Bias)** — 명세만 쓰라고 해도 직접 코드를 짜고 빌드를 돌려봄 | **명세 작성 시 Tool Lock:** 소스·테스트 코드(`src/`, `frontend/`, `test/`)에 대한 `write_file`·`edit_file`과 빌드·테스트 `run_command` 호출을 금지한다. 파일 열람·검색으로 전제(`file:line`)를 확인하고 명세 문서는 작성·수정한다. 도구 이름이 아니라 작업 종류로 경계를 판단한다 |
| **2. 압축·일반화 편향 (Compression Bias)** — 분량을 줄이려 표의 항목을 `...`, `위와 동일`로 생략함 | **표 100% 전수 열거:** 150~250줄 권장 분량을 맞출 때 산문 설명만 줄이고, 결정(D표)·시그니처·API 필드·문구/i18n·에러·배치 약속·테스트 표의 행은 단 하나도 생략하지 않는다 |
| **3. 암묵적 설계 추론 누락** — 산문 추론 중 트랜잭션·격리·동시성 경계를 빠뜨림 | **설계 Pre-flight 5대 관문 선행 기록:** 명세 상단(전제 절) 또는 백엔드 설계 시작 전에 반드시 ① 앱 구분 데이터의 `app_id = 'ulevelp'`·사용자 소유권 격리 및 `/api/v1` vs 레거시 에러 포맷 경계 ② 동시성(`reqIdRef`/`AbortController` 또는 `DatabaseFactory.dbQuery` 내부 외부 I/O 금지·`CancellationException` 재던지기·보상 트랜잭션) ③ 참조 심볼·토큰의 실제 `file:line` 열람 확인 ④ 현재 배정된 활성 진행 파일 및 열린 `step/*` PR과의 파일 충돌 여부 ⑤ 메뉴얼 항목 변경(또는 백엔드 3개 이상 파일 수정) 시 변경 항목·이유·검증 방법과 승인 범위를 먼저 확인·기록한다. 명시적 요청·승인된 단계는 재승인받지 않고 승인 밖 계약 변경·파괴적 작업만 사용자 결정을 기다린다 |
| **4. 동종 모델(Gemini↔Gemini) 맹점 공유** — 주니어와 같은 착각으로 가드 누락·거짓 양성 테스트를 통과시킴 | **적대적 반증 리뷰(Counterfactual Trace):** PR 리뷰(§7) 시 눈으로만 읽지 않고, 명세 §테스트 표의 `잡아야 할 버그`마다 "프로덕션 코드의 해당 `if` 가드(`file:line`)를 지우면 테스트의 어느 단언(`file:line`)이 실패하는지" 1:1 쌍으로 역추적해 확인한다. 정적 추적과 실제 변이 검사 결과를 구분한다 |

## 5. AI가 저지르기 쉬운 잘못 (명세 금지 사항과 리뷰 기준)

| 잘못 | 막는 방법 |
| --- | --- |
| 명세에 없는 필드·키·props·파일을 지어낸다 | 명세 표에 없는 것은 추가 금지 |
| 함수 시그니처, export 이름, 파일 경로를 바꾼다 | 기존 계약과 승인 범위를 확인한다. 승인 밖 변경만 멈추고 묻는다 |
| 범위 밖 리팩터링, 다른 파일 수정, 포맷 일괄 변경(prettier 전체 실행 포함) | 파일 목록 밖은 손대지 않는다. `git diff --stat`으로 확인 |
| 실패하는 테스트를 단언 완화·`skip`·`known` 추가로 통과시킨다 | 테스트를 고치면 이유를 결과 파일에 쓴다. `known`(알려진 실패) 추가는 시니어만 |
| 실행하지 않은 결과를 "통과"로 쓴다 | 명령 출력 끝 몇 줄을 결과 파일에 붙인다 |
| 빈 `catch`, 에러를 삼키고 빈 값 반환 | 명세 에러 표대로 처리 |
| 라이브러리·API 이름 추측, 새 의존성 추가 | `package.json`·기존 코드에서 확인. 새 라이브러리 금지 |
| 인라인 스타일(`style=`)·`dangerouslySetInnerHTML` | CSP `style-src 'self'`. CSS Modules만 쓴다(`test/security.test.js`가 잡는다) |
| 레거시 `public/*` 수정 | 레거시 화면은 제거됨. 화면 작업은 `frontend/src`에서 하고, `public/` 런타임 설정·정적 자원은 해당 작업 승인 범위에서만 변경한다 |
| 색·간격을 토큰 밖 값으로 | `frontend/src/styles/tokens.css` 변수만. 새 토큰 추가 금지(R0-T1 토큰 일치 검사) |
| 명세와 다르게 구현하고 말하지 않는다 | 결과 파일 "명세와 달라진 점"에 쓰거나 멈추고 묻는다 |
| 무관한 파일 커밋(`test-results/`, 로그, 스크린샷) | `git status`로 확인. 목록 밖 파일은 커밋하지 않는다 |
| 기존 컴포넌트를 분리·이동하며 클래스명·DOM 구조·테스트 셀렉터 계약을 깨뜨린다(CM-UI) | 수정 전 `test/`·`test/e2e/`에서 해당 클래스·`data-*`·텍스트 셀렉터 참조를 검색해 유지 목록을 결과 파일에 적는다. 이런 작업은 원래 §1.2 시니어 원스톱 대상이다 |
| API 에러 응답 구조·상태 갱신 필드를 추측해 참조한다(CM-UI `err.data.detail`, `canRepublish`) | `apiClient` 등 실제 에러 객체 생성부와 서버 응답 DTO를 `file:line`으로 확인하고, 상태 변경 후 갱신되는 필드를 전수 대조한다 |
| 다음 step까지 이어서 진행 | 배정된 step 기준. 명시적으로 승인된 연속 작업은 허용하되 §8 명세·선행 머지 관문은 유지한다 |

## 6. 주니어 행동 규칙

### 6-1. 구현
1. 명세가 없으면 코드를 쓰지 않는다(§8)
2. 판단 순서: **명세 → 체크리스트 → 명세가 "이 파일처럼"으로 지정한 기존 코드**. 셋 다 답이 없으면 멈추고 묻는다
   - 스스로 정해도 되는 것: `CLAUDE.md` "자유" 항목 — 내부 변수명, CSS 클래스 이름, 명세가 "주니어 재량"이라고 쓴 문구·간격
   - 정하면 안 되는 것: "메뉴얼" 항목 — DB 스키마, API 경로·필드, 함수 시그니처, export 이름, 파일 경로
3. 화면을 바꾸면 `프론트_정렬규격.md` §1 순서를 따른다: 배치 약속(명세에 있음) → spec 먼저 돌려 실패 확인 → 구현 → spec 통과 → 4개 폭 스크린샷 검토(§6 질문 Q1~Q9 표)
4. 배정받은 step이 §1.2 판정 질문에 해당하는데 진행 파일에 배정 판정 기록이 없으면 착수 전에 `<step ID>는 §1.2 시니어 원스톱 판정 질문 <번호>에 해당합니다. 배정 확인 후 진행합니다.`로 알린다. 사용자가 그대로 진행을 지시하면 §5의 셀렉터·에러 구조 대조를 먼저 수행한다

### 6-2. 막혔을 때
- 형식: 문제 한 줄 → 원인 → 추천 해결 1개(+대안 한 줄) → 실행·검증 결과. 사용자 결정이 필요한 경우에만 "진행할까요?"를 묻는다
- 명세의 `file:line` 전제가 실제 코드와 다르면 → 멈추고 위 형식으로 묻는다(명세를 스스로 고치지 않는다)
- 30분 넘게 같은 실패를 쫓으면 → 알아낸 것을 진행 파일 "겪은 문제"에 쓰고 멈춘다

### 6-3. step 끝 (전부 해야 완료)
1. 명세 체크리스트를 모두 `[x]`로 하고, 확인 명령 출력 끝 몇 줄을 **결과 파일** `개발산출물/결과/<step ID>_<이름>.md`에 붙인다
   - 결과 파일 필수 절: 바꾼 파일 표 / 확인 명령 출력 / 스크린샷 검토 표(화면 step) / 명세와 달라진 점 / 다음 step에 넘길 것
2. PR 전 `주니어_체크리스트.md` 전 항목으로 `git diff`를 점검한다. PR 본문에 "주니어 체크리스트 점검 완료"
3. 현재 배정된 활성 주니어 진행 파일 단계 표의 상태 칸을 고친다(`리뷰 대기` + PR 번호·CI 결과)
4. 커밋 `feat|fix|test|docs(scope): 요약` + 끝 줄 `Co-Authored-By: Gemini <noreply@google.com>`
5. push → PR(base main, 기능이 다 되면 Ready, 아니면 Draft) → `gh pr checks --watch`
6. CI 통과 시 알림: `PR #n — step/<ID> → main (CI 통과, 시니어 리뷰 대기)`. 실패면 고쳐서 통과시킨 뒤 알린다

3번의 상태 칸은 `리뷰 대기 — PR #n, CI 결과; 머지 시 완료`로 쓴다. 리뷰·머지 전 완료로 오인하지 않게 하며, 머지 뒤 상태만 고치는 PR은 없다

## 7. PR 리뷰 루프 (2026-11-07 압축 — 리뷰는 PR당 1번)

1. **주니어:** PR + CI 통과 → "시니어 리뷰 대기"로 알린다. 4단계 협업에서는 템플릿 §3 시니어 독립 검증으로 인계한다.
2. **사용자:** Claude 세션에 `PR #n 리뷰해줘`(아래 시작 멘트)
3. **시니어:** 명세, §5 표, 체크리스트 기준으로 **한 번** 리뷰한다. 기본 흐름에서는 PR 코멘트로 전달한다. 사용자가 4단계 협업을 지정해 직접 검증을 맡겼으면 템플릿 §3에 따라 필요한 범위의 수정·테스트를 수행하고 근거를 주니어에게 넘길 수 있다.
   - **검증 범위는 시작 지시에 고정한다.** 최신 head CI가 통과했고 남은 것이 특정 리뷰 지적(파일·줄 특정)뿐이면 템플릿 §3-P 핀포인트 검증으로 해당 결함과 직접 연관된 코드·테스트만 읽는다. 전체 diff 재독은 권한·소유권·데이터 변경·공개 범위 등 명세 계약 위험이 남았을 때만 한다. 읽지 않은 범위는 결과 파일에 미검증으로 적는다
   - **잔손질(몇 줄 안, 설계 판단 없음 — 오타·빠진 가드·문구·테스트 이름 등)은 시니어가 PR 브랜치에 직접 커밋**한다(`fix(scope): <step> 리뷰 잔손질`). 코멘트에는 고친 목록만
   - **주니어에게 돌려보내는 것은 설계·동작이 틀린 "머지 전 수정"만.** 형식: 번호, `파일:줄`, 문제, 고칠 방향
   - 나중에 해도 되는 것은 코멘트에 한 줄로 두고 `계획/상용_서비스_계획.md`의 기존 ID 또는 대기 목록에 연결한다(따로 반영시키지 않는다)
   - 돌려보낼 것이 없으면 "리뷰 통과 — 머지하세요"
4. **주니어(돌려받은 것이 있을 때만):** 반영 커밋 `fix(scope): <step> 리뷰 n·m번 반영` → CI 통과 → 알림. **재리뷰 없이** 사용자가 머지한다
5. **체크리스트 추가는 같은 종류 실수가 두 번째일 때만**(첫 지적은 코멘트로 끝)
6. **사용자:** 머지. AI는 `gh pr merge`를 하지 않는다
7. 머지 뒤 정리 PR은 없다 — 상태 칸은 PR 안에서 이미 `완료(머지 시)`, 인수인계 메모는 시니어가 다음 작업 PR에 같이

작업 종료 보고에는 `docs/문서_운영.md` §6을 적용한다. 위 PR/CI·리뷰·머지 대기 안내만으로 종료하지 않고, 다음 작업이 있으면 현재 역할·선행 조건을 반영한 복사 가능한 시작 코드 블록을 함께 제공한다. 다음 작업이 없으면 그 사실을 명시한다.
