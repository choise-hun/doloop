# 시니어(Claude) ↔ 주니어(Gemini) 협업 설명서

- **재개:** 2026-11-06 (win). 2026-11-03에 폐기했던 방식(원문: `git show 9c95a0e^:개발산출물/협업_시니어주니어.md`)을 지금 규칙(`CLAUDE.md`·`프론트_정렬규격.md`)에 맞게 고쳐 다시 쓴다
- **목적:** 작업량을 두 줄로 나눠 동시에 진행하고 토큰을 나눠 쓴다. 시니어는 설계·백엔드·리뷰, 주니어는 명세가 끝난 구현
- **주니어가 이 파일 하나만 읽고도 움직일 수 있게 쓴다.** step별 "무엇을"은 명세(`개발산출물/명세/<step>_구현명세.md`)에, "어떻게 일하나"는 이 파일에 있다

## 0. 주니어 세션 시작 (매번 이 순서)

1. `git switch main && git pull --ff-only`
2. 읽기: **이 파일** → `개발산출물/진행_프론트기반.md`(주니어 줄 진행 파일) → 지시받은 step의 명세 → `개발산출물/주니어_체크리스트.md`
3. 진행 파일 단계 표에서 그 step의 "선행"이 끝났는지 본다. 안 끝났으면 §8 관문 문구를 쓰고 멈춘다
4. 브랜치: `step/<step ID>` (예: `step/W-1`), base = main
5. 명세 §체크리스트 순서대로 구현 → 확인 명령 실행 → 결과 파일 → PR (§6)

## 2. 두 줄로 나눈 작업 (2026-11-06 기준)

| 줄 | 진행 파일 | 맡는 쪽 | 건드리는 곳 |
| --- | --- | --- | --- |
| 백엔드 줄 | `완료/진행_티어크레딧.md`(M1, 2026-11-06 완료) → 다음 시니어 진행 파일(M2-4 등, 새로 만듦) | 시니어 | `src/main/**`, `src/test/**`, `db/migration/**` |
| 프론트 기반 줄 | `진행_프론트기반.md` (M4-1 → W-1 → L0, 소작업 J-1·J-2, M2-1a — 완료. 다음 M2-1bd) | 주니어 | `frontend/src/**`, `test/*.test.js`, `test/e2e/**` (명세 파일 목록 안만) |

- 두 줄은 파일이 겹치지 않는다. 겹치는 파일을 고쳐야 하면 주니어는 멈추고 묻는다
- 공유 문서는 쓰는 사람을 정한다: `인수인계_메모.md`·`계획/*`·`CLAUDE.md`·`GEMINI.md` = **시니어만**. 주니어는 자기 진행 파일·결과 파일·체크리스트만 고친다
- 주니어 PR이 머지되면 시니어는 **다음 작업 PR 안에서** 인수인계 메모를 맞춘다(머지 뒤 정리만 하는 PR·세션을 만들지 않는다)
- 서버와 딱 붙은 작은 화면 작업(예: M2-1c)은 명세를 쓰지 않고 시니어가 직접 구현한다 — 명세 비용 ≈ 구현 비용이면 나누지 않는다

## 3. 설계를 두 층으로 나눈다

| 층 | 문서 | 세밀도 | 언제 쓰나 |
| --- | --- | --- | --- |
| 전체 순서 | `계획/상용_서비스_계획.md` §1, 진행 파일 단계 표 | 결정·경계·완료 기준 | 처음 한 번, 이후 시니어가 고친다 |
| 구현 명세 | `개발산출물/명세/<step ID>_구현명세.md` | 주니어가 **설계 판단 없이** 구현할 정도(결정·인터페이스·표). 코드는 §4.3 범위만 | 바로 다음 묶음만. 앞 step 결과를 본 뒤 고칠 수 있다 |

먼 step까지 세밀하게 쓰지 않는다. 앞 step 결과(실제 클래스 이름·마크업)에 따라 달라진다. 명세가 실제 코드와 맞지 않으면 주니어는 §6-2대로 멈추고 묻는다.

## 4. 시니어: 명세 작성 규칙

### 4.1 필수 항목 (step마다)
1. **파일 목록**: 경로, 신규/수정, 하는 일 한 줄. 목록에 없는 파일은 고치지 않는다
2. **시그니처**: 함수·컴포넌트(인자·반환 타입), export 이름. 기존 패턴 파일을 "이 파일처럼"으로 지정
3. **데이터·문구 표**: 화면 문구, 키 이름, 값. 화면이면 DOM 구조(태그·id·class·aria)와 상태(빈/로딩/에러/비로그인)
4. **검증·에러 표**: 조건 → 결과(화면 문구 또는 status/code)
5. **처리 순서·배치 약속**: 번호 단계. 화면이면 `프론트_정렬규격.md` §1의 배치 약속 표(상태·폭별 열·맞춤 그룹)를 명세에 미리 쓴다
6. **테스트 표**: 이름 / 준비 / 실행 / 기대 결과 / **잡아야 할 버그**(예: "늦게 온 응답이 덮어씀"). 실패 케이스 포함. 테스트 코드 본문은 주니어가 쓴다
7. **체크리스트**: `[ ]` 항목마다 확인 명령과 기대 출력. 다 채우면 완료
8. **금지 사항**: 이 step에서 하기 쉬운 잘못(§5 표에서 골라 쓴다)

### 4.2 이렇게 쓰면 주니어가 헤맨다 (금지)
- 응답·마크업을 생략(`{ ... }`) → 필드·요소를 모두 적는다
- 상태 코드·값을 둘 함께("200/201") → 조건별로 하나씩
- "적절히", "필요하면", "등" → 쓰지 않는다. 고를 일은 시니어가 고른다
- 기존 코드 전제를 확인 없이 쓴다 → 전제마다 직접 연 `file:line`을 붙인다
- 기존 파일을 "전체 코드"로 준다 → 바꿀 줄만 diff·전후 코드로. 전체 코드는 새 파일에만
- 화면 step 완료 기준이 소스 검사뿐 → 실제 빌드 + layout spec + 4개 폭 스크린샷을 넣는다

### 4.3 시니어가 쓰지 않는 것 — 명세는 구현이 아니다 (2026-11-07)

두 줄로 나눈 목적은 **토큰 분담**이다. 시니어가 코드를 완성해 명세에 붙이면 구현 토큰이 시니어 쪽에서 나가 목적이 깨진다(M2-1a·b에서 실제로 일어남 — 명세 789줄, 시니어가 worktree 구현·e2e 234개·변이 검사까지 돌림).

| 시니어가 쓴다 | 시니어가 쓰지 않는다(주니어 몫) |
| --- | --- |
| 결정(D표), 파일 목록, 전제 `file:line`(직접 열어 읽은 것) | 마크업·JSX·CSS 본문 |
| 시그니처·export·API 필드·타입, 문구·i18n 키 표, id·`data-*` 이름 | 테스트 코드 본문(표의 이름·준비·기대·잡을 버그만) |
| 배치 약속 표, 검증·에러 표 | 명세를 쓰기 위한 빌드·e2e·layout 실행, 스크린샷, 변이 검사 |
| **비동기·동시성 핵심 흐름만** 의사코드(골격) — 한 흐름 20~40줄, step당 합계 80줄 이하 | worktree에 구현해 보고 그 코드를 붙이기 |
| 기존 파일은 바꿀 곳의 앵커(`file:line`·식별자)와 한 줄 설명 | 기존 파일의 바뀐 블록 통째(§4.2) |

- **분량:** 명세 하나 150~250줄. 넘으면 결정·표를 줄인다(step을 더 쪼개지 않는다 — step 수가 늘면 리뷰 왕복이 늘어 토큰이 더 든다)
- **step 크기:** 주니어 step = **PR 하나, 리뷰 1번으로 볼 수 있는 크기**. 시간(1시간)으로 쪼개지 않는다. 한 세션에 안 끝나면 같은 브랜치·PR에 이어서 쌓는다
- **확인 방법:** 실행 대신 **읽기**로 전제를 확인한다(기존 테스트가 무엇을 비교하는지, 검사 범위 등). 실행해 봐야 알 것 같은 위험은 명세 "주의" 줄로 적고, 주니어가 처음 돌릴 때 확인한다(§6-2)
- **품질은 리뷰에서:** "가드를 빼면 실패하는 테스트인가"는 시니어가 PR 리뷰에서 본다(§7)
- 예외: 다국어 사전 값 대조처럼 **값 자체가 명세**인 경우만 시니어가 스크립트로 확인한다(LS-1)

## 5. AI가 저지르기 쉬운 잘못 (명세 금지 사항과 리뷰 기준)

| 잘못 | 막는 방법 |
| --- | --- |
| 명세에 없는 필드·키·props·파일을 지어낸다 | 명세 표에 없는 것은 추가 금지 |
| 함수 시그니처, export 이름, 파일 경로를 바꾼다 | 메뉴얼 항목. 바꾸려면 멈추고 묻는다 |
| 범위 밖 리팩터링, 다른 파일 수정, 포맷 일괄 변경(prettier 전체 실행 포함) | 파일 목록 밖은 손대지 않는다. `git diff --stat`으로 확인 |
| 실패하는 테스트를 단언 완화·`skip`·`known` 추가로 통과시킨다 | 테스트를 고치면 이유를 결과 파일에 쓴다. `known`(알려진 실패) 추가는 시니어만 |
| 실행하지 않은 결과를 "통과"로 쓴다 | 명령 출력 끝 몇 줄을 결과 파일에 붙인다 |
| 빈 `catch`, 에러를 삼키고 빈 값 반환 | 명세 에러 표대로 처리 |
| 라이브러리·API 이름 추측, 새 의존성 추가 | `package.json`·기존 코드에서 확인. 새 라이브러리 금지 |
| 인라인 스타일(`style=`)·`dangerouslySetInnerHTML` | CSP `style-src 'self'`. CSS Modules만 쓴다(`test/security.test.js`가 잡는다) |
| 레거시 `public/*` 수정 | 롤백용 동결. 화면 작업은 `frontend/src`만 |
| 색·간격을 토큰 밖 값으로 | `frontend/src/styles/tokens.css` 변수만. 새 토큰 추가 금지(R0-T1 토큰 일치 검사) |
| 명세와 다르게 구현하고 말하지 않는다 | 결과 파일 "명세와 달라진 점"에 쓰거나 멈추고 묻는다 |
| 무관한 파일 커밋(`test-results/`, 로그, 스크린샷) | `git status`로 확인. 목록 밖 파일은 커밋하지 않는다 |
| 다음 step까지 이어서 진행 | 한 세션 = 한 step. §8 관문 |

## 6. 주니어 행동 규칙

### 6-1. 구현
1. 명세가 없으면 코드를 쓰지 않는다(§8)
2. 판단 순서: **명세 → 체크리스트 → 명세가 "이 파일처럼"으로 지정한 기존 코드**. 셋 다 답이 없으면 멈추고 묻는다
   - 스스로 정해도 되는 것: `CLAUDE.md` "자유" 항목 — 내부 변수명, CSS 클래스 이름, 명세가 "주니어 재량"이라고 쓴 문구·간격
   - 정하면 안 되는 것: "메뉴얼" 항목 — DB 스키마, API 경로·필드, 함수 시그니처, export 이름, 파일 경로
3. 화면을 바꾸면 `프론트_정렬규격.md` §1 순서를 따른다: 배치 약속(명세에 있음) → spec 먼저 돌려 실패 확인 → 구현 → spec 통과 → 4개 폭 스크린샷 검토(§6 질문 Q1~Q9 표)

### 6-2. 막혔을 때
- 형식: 문제 한 줄 → 원인 → 추천 해결 1개(+대안 한 줄) → "진행할까요?"
- 명세의 `file:line` 전제가 실제 코드와 다르면 → 멈추고 위 형식으로 묻는다(명세를 스스로 고치지 않는다)
- 30분 넘게 같은 실패를 쫓으면 → 알아낸 것을 진행 파일 "겪은 문제"에 쓰고 멈춘다

### 6-3. step 끝 (전부 해야 완료)
1. 명세 체크리스트를 모두 `[x]`로 하고, 확인 명령 출력 끝 몇 줄을 **결과 파일** `개발산출물/결과/<step ID>_<이름>.md`에 붙인다
   - 결과 파일 필수 절: 바꾼 파일 표 / 확인 명령 출력 / 스크린샷 검토 표(화면 step) / 명세와 달라진 점 / 다음 step에 넘길 것
2. PR 전 `주니어_체크리스트.md` 전 항목으로 `git diff`를 점검한다. PR 본문에 "주니어 체크리스트 점검 완료"
3. 진행 파일 `진행_프론트기반.md` 단계 표의 상태 칸을 고친다(`리뷰 대기` + PR 번호·CI 결과)
4. 커밋 `feat|fix|test|docs(scope): 요약` + 끝 줄 `Co-Authored-By: Gemini <noreply@google.com>`
5. push → PR(base main, 기능이 다 되면 Ready, 아니면 Draft) → `gh pr checks --watch`
6. CI 통과 시 알림: `PR #n — step/<ID> → main (CI 통과, 시니어 리뷰 대기)`. 실패면 고쳐서 통과시킨 뒤 알린다

3번의 상태 칸은 `완료(머지 시) — PR #n`으로 쓴다. 머지가 곧 완료이므로 머지 뒤 상태만 고치는 PR은 없다

## 7. PR 리뷰 루프 (2026-11-07 압축 — 리뷰는 PR당 1번)

1. **주니어:** PR + CI 통과 → "시니어 리뷰 대기"로 알린다
2. **사용자:** Claude 세션에 `PR #n 리뷰해줘`(아래 시작 멘트)
3. **시니어:** 명세, §5 표, 체크리스트 기준으로 **한 번** 리뷰 → PR 코멘트 하나로 남긴다
   - **잔손질(몇 줄 안, 설계 판단 없음 — 오타·빠진 가드·문구·테스트 이름 등)은 시니어가 PR 브랜치에 직접 커밋**한다(`fix(scope): <step> 리뷰 잔손질`). 코멘트에는 고친 목록만
   - **주니어에게 돌려보내는 것은 설계·동작이 틀린 "머지 전 수정"만.** 형식: 번호, `파일:줄`, 문제, 고칠 방향
   - 나중에 해도 되는 것은 코멘트에 한 줄로 두고 `인수인계_메모.md` "나중에"로 옮긴다(따로 반영시키지 않는다)
   - 돌려보낼 것이 없으면 "리뷰 통과 — 머지하세요"
4. **주니어(돌려받은 것이 있을 때만):** 반영 커밋 `fix(scope): <step> 리뷰 n·m번 반영` → CI 통과 → 알림. **재리뷰 없이** 사용자가 머지한다
5. **체크리스트 추가는 같은 종류 실수가 두 번째일 때만**(첫 지적은 코멘트로 끝)
6. **사용자:** 머지. AI는 `gh pr merge`를 하지 않는다
7. 머지 뒤 정리 PR은 없다 — 상태 칸은 PR 안에서 이미 `완료(머지 시)`, 인수인계 메모는 시니어가 다음 작업 PR에 같이

## 8. 관문 문구

| 상황 | 주니어가 쓰는 문구 |
| --- | --- |
| step 명세 파일이 없음 | `<step ID> 구현 명세가 없습니다. 다음 진행은 문서 보강 및 검토 후 진행이 필요합니다.` |
| 선행 step이 머지되지 않음 | `<step ID>의 선행 <선행 ID>가 아직 머지되지 않았습니다. 머지 후 진행합니다.` |
| 묶음 마지막 step 완료 | `프론트 기반 묶음(<step 목록>) 단계 완료하였습니다. 다음 진행은 문서 보강 및 검토 후 진행이 필요합니다.` |
| 명세로 판단할 수 없음 | 문제 한 줄 → 원인 → 추천 1개(+대안) → "진행할까요?" |
