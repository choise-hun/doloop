## 2. 구현과 자체 검토 근거

- `TakeService.kt:302`, `:445`, `SongService.kt:397`, `ProfileService.kt:352`, `TierService.kt:289`: 삭제 전 같은 트랜잭션에서 기존 `removeShareAttachments` 호출 5곳 추가. 즉시 purge가 있는 경로는 반환 ID를 합치고, 계정 삭제·티어 정지는 cron 대기열에 남긴다. 삭제는 프로필 잠금을 먼저 획득해 확정과 직렬화한다. DB 정리용 서비스 객체는 저장소 없이 공통 트랜잭션 함수만 사용하며 I/O를 수행하지 않는다.
- `ShareAttachmentService.kt:192`: 이번 세션 외 ready 20개 및 이동 24시간 확정 20건 검사. 기존 Supabase tx1/tx2와 Drive 업로드/확정에 적용한다. ready 확정과 V13 이력 insert는 같은 트랜잭션이며 유지·같은 녹음 재요청은 이력을 추가하지 않는다.
- `ShareAttachmentService.kt:198`: Drive 확정은 소유·세션·원본·uploaded 조건의 행만 `FOR UPDATE`하고 만료를 재검사한다. 외부 I/O 없이 ready 변경·guard 삭제·기존 ready 정리·게시·확정 이력 기록을 커밋한다.
- `ShareAttachmentService.kt:226`: Drive 업로드는 소유·동의·티어·이름·숨김·상한·저장 위치를 바이트 reader보다 먼저 검사한다. tx1 → 최대 10MB+1 읽기·실제 크기/시그니처 검사 → DB 밖 upload → tx2 uploaded 전환. 취소/실패 보상은 prepared key와 실제 guard를 확인하고 NonCancellable에서 정리한다. Drive 접근·토큰 수신 없음.
- `ShareAttachmentService.kt:320`: 만료 진행 행은 `FOR UPDATE SKIP LOCKED` 후 상태·시각 재확인, 공통 정리로 guard 해제. 숨김 30일 초과 카드도 공통 정리한다. `StorageTrashService.kt:73`: shared 키만 최대 50개 claim·백오프 시각 갱신·커밋 뒤 purge, stuck/overdue 집계·로그. 개인 키는 새 cron에서 처리하지 않는다.
- `EpisodeRoutes.kt:153`: 신규 경로에 기존 인증 플러그인을 적용한다. 기존 `EpisodeLogService`·호출 라우트 파일을 변경하지 않도록 Main에서 lifecycle 경로를 별도 등록했다. 기존 공개 API 경로와 응답은 명세 추가분 외 변경하지 않았다.
- `AdminService.kt:225`: 첨부 존재 여부는 신고 목록 SQL의 상관 EXISTS로 읽는다. 기존 신고·카드·프로필의 단일 READ COMMITTED 스냅샷을 유지하며 추가 개별 조회를 만들지 않았다.
