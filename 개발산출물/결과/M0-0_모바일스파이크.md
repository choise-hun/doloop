# M0-0 결과 — 모바일 미디어 실기기 사전 확인(스파이크)

> 2026-11-15 / Mac / 시니어(Claude) + 사용자(실기기 조작). 진행 파일: [완료/진행_모바일스파이크](../완료/진행_모바일스파이크.md)
> 스파이크 코드: 버리는 브랜치 `spike/M0-0`(최종 `8caabcc`, Capacitor 8.6.2). main에는 이 결과 문서와 진행 파일 아카이브만 넣는다.

## 1. 판정

- **4기기 × T1~T5 모두 기록 완료.** Android 2대는 앱 번들 방식(A)으로 전부 통과. iOS 2대는 A에서 **T1 실패(YouTube 오류 153)**, 원격 https 로드(B)로 T1~T5 통과.
- §2 규칙(한 기기라도 실패하면 대안을 먼저 묻는다)에 따라 사용자에게 대안을 물었고, **사용자 결정(2026-11-15): Capacitor 유지 + iOS 보정.** PWA 전환·iOS 원격 로드 고정은 채택하지 않았다(원격 로드는 보정 실패 시 물러설 자리로만 남김).
- 따라서 M0-1은 진입 가능하되, **첫 step에서 iOS 오류 153 보정을 실기기로 먼저 확인**한다(§5). 계획의 M0-1 다른 선행(웹 기능 수용 기준·검수 통과)은 그대로다.

## 3. 원인 분석

### 3.1 iOS T1 — 오류 153(동영상 플레이어 구성 오류)

- A 방식 iOS 출처는 `capacitor://localhost`다. YouTube IFrame이 임베드 출처(Referer)를 확인하지 못해 오류 153을 낸다. 같은 기기에서 https 출처(B)로 불러오면 통과하므로 원인은 출처 scheme이다.
- Android의 A 방식 출처는 `https://localhost`라서 문제가 없었다(갤럭시·Lenovo 모두 통과).

### 3.2 iOS T4 — 녹음 중 영상 재생 음량 저하(주의)

- 마이크 녹음을 켜면 영상 재생 소리가 크게 작아진다. iPad가 iPhone보다 심하다. **녹음 파일 자체의 목소리 크기는 정상**이다. 처음 "녹음도 작다"던 보고는 작아진 영상 소리가 다시 녹음된 것이었다.
- **iPad Safari(앱 밖)에서도 똑같다** → Capacitor 문제가 아니라 iOS WebKit 공통 동작이다. PWA로 바꿔도 해결되지 않는다.
- 웹 코드는 이미 `echoCancellation/noiseSuppression/autoGainControl: false`(`frontend/src/pages/PracticePage.tsx:1096-1097`)다. 마이크를 쓰는 동안 iOS 오디오 세션이 재생+녹음으로 바뀌면서 출력이 낮아지는 것으로 추정한다(미확정).
- 판정 기준("녹음이 시작되고 영상 소리가 계속 들리며, 녹음 파일이 재생된다")은 충족하므로 통과로 기록했다. 다만 연습 품질에 영향이 있어 M0-1/M0-3 오디오 항목으로 넘긴다.
- Android 2대는 같은 시험에서 음량 저하가 없었다.

## 5. M0-1 입력

1. **첫 step — iOS 오류 153 보정 확인(실기기).** 후보: 우리 https 도메인에 플레이어 전용 페이지를 두고, 앱(`capacitor://localhost`)에서 그 페이지를 iframe으로 넣어 YouTube 플레이어의 출처를 https로 만든다. 이 방법은 **아직 시험하지 않았다.** iPhone에서 T1·T2(재생·구간·배속 제어가 iframe을 넘어 전달되는지)를 먼저 확인한다. 실패하면 iOS만 원격 로드(B)로 물러서는 안을 사용자에게 다시 묻는다. B는 Capacitor 문서상 운영용이 아니며 App Store 심사 4.2·오프라인 동작 위험이 있다.
2. 발견 문제 1~3(라우팅·safe area·API Origin)을 정식 도입 범위에 넣는다.
3. iOS 오디오(§3.2)는 네이티브 오디오 세션 설정으로 나아지는지 M0-3 "오디오" 항목과 함께 확인한다. WKWebView가 오디오 세션을 직접 관리하므로 보정이 안 될 수도 있다(미확인).

## 6. 재현 방법

`spike/M0-0` 브랜치에서 [진행 파일 §4.1](../완료/진행_모바일스파이크.md) 명령을 쓴다. 이번에 추가로 검증한 부분:

```bash
# iOS 실기기(무료 Personal Team, Xcode에 Apple ID 로그인 필요)
cd ios/App && xcodebuild -project App.xcodeproj -scheme App -configuration Debug \
  -destination 'id=<기기 UDID>' DEVELOPMENT_TEAM=<팀 ID> CODE_SIGN_STYLE=Automatic -allowProvisioningUpdates build
xcrun devicectl device install app --device <UDID> <DerivedData>/Build/Products/Debug-iphoneos/App.app
xcrun devicectl device process launch --device <UDID> com.ulevelp.spike
# 첫 설치 후 기기에서: 설정 → 일반 → VPN 및 기기 관리 → 개발자 앱 신뢰. 개발자 모드 필요
```

- B 방식은 `CAP_SERVER_URL=https://ulevelp-d5ympfsmfq-du.a.run.app npx cap sync ios`로 iOS에만 적용했다(`cap sync android`는 A 그대로).
- Android는 `adb install -r` 뒤 `adb shell monkey -p com.ulevelp.spike -c android.intent.category.LAUNCHER 1`로 실행한다. USB 디버깅 허용 창을 승인해야 한다(`unauthorized`).
