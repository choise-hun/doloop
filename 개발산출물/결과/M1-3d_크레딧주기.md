## 1. 규칙 (사용자 결정 2026-11-05 + 이 step에서 정한 세부)

| # | 규칙 |
| --- | --- |
| D1 | **무료 → 유료**: 그 순간 그 티어의 월 지급(Pro 170·Pro+ 350)을 주고, 다음 충전 = 전환 시각 + **30일(정확히 720시간, KST 자정 맞춤 없음)** |
| D2 | **충전**(cron, 매시 정각): 충전 시각이 지난 계정마다 남은 월 지급분 소멸 → 그 시각의 실제 티어(override 기한 반영)가 유료면 지급, 다음 = **이전 다음 + 30일**(cron이 늦어도 경계가 밀리지 않음. 여러 주기를 건너뛰었으면 지금이 든 주기로 한 번만 지급) |
| D3 | **Pro → Pro+**: 이번 주기에 지급한 티어와의 **차액만 즉시**(350 − 170 = 180, 원장 `monthly_topup`), 다음 충전 시각 그대로. `credit_cycle_tier`가 그 주기의 가장 높은 티어를 기억 → 내렸다 다시 올려도 차액은 주기에 한 번 |
| D4 | **유료 → 낮은 유료(Pro+ → Pro, override 만료 포함)**: 차액 회수 없음, 다음 충전부터 170 |
| D5 | **유료 → 무료**: 전환 때 아무것도 안 한다. 남은 월 지급분은 주기 끝까지 쓸 수 있고, 충전 시각에 소멸 + 주기 종료(두 열 NULL), 충전 없음. `/credits`의 `nextGrantAt`은 무료면 null |
| D6 | **주기 안 재가입**(무료로 내린 뒤 충전 시각 전에 다시 유료): 앞 주기의 남은 월 지급분을 소멸하고 **새 주기**(즉시 지급 + 그 시각 + 30일). 같은 분 안 재가입은 지급 키가 같아 새로 주지 않고 차액만 본다 |
| D7 | **충전 시각이 지났는데 cron 전에 티어를 바꾸면**(최대 1시간 창): 관리 API가 먼저 **바꾸기 전 티어로** 충전을 처리한 뒤 전환 판정(cron이 제때 돌았을 때와 같은 결과) |
| D8 | **주기 없는 유료 계정**(V7 배포 시점에 이미 유료, DB로 바로 바꾼 계정): 다음 cron이 그 실행 시각에 주기를 시작한다. → 계획(§3-1)의 "V7에서 `credit_cycle_next_at = now()`" 대신 cron 쪽에서 처리(데이터 UPDATE 없음, 결과는 같음 — 배포 뒤 최대 1시간 안에 지급) |
| D9 | 원장 `period` = **주기 시작 시각 키** KST 분 단위 `YYYY-MM-DDTHH:MM`(예 `2026-11-06T14:03`). 지급·소멸·차액 모두 그 주기의 키. 유니크 인덱스 `(user, bucket, reason, period)`가 cron 재시도 중복의 마지막 방어 |
| D10 | `tier-expire` cron은 크레딧 주기를 건드리지 않는다(D5 — 소멸은 충전 시각의 `monthly-credits`가 실제 티어로 판정) |

결제(M4-2) 웹훅도 같은 함수를 부른다: `Transaction.onTierChange(userId, before, after, now)` (앞에 `processDueCycle(userId, before, now)`).

## 4. 겪은 문제

- 첫 설계의 `startCreditCycle` ↔ `topUpCreditCycle` 상호 호출이 "같은 분에 이미 지급 + 주기 없음"이면 무한 재귀가 될 수 있었다 → 시작 쪽은 **주기가 있을 때만** 차액 경로로 넘긴다(코드 작성 중 발견, 테스트 C5로 같은 분 재가입 확인)
- 주기 없는 계정의 월 버킷 잔액(관리 API로 월 버킷에 준 것)을 주기 시작 때 "새 키"로 소멸하면 주기 끝 소멸이 같은 키라 건너뛰어진다 → 주기 시작 때는 **앞 주기가 있을 때만** 소멸(없으면 그 잔액은 새 주기 끝에 함께 소멸)
