## 1. 목적과 승인 경계

목표 기능은 **연습 기록 카드 공유**다. 사용자는 자신의 연주 녹음을 카드에 첨부하여 커뮤니티에 게시한다. 개인 녹음 저장소를 공개로 바꾸는 대신 공유 시점의 카드 내용과 선택한 녹음 파일을 커뮤니티용 사본으로 적재한다.

- 사용자 제시 방향: 개인/공유 데이터 분리, 카드 및 녹음 사본, 개인 원본 카드 삭제 → 커뮤니티 카드 삭제의 단방향 연결, 최초 공유 때 동의.
- 이번 승인: 대화에서 나온 방향과 검토 필요 내용을 임시 문서로 보존하고 다음 세션에서 하나씩 검토.
- 미승인: 구체적인 DB/API/DTO 계약, 저장소 구성, 상세 구현, Git 커밋·push·PR·배포.
- 아래의 **권장안·후보·미정**은 사용자 확정 결정이 아니다. 이전 S3b 제안의 ‘녹음 1개’, ‘서명 URL’도 자동 확정하지 않는다.
- ‘정책 대기’는 구현 금지 판정이나 AI 안전정책 반려의 증거가 아니다. 미결정 항목은 §9에서 개별적으로 검토한다. 이미 제시된 기능 목표를 반복 승인받지 않는다.

## 3. 데이터 경계와 복사의 의미

```text
개인 영역: 연습 기록 + 본인 녹음(DB 메타데이터 / 개인 저장소·Drive 파일)
                     │ 사용자가 공유 대상 선택 → 최초 동의 → 사본 생성
                     ▼
커뮤니티 영역: 공유 카드 스냅샷 + 공유 첨부 메타데이터 + 녹음 파일 사본

원본 카드 삭제 ───→ 공유 카드 비노출·삭제 + 첨부 사본 정리
공유 중지     ───→ 개인 원본 유지
```

- DB 행 또는 개인 파일 URL/Drive ID만 복사하는 것은 파일 사본 생성이 아니다. 커뮤니티 재생은 커뮤니티용 파일을 사용한다.
- 개인 저장소의 ACL·공개 설정은 유지한다. 읽어서 복사하는 작업은 필요하지만 개인 파일에 공개 권한을 부여하지 않는다.
- 커뮤니티용 저장 영역은 별도 버킷 또는 확실히 격리된 경로 후보로 검토한다. 논리적으로 공개된 카드라고 해서 저장소 자체를 익명 공개 버킷으로 만들 필요는 없다.
- 원본과의 연결은 삭제·소유권 추적 목적이다. 개인 기록 변경을 공개본에 자동 반영하는 양방향 동기화로 확대하지 않는다.
- 개인 메모, 비선택 녹음, 개인 파일 키·URL·Drive ID·OAuth 토큰은 공개 DTO로 보내지 않는다. 파일 메타데이터의 개인 파일명·태그 노출 여부도 확인한다.
- 공유 전 앱·사용자·세션·녹음 소유권과 첨부 가능한 관계를 서버가 검증한다. 다른 앱/사용자 녹음으로 대체하지 않는다.

## 4. 사용자 흐름 (검토용 권장안)

1. 개인 연습 기록 카드에서 ‘공유’를 선택한다. 기존 공유 진입·공개 이름·티어 조건과 충돌하지 않게 한다.
2. (선택) 같은 세션의 본인 녹음 중 1개를 고른다. 고르지 않으면 현행처럼 녹음 없는 카드로 게시한다(R01 확정).
3. 공개될 정보·녹음·청취 범위를 미리 보여 준다. 여러 테이크를 자동으로 전부 첨부하지 않는다.
4. 최초 공유 동의를 받는다. 거절하면 개인 데이터는 유지하고 게시하지 않는다.
5. 파일을 커뮤니티 영역으로 복사하고 검증한다. 준비 중 카드는 피드·재생 API에 노출하지 않는다.
6. 원본 존재·소유권·동의·티어·신고/숨김 상태를 다시 확인한 뒤 카드와 첨부를 확정한다.
7. 성공 결과로 화면을 갱신한다. 중복 클릭·네트워크 재시도는 중복 게시/중복 파일을 만들지 않도록 설계한다.
8. 청취자는 공유 카드의 녹음 사본을 재생한다. 단일 플레이어와 로딩·재생·오류·재시도를 제공한다.

새 공유 준비 실패 시 기존 공개본이 있다면 이를 유지하는 원자적 교체를 권장한다. 취소·계정 전환·원본 삭제·기한 만료 후 도착한 복사 결과는 게시하지 않는다.

## 5. 최초 동의와 안내 개정

- 사용자 방향은 최초 공유 동의다. 계정 단위인지 카드 단위인지, 녹음 없는 최초 공유도 녹음 공개까지 포함하는지 R02에서 확정한다.
- 권장안: 서비스가 해당 계정에 필요한 공유 안내 버전의 동의 이력을 보관하고, 매 게시 시 선택한 카드·첨부의 공유 의사는 게시 행동으로 확인한다. 일괄 녹음 자동 공개 동의로 해석하지 않는다.
- 동의 이력 후보: 사용자 식별자, 안내 버전, 동의 시각, 허용 범위. 각 게시본에는 실제 선택한 첨부와 게시 시점을 기록한다. 보관 기간·철회 후 처리·재동의 조건은 미정이다.
- 최초 안내 후보: 공개 정보, 녹음 사본 생성·저장 목적, 청취 대상, 공유 중지·원본 삭제 영향, 이미 전달된 파일의 회수 한계, 보관/정리 기준, 신고 처리.
- 기존 사용자·기존 카드·기존 개인 녹음은 자동 공개하거나 과거 동의를 신규 녹음 공유 동의로 간주하지 않는다.
- ‘어떤 경우에도 녹음 비공개’ 문구를 명시적 공유 예외와 일치시키고 ko/en/ja, 개인정보 안내, 공유 확인 UI, 상위/기존 명세의 영향 범위를 조사한다.
- 타인 음성·반주 등 권리 안내와 신고/차단 흐름도 검토한다. 이 문서는 법적 적정성이나 특정 법령 준수를 인증하지 않는다. 법률·운영 검토가 필요한 실제 질문만 분리하고 명세 조사를 일괄 중단하지 않는다.

## 6. 수정·삭제·철회와 접근 차단

| 사건 | 처리 방향 | 구분 |
| --- | --- | --- |
| 개인 원본 카드 삭제 | 연결 공유 카드도 삭제하고 첨부 사본 정리 | 확정(R03): 세션이 사라지는 모든 경로. 세션 개별 삭제 기능은 추후 별도 구현 |
| 커뮤니티 공유 중지 | 공개 접근 차단·사본 정리, 개인 원본 유지 | 권장안. 현행 철회 이력·신고 이력 보존 범위 검토 |
| 개인 기록 수정·녹음 추가 | 기존 공유본 유지, 명시적 재공유 시 교체 | 권장안, 자동 동기화 여부 R04 |
| 개인 녹음만 삭제 | 해당 공유 첨부도 제거하고 카드는 유지 | 확정(R03). 업로드 시 교체 경로 포함. 외부 Drive 직접 삭제는 앱이 감지 못함(R06) |
| 개인 저장 위치 이동 | 이미 생성된 공유 사본 유지 | 권장안. 개인 저장소 마이그레이션을 공유 철회로 오해하지 않음 |
| 계정·곡·세션 삭제 | 관련 카드 비노출 및 사본 정리 | 삭제 경로별 누락 검증 필요 |
| 관리자 숨김·티어 정지 | 카드와 재생 접근 함께 차단 | 저장 파일 유지/삭제·복원/재공유 조건은 R08에서 결정 |
| 원본 복구·재구독·숨김 해제 | 자동 재공개하지 않는 방향 | 기존 게시 계약과 대조 후 확정 |

DB CASCADE만으로 저장소 파일이 삭제되지는 않는다. 삭제 대상 파일 식별자를 잃기 전에 내구성 있는 정리 작업을 남기고 삭제와 함께 커밋하는 구조를 검토한다. 계정/곡/세션 삭제·관리자 삭제 등 모든 진입점에서 동작해야 한다.

카드 비노출 시점, 신규 재생 접근 차단 시점, 저장소 물리 삭제 완료 시점은 구분한다. URL 방식이면 기존 발급 URL·브라우저/CDN 캐시의 잔여 접근 시간이 있을 수 있다. 즉시 차단이 요구되면 서버 중계 등 대안을 비교한다. 이미 사용자가 내려받은 사본의 회수는 보장하지 않는다.

## 7. 파일 취득·저장·트랜잭션 검토

- Supabase 저장 녹음: 서버 소유권 확인 후 내부 읽기/복사 경로 후보. 파일 크기·메모리·시간 제한과 스트리밍 가능성을 확인한다.
- Drive 저장 녹음: 사용자 인증으로 브라우저에서 읽어 업로드하는 방식과 서버 위임 방식 비교. 기존 로그인/권한 범위·재인증·토큰 보관 영향을 확인한다. 임의 URL을 서버가 가져오게 하지 않는다.
- Drive에서 받은 바이트를 브라우저가 전송하면 원본 ID가 본인 것이라는 검사만으로 원본과 바이트의 일치가 증명되지는 않는다. ‘연결 녹음의 정확한 복사’ 보장 수준과 검증 방법을 결정한다.
- 새 파일 업로드는 허용하지 않는다(R01 확정). 첨부 원본은 해당 카드 세션의 기존 `takes` 행뿐이다.
- 저장소 복사와 DB 트랜잭션은 하나의 원자적 트랜잭션이 아니다. 준비 작업 식별자·중복 방지·확정 여부 확인·보상 삭제·고아 사본 정리를 설계한다.
- 외부 I/O 중 DB 잠금을 오래 유지하지 않고 확정 시 재검사한다. 취소를 전파하고 커밋 직후 취소로 정상 파일을 오삭제하지 않는다. [백엔드 규칙](../../docs/rules/backend-kotlin.md) §1~4 적용.
- 삭제 실패는 성공으로 숨기지 않고 재시도한다. 별도 버킷이면 기존 정리 대기열이 버킷/저장소를 구분할 수 있는지 확인한다.
- 첨부 개수·파일 크기·길이·MIME/실제 포맷·총 저장량·일일 게시량·재생 트래픽·사용자별 제한·동시 복사 한도·타임아웃은 수치까지 후속 결정한다. 아직 수치를 발명하지 않는다.

## 10. 결정 기록

### R01 / 2026-11-12 / 확정

- **사용자 답:** ① 녹음 없는 카드 공유 유지(첨부 선택 사항). ② 초기 첨부 0~1개, 확장 가능한 구조. ③ 같은 세션의 기존 녹음만 첨부 가능(다른 세션 녹음·외부 파일 업로드 불가).
- **이유·영향:**
  - 현행 녹음 없는 공유는 회귀 없이 유지된다(V11). 첨부 원본 = 카드 `session_id`와 같은 `takes.session_id` 행. 기존 복합 FK `(user_id, session_id, song_id)`가 본인·같은 연습임을 보장하고, 서버는 게시 시 이 관계를 재검사한다.
  - 새 업로드 API·포맷 검증 경로가 생기지 않는다. R06은 “기존 개인 사본 → 커뮤니티 사본 복사”만 조사한다.
  - 세션에 녹음이 여러 개면 1개를 고르는 UI가 필요하다. 자동 첨부 없음. 녹음 `memo`·개인 파일명은 비공개.
  - 0~1개 제한은 서비스 검증으로 두고, 첨부는 카드와 별도 엔터티(1:N 가능)로 설계해 개수 확대 시 스키마 변경을 피한다.
- **첨부 종류 확장 여지(사용자 질문, 2026-11-12 조사):**
  - 현재 녹음 형식은 다섯 군데에 오디오 전용으로 고정되어 있다: `takes.mime` CHECK 6종 audio·`size_bytes ≤ 50MB`([V1:94-96](../../src/main/resources/db/migration/V1__init.sql#L94-L96)), `TakeService.MAX_FILE_BYTES`([TakeService.kt:649](../../src/main/kotlin/ulevelp/service/TakeService.kt#L649)), 확장자 맵([apiClient.ts:614](../../frontend/src/lib/apiClient.ts#L614), [NotionPushWorker.kt:71](../../src/main/kotlin/ulevelp/notion/NotionPushWorker.kt#L71)), CSP `media-src 'self' blob: <supabase>`([index.html](../../frontend/index.html)). 즉 `takes`는 “녹음” 테이블이며 영상 파일 확장은 마이그레이션·검증·저장 비용 정책을 동반한다.
  - 따라서 공유 첨부는 `takes`를 넓히지 않고 **첨부 종류(kind)를 가진 별도 엔터티**로 설계한다. 초기 kind는 `audio_copy`(녹음 사본)만 구현하고, 나중 kind를 추가할 때 첨부 테이블 CHECK 값 + DTO 판별 필드 + 재생 컴포넌트만 늘리게 한다. 공개 DTO는 처음부터 `kind` 판별 필드를 두는 방향을 상세 명세에서 검토한다.
  - 연주 영상: 파일 업로드는 저장·트래픽 비용 때문에 **도입하지 않는 방향(후보 제외)**. 대안 후보는 외부 영상 링크 kind(예: `external_video`). 기존 자산: YouTube ID 정규식 CHECK(`^[A-Za-z0-9_-]{11}$`), `ExportImportService.extractVideoId`, CSP `frame-src https://www.youtube.com`. 링크는 서버가 가져오지 않고 ID만 저장·임베드(SSRF 없음), 파일 사본 없음 → 원본 삭제 전파·물리 삭제 이슈가 없지만, 외부 영상 자체의 비공개/삭제는 서비스가 통제하지 못한다.
- **남은 조사(R01):** 외부 영상 링크는 이번 S3b 범위 밖(후속 후보). 도입 시 허용 호스트(YouTube만?), 일부공개 영상 처리, 신고 대상 포함, 곡 영상과의 구분 표시를 결정한다. 녹음 첨부 메타데이터 공개 항목(길이·MIME)은 R09/상세 명세에서 확정.

  - 동의 안내는 **하나의 커뮤니티 공유 안내**로 받되, 그 안에 녹음 첨부 시 사본 생성·청취 대상·철회 한계를 포함한다. 기록에는 안내 버전과 허용 범위 항목(카드 공유, 녹음 첨부)을 남긴다. 녹음 없이 첫 공유한 사용자도 이후 녹음 첨부 시 추가 동의 화면 없이 게시별 녹음 선택만으로 진행한다(동의 범위에 이미 포함).
  - 표시 시점: 공개 이름 설정 화면 두 곳에서 동의 안내를 함께 보여 기록한다. 이미 공개 이름이 있거나 동의 기록이 없는 기존 사용자는 **다음 공유 시도 때** 같은 안내를 보여 준다(과거 체크박스를 동의 기록으로 간주하지 않음). 공개 이름 변경만으로 재동의를 받지 않는다.
  - 강제 지점은 서버: 카드 게시·녹음 첨부 요청에서 유효한 동의 기록(현재 요구 버전 이상·해당 범위 미철회)을 검사한다. 공개 이름 API의 기존 계약(`PUT /me/public-name`)은 이름 저장 전용으로 두고, 동의 기록은 별도 계약 후보로 둔다(이름 API에 동의를 섞을지는 R10 상세 명세에서 결정).
  - 게시별 공유 의사: 게시마다 카드 내용·첨부 녹음을 미리 보고 게시 버튼을 누르는 행동으로 확인한다. 현행 게시별 체크박스 유지 여부는 UI 명세에서 결정.
  - 버전: 안내 버전에 “재동의 필요” 표시를 둔다. 확대 변경이면 다음 게시·첨부 때 재동의, 기존 게시물은 그대로. 단순 문구 수정은 버전만 올리고 재동의 없음.
  - 철회 대상은 **녹음 첨부 범위**다. 카드 공유 전체 중지는 기존 게시물별 ‘공유 중지’로 한다. 철회 확인 대화: [첨부도 모두 삭제] / [새 첨부만 중단] / [취소]. ‘첨부도 모두 삭제’는 해당 사용자의 모든 공유 첨부를 비노출 후 사본 정리(R07 삭제 경로 재사용), 카드는 녹음 없이 유지. ‘새 첨부만 중단’ 후에도 기존 첨부는 게시물별로 개별 제거 가능해야 한다(R04에서 확정). 철회 후 다시 첨부하려면 재동의.
- **남은 조사:** 동의 이력 보관 기간·계정 삭제 시 처리(R09), 일괄 삭제 진행/실패 표시·재시도(R07·R10), 철회 버튼 위치(설정 또는 프로필, UI 명세), 폴더 공유·학습 기록 공유 등 기존 다른 공개 기능에 같은 동의를 적용할지(현재 S3b는 연습 카드만 대상, 확대는 범위 밖 후보).

  - Drive 원본 = 브라우저가 Drive에서 읽어 서버의 “공유 사본 업로드”로 전송, 서버는 확정 시 원본 `takes` 행의 MIME·크기와 대조하고 파일 앞부분 포맷 헤더를 확인한다. 서버는 Drive 토큰을 갖지 않고 임의 URL을 가져오지 않는다(SSRF 없음).

- **조사 결과 — Drive 창 깜빡임(사용자 질문):**

  - 신고·이력: 현행 유지. 원본 삭제로 카드가 CASCADE 삭제되면 신고 기록도 함께 사라지고, 관리자 조치는 감사 로그에 남는다.
- **남은 조사:** 길이·크기 상한을 서버가 어떻게 신뢰할 수 있는 값으로 판정하는지(`takes.duration_sec`·`size_bytes`는 클라이언트 신고값이므로 Drive 경로는 업로드 바이트 실측과 대조, R10). 상한 수치는 운영 후 비용을 보고 조정. 숨김 보관 30일 경과 정리 작업은 R07 재시도 작업과 같은 실행 수단 사용 가능한지 R10에서 확인.
