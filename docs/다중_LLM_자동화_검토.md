# 다중 LLM 자동화 검토와 실행 초안

작성일: 2026-11-09. 사용자 지정 흐름과 기존 구독 로그인 사용을 기준으로 검토했다.
기존 파일은 변경하지 않았다. 이 문서와 실행기는 기존 역할 규칙을 전역 교체하지 않는다.

## 1. 결론

**적용 가능하다. 세 회사 CLI를 로컬 실행기가 순차 호출하고, 파일로 결과를 인계하는 구조를 권장한다.**
사용자는 처음에 목표·허용 파일·검증 명령을 정하고 명세가 나온 시점에 한 번 확인한다.
그 이후 구현·검증·검토는 자동 연결한다. 일반적인 성공 경로에서의 확인 횟수이며,
모호한 계약·인증 실패·권한 거절·검증 실패가 발생하면 원인을 해결해야 한다.

이번 산출물은 실행 가능한 **연결 프로토타입**이다. 실계정 네 단계 통합과 무인 Git 게시까지 검증된 완성 도구는 아니다.
현재 CM-BE 등 제품 작업에는 적용하거나 역할을 재배정하지 않았다.

```text
목표·허용 파일·검증 명령
  → Gemini CLI: 탐색·초안
  → Codex CLI: 실제 코드 대조·명세
  → 사용자: 명세 검토·해시 확인
  → Claude Code: 허용 파일 구현
  → 실행기: 지정 검증 명령·종료 코드 확인
  → Gemini CLI: 코드·명세·검증 로그 검토
  → 검토 보고서 / 결함이면 중단
  → 후속 확장: 조건을 만족할 때 결정적 Git 게시
```

## 2. 원문에서 채택하거나 고칠 부분

| 주장 | 검토 결과와 적용 방법 |
| --- | --- |
| 모델별 분업이 토큰 관점에서 최적 | 사용자 경험에 기반한 좋은 초기 가설이다. 모델별 우열·최적 비용은 입증되지 않았다. 실제 재작업과 한도 소모까지 측정한다. |

| API 오케스트레이션과 파일 인계는 양자택일 | 파일은 인계 형식이고 CLI/API는 호출 수단이다. CLI 자동 호출 + 파일 인계를 함께 사용한다. 별도 프레임워크는 초기에는 필요 없다. |
| 검토 모델이 모든 테스트와 Git을 담당 | 테스트 명령·종료 코드·Git 상태는 실행기가 확인하고, 모델은 의미·계약·결함을 검토한다. 모델의 “통과” 문장만으로 게시하지 않는다. |
| Antigravity와 Gemini CLI를 동일시 | 별도 제품·실행 표면이다. Antigravity를 화면 조작하는 대신 Gemini CLI를 자동화 어댑터로 사용한다. 모델·한도·동작 동일성은 보장하지 않는다. |

기존 모델별 시니어·주니어 배정은 이번 검토에서 고정 제약으로 쓰지 않았다.
새 실행 프롬프트는 이번 단계의 사용자 배정을 명시한다. 기존 규칙 파일을 읽더라도
일반적인 품질·도메인·문서 규칙은 유지하고 역할 배정만 이번 지시를 따른다.

## 4. 제공한 실행기의 범위

- [PowerShell 진입점](../scripts/Invoke-LlmHandoff.ps1), [실행기](../scripts/llm-handoff.py), [연결 검증용 설정](../scripts/llm-handoff.example.json), [오프라인 테스트](../scripts/test_llm_handoff.py).
- Python 표준 라이브러리만 사용한다. PowerShell 진입점은 Python 실행기에 인자를 전달한다.
- Windows PowerShell의 네이티브 CLI 입출력은 [UTF-8 중계기](../scripts/Invoke-LlmNative.ps1)를 거친다. 한글 stdin/stdout 보존을 Node 대체 CLI로 검증했다.
- `init`은 새 작업만 만들며 기존 작업·산출물을 덮어쓰지 않는다. 깨끗한 별도 체크아웃을 요구한다.
- `run`은 초안→명세까지 호출한 뒤 멈춘다. `approve`에 명세 SHA-256을 넘기면 구현→검증→검토를 이어간다.
- 작업 ID, HEAD, 브랜치, 파일 해시를 기록한다. 소스가 외부에서 바뀌었으면 재개를 막고 새 작업으로 다시 검토한다.
- 실행 로그와 중간 자료는 `.llm-handoff/<id>/`, 명세·결과·진행 문서는 기존 문서 역할에 맞는 경로에 생성한다.
- 구현 CLI에는 읽기·편집 도구만 제공한다. 테스트·빌드는 설정의 명령 배열을 실행기가 `shell=False`로 수행한다. 명령 문자열을 셸에 조립하지 않는다.
- 모델 실패·빈 출력·검증 명령 실패·허용 범위 밖 변경·승인 명세 변경을 감지하면 다음 단계로 넘어가지 않는다. 실패한 변경은 자동 되돌리지 않는다.
- 모델명을 지정하지 않으면 각 CLI의 현재 기본 설정을 쓴다. 반복 측정에는 `models`에 `explore/spec/implement/audit`별 실제 계정에서 사용 가능한 모델을 고정한다.

검토 산출물의 `report_ready`는 보고서 생성 상태다. 결함 없음·출시 가능·머지 가능 판정이 아니다.
검증 실패를 Claude에 무한 자동 재시도하거나 검토 지적을 무조건 자동 수정하는 루프는 넣지 않았다.
실패 단계의 `run` 재호출은 앞서 성공한 단계를 반복하지 않는다. 수정이 필요하면 원인과 부분 변경을 먼저 확인한다.

## 5. 설치·구독 전제

2026-11-09 이 PC에서 확인한 버전은 Codex `0.164.0-alpha.11.1`, Claude Code `2.1.318`,
Gemini CLI `0.67.0`, Python `3.12.7`, Node `v26.8.1`이다. Gemini CLI는 이번에
`npm install --global @google/gemini-cli`로 추가 설치했다. 저장소 의존성 파일은 바꾸지 않았다.
npm은 `@github/keytar`의 설치 스크립트가 허용 목록에 없다는 경고를 냈다. 설치·버전·help는 성공했지만
로그인 저장 동작은 아직 확인하지 않았다. 이 경고를 이유로 전역 설치 정책을 자동 변경하지 않았다.

각 CLI의 공식 로그인 절차로 같은 구독 계정에 로그인한 뒤 실제 활성 인증과 모델을 확인한다.
API 키를 새로 설정하지 않아도 되는 로그인 경로를 우선한다. **현재 이 PC의 구독 종류·잔여 한도·인증 성공은 미확인이다.**
세 서비스 구독을 보유했다는 사실만으로 모든 CLI/API 사용량이 포함된다고 가정하지 않는다.

- Codex의 비대화형 호출과 저장된 CLI 인증 재사용은 [공식 문서](https://learn.chatgpt.com/docs/non-interactive-mode)에 설명되어 있다.
- Claude Code의 계정 로그인은 [인증 문서](https://code.claude.com/docs/en/authentication), `claude -p`는 [자동 호출 문서](https://code.claude.com/docs/en/headless)를 따른다. 구독 로그인 사용을 위해 `--bare`는 사용하지 않는다.
- Gemini CLI는 [설치 문서](https://geminicli.com/docs/get-started/installation/)와 [인증 문서](https://geminicli.com/docs/get-started/authentication/)를 따른다. 캐시된 인증을 재사용하는 headless 경로와 `-p`·출력 형식은 [공식 headless 문서](https://geminicli.com/docs/cli/headless/)에서 확인했다.

호출 형태와 옵션은 로컬 `--help`와 대조했다. headless 도구 승인·조직 정책·로그인·요금 한도로
추가 확인이 필요할 수 있으므로 실계정 무인 실행 가능 여부는 연결 검증 후 판정한다.

## 6. 최초 사용 흐름

현재 작업 트리에는 사용자의 기존 변경과 이번 신규 파일이 있으므로 이 위치에서 바로 `init`하지 않는다.
별도 깨끗한 체크아웃에 실행할 제품 코드가 있어야 한다. 이 스크립트는 절대 경로로 호출할 수 있어
대상 체크아웃에 스크립트를 복사하거나 기존 문서를 수정할 필요가 없다.
아래는 사용자가 연결 검증 실행을 지시할 때 쓸 명령이며 **이번 세션에서는 실행하지 않았다.**

```powershell
$runner = 'C:\seokhunchoi_Ax_Fullstack\ULevelP\scripts\Invoke-LlmHandoff.ps1'
$target = 'C:\path\to\clean-checkout'
$task = 'C:\seokhunchoi_Ax_Fullstack\ULevelP\scripts\llm-handoff.example.json'

# 로그인 확인 후 실행. 이 run부터 모델 사용량이 발생한다.
& $runner init --repo $target --task $task
& $runner run --repo $target --id handoff-smoke

# 생성된 명세를 읽고, run이 표시한 SHA-256을 넣는다.
& $runner approve --repo $target --id handoff-smoke --spec-sha '<검토한 명세의 SHA-256>'

# 실패 원인·부분 변경·다음 단계를 조회한다.
& $runner status --repo $target --id handoff-smoke
```

일반 기능 작업에서는 설정 JSON을 **새 이름으로 생성**하고 목표·참조 파일·정확한 허용 파일·검증 명령을 바꾼다.
명세 확인 시 요구사항뿐 아니라 허용 파일과 검증 명령의 충분성을 함께 검토한다.
현재 설정은 새 텍스트 파일 하나를 만드는 연결 검증 전용이며 제품 기능의 검증 명령으로 재사용하지 않는다.

진행 파일은 실행기가 상태 JSON에서 생성한다. 공유 인수인계·전체 계획은 자동 수정하지 않는다.
실제 프로젝트에 도입할 때 현재 작업 담당자가 진행 파일 링크와 작업 순서를 기존 운영 기준에 맞게 반영한다.
`.llm-handoff/`에는 프롬프트·경로·모델 응답이 남는다. 이번 요청에서 `.gitignore`를 수정하지 않았으므로
게시 시 `git add .`를 쓰지 않고 필요한 경로만 선별한다. 여러 PC 자동 동기화와 원시 로그 보관 정책은 미구현이다.

## 7. Git 자동화와 결함 반환 설계

최종 운영안에서는 Git을 Gemini의 자유 도구 호출로 맡기지 않고 실행기 후처리로 둔다.
초기 작업 설정에 Git 게시 승인 범위가 있을 때만 커밋→작업 브랜치 push→main PR→최신 CI·리뷰 확인을 수행한다.
최초 명세 확인 이후 승인된 Git 범위를 반복 확인하지 않는다. 머지는 사용자가 한다.

게시 전 조건은 허용 파일 이외 변경 없음, 검증 명령 전부 성공, 검토의 미해결 결함 없음,
검토 대상 diff/HEAD 일치, 비밀값·임시 로그 제외다. PR 생성 후 CI 중·종료 후·최종 보고 직전 리뷰를 따로 확인한다.
검토 보고서의 자연어 “문제없음”만으로 이 조건을 대체하지 않는다.

이 프로토타입은 Git 쓰기와 외부 메시지를 실행하지 않는다. Git 후처리와 구조화된 감사 판정은 후속 구현 범위다.
Claude 구현 실패는 같은 승인 명세와 실패 로그로 구현 단계에 반환하고,
Gemini가 찾은 구현 결함은 증거와 회귀 조건을 붙여 Claude에 반환한다.
명세·요구사항의 결함이면 Codex에 반환하고 변경 명세를 다시 확인한다.
자동 수정 루프를 추가한다면 최대 횟수와 동일 실패 중단 조건을 둔다.

## 8. 토큰 최적화 판단 방법과 한계

전체 저장소 재주입, 단계마다 긴 대화 복사, 구현에 가까운 명세 작성부터 줄인다.
한 작업을 네 모델에 보내는 횟수를 고정할 필요는 없다. 작은 수정은 탐색·명세를 합치고 독립 검토만 유지할 수 있다.
이번 기본안은 사용자가 원하는 네 단계이며, 작은 작업 우회 경로는 아직 구현하지 않았다.

작업별 모델·사용량·소요 시간·수정 횟수·발견 결함·사용자 개입을 비교한다.
회사마다 다른 토큰과 구독 한도를 단순 합산하지 않고, 추가 비용·한도 소모·완료 시간과 품질을 함께 본다.
현재 실행기는 명령·응답·stderr를 저장하지만 표준화된 사용량/비용 집계는 하지 않는다.
대표 작업을 반복 측정하기 전에는 이 배치를 “최적”이라고 확정할 수 없다.

현재 한계: 실제 모델 통합 미실행, 인증 미확인, 도구/훅 정책의 환경 차이, 타임아웃 후 하위 프로세스 정리 미검증,
무시된 파일·저장소 밖 쓰기·외부 통신에 대한 강제 격리 없음, 모델 산출물 의미 검증 없음,
검토 판정에 따른 자동 수정·Git 후처리 없음. 파일/도구 검사는 사고 후 탐지이므로 별도 작업 환경을 권장한다.
이 한계들은 모델 연결 가능성의 부정이 아니라 프로토타입과 운영용 자동화의 구분이다.
