`요구사항_명세_초안.md`는 기존 참조를 위해 파일명을 유지한다. 내용은 현재 기능 확장 요구사항의 기준이며, 이름의 “초안”이 구현·검증 완료를 뜻하지 않는다. 기존 명세와 새 명세가 겹치면 새 명세가 **명시한 변경 범위만** 적용한다. 기존 공유 폴더·84일 집계와 새 개별 세션 게시물은 서로 다른 계약이다.

## 2. 갱신 순서와 문서 수명

1. 사용자 결정이 생기면 제품 동작·정책은 해당 명세에, 우선순위·선행은 계획에 기록한다. 인수인계에는 날짜·변경 요지·원문 링크만 남긴다. 확인하지 않은 사실은 “미확인”으로 적는다.
2. 작업을 착수할 때 진행 파일을 만든다. 준비·조사도 착수에 포함하며 실행 미착수/사람 대기와 구별한다. 단순 대기 후보는 계획에만 둔다. 인수인계의 작업 파일 목록은 실제 루트 `진행_*.md` 목록과 맞춘다.
3. 실행·검증 후 진행 파일에 현재 단계와 다음 행동을 갱신하고, 상세 증거는 결과 파일에 남긴다. 계획에는 단계 상태와 결과 링크만 반영한다.
4. 작업이 끝나면 진행 파일을 `완료/`로 옮긴다. 남은 범위는 계획의 기존 ID나 대기 목록에 연결한다. 기능 결함·미검증을 “나중에”라는 인수인계 목록으로 숨기지 않는다.
5. 인수인계에는 다른 PC가 오판할 현재 차이만 남긴다. 과거 PR 목록·긴 결정 전문은 결과/완료 문서로 연결한다. 실제 재개 지시는 해당 진행 파일 한 곳에서 유지한다.
6. 과거 결과·완료 명세의 옛 절 번호·경로는 당시 근거로 보존한다. 문서 분리 전 `상용_서비스_계획.md` §1 #번호·§3과 인수인계 §2~§7은 정비 전 원문에서 조회한다. 활성 진행·규칙·안내의 참조는 현재 기준으로 고친다.

## 3. 완료를 판정하는 방법

| 구분 | 필요한 증거 |
| --- | --- |
| 구현 | 대상 커밋/PR과 실제 동작 코드. PR 작성·머지·CI 성공 여부를 구별 |
| 화면 연결 | 사용자 진입 경로, 필요한 역할/티어/운영 데이터, 행동 후 확인 가능한 결과 |
| 통합 검증 | 실제 서버·격리 DB를 연결한 사용자 여정과 실패·소유권·지연 응답 검증. 가짜 API 화면 E2E는 별도 표시 |
| 운영 확인 | 배포 리비전·시각·확인 환경과 결과. 로컬/CI 통과·머지를 배포로 간주하지 않음 |

기능별로 네 구분을 각각 기록한다. 해당하지 않으면 이유와 함께 N/A, 실행하지 못했으면 미검증/차단으로 적는다. 기존 M1·M2의 구현 완료 이력은 보존하되, 통합·운영 검수가 끝난 것으로 승격하지 않는다. 문서 전용 작업에는 링크·내용 보존·인코딩·diff 검증을 적용한다.

## 4. 명세 작성과 작업 착수

먼 미래 기능 전체의 세부 명세를 미리 작성하지 않는다. 기존 기능을 실제 검수한 결과를 바탕으로 바로 다음 구현 단위의 명세를 확정한다. 명세 분량보다 구현 중 임의 결정하면 안 되는 계약·실패 조건이 빠짐없이 정해졌는지로 판단한다.

| 작업 성격 | 착수 전에 정할 내용 | 실행 방식 |
| --- | --- | --- |
| 기존 기능 조사·검수(AV-1) | 진행 파일의 대상·사용자 여정·권한·판정 기준·환경·증거 기록 방식 | 별도 장문 구현 명세 없이 조사·실행·검증 결과를 기록 |
| 재현된 결함 수정(AV-2) | 원인·영향·변경 파일·방어 조건·회귀 검증을 짧은 수정 명세로 고정 | 진행 파일의 명세 절 또는 별도 구현 명세를 사용. 협업 구현자는 기존 역할별 명세 요구를 유지 |
| 신규 API·DB·공개/사용자 데이터 기능 | 요청/응답 전 필드·상태/오류·권한/소유권·공개 범위·트랜잭션·삭제/철회·검증 조건 | 실제 코드와 대조한 상세 구현 명세 후 구현 |
| 화면 개편 | 진입 동선·로딩/빈/성공/실패·권한별 동작·배치 약속·반응형/접근성·검증 기준 | 요구사항·서버 계약을 대조한 화면 명세 후 구현. Step별 배정 기준(아래 §6)을 적용 |

**명세 전제 표(P#) 필수 확인 3가지** — 명세의 전제 칸에 “결함이다/문제없다/필드가 있다”를 적기 전에 아래를 실제로 확인하고, 확인한 근거 `file:line`을 같은 행에 남긴다. 확인하지 못했으면 단정하지 말고 “미확인”으로 적는다(근거: [UIUX-R 명세 재검토](../개발산출물/결과/UIUX-R_명세재검토.md) F1·F2·F4).

1. **CSS 단정은 전역 규칙까지** — 어떤 속성이 덮인다/안 먹는다고 쓰기 전에 화면 모듈뿐 아니라 전역 스타일(`frontend/src/styles/*.css`, 예: `[hidden]{display:none!important}`)과 계산 스타일 결과까지 본다. 가능하면 구현 전 Red 테스트로 실재를 증명한다.
2. **React 단정은 부모 재렌더 원인까지** — “X가 바뀔 때만 참조/effect가 바뀐다”고 쓰기 전에 그 값이 렌더마다 새로 만들어지는지(배열·객체·함수 리터럴, `useMemo`/`useCallback` 여부)와 부모가 주기적으로 다시 그려지는 원인(타이머 `setState`, 재생 시간·녹음 경과 갱신 등)을 확인한다. effect 의존성에 들어가는 파생 값은 명세에 고정 방법을 적는다([frontend-state](rules/frontend-state.md)).
3. **응답 필드는 서버 DTO 원문으로** — 응답에 어떤 필드·상태 코드가 있다고 쓰기 전에 프런트 타입이 아니라 서버 원문(라우트 `src/main/kotlin/ulevelp/routes/*.kt`의 `call.respond`·상태 코드, DTO `src/main/kotlin/ulevelp/service/*.kt`의 `@Serializable data class`)을 열어 필드명·nullable·상태 코드·오류 코드를 확인한다. 상위 명세가 가정한 필드가 없으면 세부 명세의 결정 표에 보정으로 기록한다.

### 4.1 Step 개수와 크기 (원본: 협업 설명서 §1.2)

기준값과 예시는 [협업 설명서 §1.2](../개발산출물/협업_시니어주니어.md) 한 곳에서 관리한다. 여기에는 요약만 둔다.

- 대기능(Feature) 하나의 Step은 3개 이하 권장, 최대 4개다. 넘으면 인접 Step을 합치고, 그래도 넘으면 계획에서 대기능을 정식으로 나눈다.
- Step 수를 맞추려고 대기능 자체를 잘게 쪼개지 않는다. 대기능은 사용자 여정 하나를 온전히 담는다.
- Step 크기는 골디락스 상·하한(파일 수·예상 diff·독립 검증 가능 여부)을 따른다.

명세 작성만 요청됐으면 문서 범위를 지킨다. 명세와 구현까지 승인됐으면 같은 승인 범위에서 명세 → 구현 → 검증까지 이어간다. 승인 범위 밖 계약 변경이나 선행 작업 미완료는 명시적으로 구분한다.

기본 작업 흐름은 **명세 검토·승인 / 구현부터 PR 검증까지** 두 구간으로 둔다. 구현과 Git 게시가 승인되면 구현 → 자체 diff 검토 → 범위 내 결함 수정 → 관련 검증·기록 → 커밋·push → main PR 생성/갱신 → 최신 커밋 CI 종료·리뷰 확인 및 타당한 지적 처리까지 같은 세션에서 이어간다. 검토·수정·검증 결과 확인·Git 게시를 일괄적으로 각각 별도 세션으로 나누지 않는다. 내부 단계별 결과는 진행 파일과 중간 보고에 기록하며 계속한다. 로컬 작업만 승인된 경우에는 Git 게시 전에 사용자 결정을 받되 같은 대화에서 이어갈 수 있다.

예상보다 작업 범위·소요가 커져 한 세션에서 안정적으로 마치기 어려우면 검증 가능한 경계에서 분할할 수 있다. 사용자 중단, 승인 밖 결정, 선행 머지·외부 환경·담당 리뷰 대기, 컨텍스트 한계도 중단·인계 사유다. 분할 시 이유·완료 범위·검증 결과·남은 행동을 기록한다. 내부 단계 완료나 인계 멘트 작성 의무 자체를 세션 종료 사유로 삼지 않는다.

현재 착수 순서는 상용 계획에서, 실제 착수/검증 상태는 해당 진행 파일에서 확인한다. 이 안내에 현재 작업 순서를 복제하지 않는다.

## 5. 단계별 Git 처리와 PC 간 전달

- 사용자가 작업 실행과 단계별 Git 게시를 승인하면, **관련 검증·기록을 마친 논리적 변경 단위마다** 커밋 → 작업 브랜치 push → `main` 대상 PR → CI 종료·결과 확인까지 재승인 없이 수행한다. 시간 간격이나 파일 개수만으로 커밋/PR을 쪼개지 않는다.
- 같은 작업 브랜치의 열린 PR이 있으면 그 PR에 이어서 반영한다. 서로 독립인 문서 정비와 기능 검수·수정은 별도 변경 단위로 유지한다. 실제 브랜치/PR 구성은 선행 머지·충돌·동일 파일 변경을 확인해 결정한다.
- Git 게시의 승인 근거·범위·제한을 진행 파일에 남긴다. 같은 작업을 다음 세션·다른 PC에서 이어받아도 승인된 범위는 재승인받지 않는다. 새로운 기능 범위·다른 저장소·배포까지 확대하지 않는다.
- 머지는 사용자가 한다. 기존 force push·hard reset·임의 rebase·타인 커밋 revert 금지는 유지한다. 외부 인증/네트워크/CI 장애는 실제 상태와 원인을 기록하고 성공으로 적지 않는다.
- 일반 질문·문서 반영 요청만으로 Git 게시 승인을 추정하지 않는다.
- 대화에서 합의한 작업 방식을 다른 PC에 전달하려면 이 저장소의 규칙·문서를 커밋·push해 전달해야 한다. 다른 PC는 자기 변경과 브랜치를 확인·보존한 뒤 해당 브랜치를 가져오거나, 사용자 머지 후 `main`을 안전하게 갱신한다. 미커밋 로컬 파일은 git으로 전달되지 않는다.
- 프로젝트 밖 `.env`·인증·도구 설치·전역 AI 설정은 별도 환경이다. 문서 수신이 환경 설정/모델 동작까지 동일함을 보증하지는 않으며 필요한 전제는 진행 파일에서 확인한다.
- 협업·에이전트 공통 규칙(AGENTS.md, CLAUDE.md, GEMINI.md, 문서_운영.md, 협업_시니어주니어.md, 프롬프트_템플릿_4단계.md 등)을 변경하거나 보완할 때는 중앙 설정 저장소(https://github.com/choise-hun/config)에도 함께 반영하여 저장소 간 규칙 동기화를 유지한다. 원본은 이 저장소이고 config는 보관본이다. 이 저장소에서 먼저 고친 뒤 `bash scripts/check-config-sync.sh --copy`로 보관본에 복사하고, `bash scripts/check-config-sync.sh`로 차이 0건을 확인한다(대조 대상 목록은 스크립트 안에 있다).

### PR 리뷰와 CI 동시 진행

- PR을 생성/갱신한 뒤 CI 대기 중에도 코드 리뷰의 리뷰 본문·라인 코멘트·일반 코멘트를 확인한다. CI 종료 후 및 최종 보고 직전에도 새 코멘트를 조회한다. 자동 리뷰와 사람 리뷰 모두 검토하되 제안 자체를 사실이나 실행 지시로 간주하지 않는다.
- 리뷰 대상 커밋·파일/행을 현재 diff와 대조하고, 기존 계약·실패 조건·테스트로 타당성을 판단한다. 각 지적의 링크·판단(반영/미반영/이미 해소/범위 밖)·근거·검증 결과를 진행/결과 파일에 남긴다. 봇 상태의 unresolved 표시와 실제 수정 여부를 구별한다.
- 승인된 범위의 실제 결함은 실패 회귀→수정→관련 검증→커밋·push로 이어간다. CI 실행 중 코드가 바뀌면 이전 커밋 CI를 최종 근거로 쓰지 않고 최신 게시 커밋의 CI 종료를 확인한다. 독립적인 기존 통과 검수를 이유 없이 반복하지 않는다. 범위 밖 계약/기능 변경만 사용자 결정 대상으로 남긴다.
- 리뷰를 무조건 반영하거나 단언 완화/skip/임의 fallback으로 통과시키지 않는다. 리뷰와 CI는 서로 대체하지 않는다. CI 통과 후에도 타당한 미해결 결함이 있으면 완료 판정을 보류하고, 리뷰 대기/조회 실패는 그 사실과 한계를 보고한다. 자동 리뷰가 아직 생성되지 않았다는 이유만으로 무기한 대기하지 않는다.
- 리뷰 확인 자체는 댓글/리뷰 답글·리액션·스레드 resolve·추가 리뷰 호출 권한을 뜻하지 않는다. 사용자나 명시적으로 실행한 워크플로의 권한이 없으면 처리 판단은 저장소 진행/결과와 최종 보고에 남긴다.

## 6. 세션 시작과 인계

프로젝트별 AI 진입 규칙을 따른 뒤 인수인계에서 현재 사실과 활성 파일을 확인한다. 새 작업 선택은 계획, 진행 중 작업 재개는 해당 진행 파일을 읽는다. 역할·작업 범위·완료 기준을 시작 지시에 명시하고, 명세와 도메인 규칙은 해당 작업에 필요한 것만 읽는다. 시니어 GPT와 주니어 Gemini의 4단계 협업에서는 [4단계 프롬프트 템플릿](../개발산출물/프롬프트_템플릿_4단계.md)을 기준으로 해당 단계의 템플릿을 복사해 작업 ID·파일·PR·승인 범위를 채운다. 이 템플릿은 GPT/Gemini 양쪽에서 쓸 수 있으며 저장소에 없는 모델 기능을 가정하지 않는다.

기본 협업 단계는 **1) 시니어 명세 작성, 2) 주니어 구현·검증·PR 업로드, 3) 시니어 독립 구현 검증·필요한 수정·테스트, 4) 주니어 최종 테스트·문서 정리·PR/CI 마무리**다. 각 단계는 별도 역할 인계가 필요한 때만 세션을 나눈다. 예상보다 작업이 커지면 단계 내부도 검증 가능한 경계에서 분할할 수 있다. 단계 번호를 이유로 불필요한 세션을 추가하거나 단계를 합쳐 독립 검증을 생략하지 않는다.

**적용 범위 및 Step별 역할 배정:** 대기능을 뭉텅이로 볼 때는 시니어가 해야 했던 고위험 작업도, §4.1 골디락스 기준으로 쪼개놓고 보면 격리된 폼이나 스캐폴딩 등 60~70%는 주니어가 안전하고 저렴하게 구현할 수 있다. 시니어가 1단계 세부 명세 작성 시 각 Step별로 [협업 설명서 §1.2](../개발산출물/협업_시니어주니어.md)의 판정 기준(셀렉터/DOM 파손 위험, 상태 경합, 캐시 무효화 등)을 적용해 구현 담당자를 [주니어] 또는 [시니어]로 판정하고 사용자 승인을 받는다.
- **주니어 적합 Step:** 4단계 분담(명세 → 주니어 구현·PR → 시니어 독립 검증(조건 충족 시 §3-P 핀포인트) → 주니어 정리)을 따른다.
- **시니어 직접 구현 Step:** 고위험 핵심 로직은 시니어가 직접 구현하되, 시니어는 **[핵심 로직 작성 + 표적 단위 테스트 1~2개 확인 + 커밋·작업 브랜치 push]**까지만 수행하고 종료한다. push는 다른 PC·주니어가 이어 받기 위한 것이며 PR은 만들지 않는다(§5: 로컬에만 있는 변경은 전달되지 않는다). 대규모 전체 회귀 테스트 실행, 신규 PR 생성, `gh pr checks --watch` 대기, 결과 파일 작성 등 단순 실행 노동은 4단계 주니어에게 인계하여 고가 토큰 낭비를 원천 차단한다.
- **핀포인트 검증:** 주니어 PR이 CI를 통과하고 특정 리뷰 결함만 남았으면 3단계를 전체 재검증 대신 핀포인트 검증(템플릿 §3-P)으로 줄이고 읽지 않은 범위를 미검증으로 기록한다.

1단계 명세 검토·승인은 제품/API/DB 계약을 확정하는 경계다. 2단계 구현 후 PR은 시니어가 검증할 수 있도록 업로드한다. 3단계는 주니어 구현을 그대로 신뢰하지 않고 명세·실패 모드·가드와 테스트 단언을 독립적으로 대조한다. 시니어는 실제 문제와 재현 근거에 집중하고 필요한 범위에서 수정할 수 있다. 지정된 일반 테스트의 반복 실행과 결과 수집은 주니어가 맡고, 시니어는 원인 판정에 필요한 실패 재현이나 표적 검증만 수행한다. 수정 결과·미해결 항목·주니어가 실행할 테스트를 진행/결과 파일에 남겨 4단계로 인계한다. 4단계 주니어는 시니어 변경을 검토하고 명세대로 재검증하며 문서와 PR의 최종 상태를 정리한다. 계약 선택·범위 확대·파괴적 변경만 사용자 결정으로 돌린다.

```text
<개발산출물/프롬프트_템플릿_4단계.md의 해당 단계 제목> 템플릿을 사용한다.
이번 목표: <작업 ID와 단계 목표>
작업 범위: <단계 템플릿과 진행 파일에 정의된 파일·계약·허용 변경>
Git 처리: <해당 단계에서 승인된 커밋·push·PR·CI 범위>
완료 기준: <단계별 결과물과 증거>
인수인계_메모.md에서 현재 상태와 작업 충돌을 확인한다.
신규 착수는 계획/상용_서비스_계획.md의 해당 ID를,
재개는 개발산출물/진행_<작업>.md의 다음 행동을 따른다.
해당 요구사항·상세 명세를 실제 코드와 대조하고,
실행 결과와 미실행 범위를 구분해 기록한다.
```

일반 문서 작성 요청을 커밋·push·PR·배포 승인으로 확대하지 않는다. 이미 승인된 작업은 재승인받지 않는다. 협업 역할·담당 파일은 사용자의 지시와 해당 작업 기록으로 확인한다.

**PR 검증 완료 기준:** 승인된 구현·자체 검토·범위 내 결함 수정·관련 검증·기록·커밋·push·main PR 생성/갱신을 마치고, 최신 게시 커밋 CI 종료·통과와 §5의 리뷰 확인·처리까지 확인한다. 타당한 미해결 결함이나 필수 검증/담당 리뷰 대기가 있으면 완료로 보고하지 않는다. PR 머지는 사용자가 하며 배포는 별도 승인 범위다.

**작업 종료 보고의 필수 출력:** PR 검증까지 완료했으면 아래 형식으로 보고한다. 실제 PR 링크·최신 커밋 CI 결과·리뷰 판단·검증/미실행 범위를 함께 적는다.

```text
현재 <작업 ID·이름> 작업은 구현부터 PR 검증까지 완료되었습니다.
PR #<N> 머지 후 아래의 다음 작업 단계 시작을 위한 세션 멘트를 활용하세요.
```

다음 작업이 있으면 다음 **협업 단계**에 맞는 프롬프트 템플릿을 바탕으로 복사 가능한 코드 블록을 제공한다. PR 검증을 마친 작업이면 실제 PR 머지 확인을 선행 조건으로 하는 다음 작업의 1단계 템플릿을 사용하고, 동일 작업의 단계 간 인계라면 완료 단계와 미완료 내용을 지정한 다음 단계 템플릿을 사용한다. 사용자 변경 보존·브랜치 동기화 조건을 넣고 끝난 단계를 반복시키지 않는다. 다음 작업이 없으면 사용자 머지 대기와 “다음 작업 없음”을 명시한다.

명세 검토·승인 대기, 장기화에 따른 분할, 실제 차단으로 종료할 때는 완료 범위·종료 이유·남은 행동을 적고 재개용 코드 블록을 제공한다. PR 검증을 마치지 않았으면 위 완료 문구를 사용하지 않는다. PR 링크·다음 단계 한 줄·진행 파일 링크만으로 코드 블록을 대체하지 않는다. 짧은 후속 질문 답변·진행 중 상태 보고에는 반복하지 않는다. 종료 보고 의무 때문에 내부 단계마다 작업을 종료하지 않는다.

시작 멘트에는 템플릿의 역할·목표·작업 범위·완료 기준·Git 처리·선행 조건을 채운다. 이미 끝난 단계의 멘트를 재사용하지 않는다. 다음 범위가 미승인이면 그 사실을 밝히고 사용자가 다음 단계 템플릿을 지시할 수 있게 제안한다. 코드 블록을 제공한 것 자체를 다음 작업의 실행 승인으로 간주하지 않는다.

아직 작업이 없거나 사용자가 중단/취소했으면 “다음 작업 없음” 또는 중단 상태를 명시하고 새 작업을 지어내지 않는다. 이미 받은 멘트의 사용법만 묻는 단순 후속에는 유효 여부만 확인한다. 실제 종료 보고에는 현재 상태에 맞는 코드 블록을 제공하되, 내부 단계마다 종료 보고를 만들지 않는다.

최종 답변을 보내기 전에 결과·검증/미실행·Git 상태와 함께 `다음 작업 있음 → 시작 코드 블록 / 없음 → 없음 명시`를 확인한다. 이는 응답 작성 규칙이며 모델의 준수를 자동 검사하는 테스트가 설치됐다는 뜻은 아니다.

진행 중 작업의 구체적인 재개 지시·다음 행동은 해당 진행 파일에 같은 내용으로 유지하고, 답변 프롬프트는 그 파일을 가리킨다. 미착수 작업은 계획의 ID를 가리키고 착수 때 진행 파일을 만든다. 완료된 작업을 새 세션에서 반복하도록 쓰지 않는다. 매 답변마다 세션 종료를 권하거나 인수인계에 긴 프롬프트를 쌓지 않는다.
