# ULeveLP 모바일 앱 개발 계획 및 상위 명세서

- **문서 버전:** 2026-11-04 (v1.1 — Capacitor vs React Native 심층 비교, 무료/유료/업그레이드 티어 세부 제약 수치, 크레딧 초과 중도 차단 명세 반영)
- **대상 저장소:** `choise-hun/ULevelP` (React 18 + TypeScript + Vite / Kotlin Ktor + Cloud Run / PostgreSQL 16 + Supabase)
- **작성 목적:** iOS·Android 동시 지원 모바일 앱 전환을 위한 기술 아키텍처 비교(Capacitor vs React Native), 수익화·티어별 정밀 쿼터, 중앙화된 Gemini API 과금 및 중도 차단 제어, 저작권·법적 검토, 노션 연동 방향성 및 단계별 작업 단위(Step) 상위 명세 정의

## 1. 모바일 앱 크로스플랫폼 아키텍처 심층 비교 및 전략 (요구사항 1 & 2)

### 1.1 현재 코드베이스 진단

현재 `ULeveLP`는 단일 Google Cloud Run 컨테이너(`Ktor`)가 정적 빌드 산출물과 REST API(`/api/v1/*`, `/api/*`)를 함께 서빙하는 구조이며, 프런트엔드는 레거시(`public/*.html`)에서 **React 18 + TypeScript + Vite (`frontend/src/`)** 전환을 마친 상태입니다.

- **디자인 토큰(`frontend/src/styles/tokens.css`):** 순백(`#FFFFFF`) 사용 금지 및 웜 뉴트럴 배경(`#F0EEEA`, 다크 `#171716`), 컨트롤은 `9999px` 필 버튼(`--radius-pill`), 카드·패널·모달은 `0px` 직각(`--radius-card`), 중간 곡률(`3~16px`) 전면 금지 규칙이 엄격하게 적용되어 있습니다.
- **클라이언트 핵심 엔진:** 음악 이론·보이싱 계산(`frontend/src/lib/musicEngine.ts`), Web Audio API 기반 실시간 음 합성, SVG 지판·건반 다이어그램(`ChordDiagrams.tsx`, `SanitizedSvg.tsx`), YouTube IFrame 구간 반복 및 `MediaRecorder` 녹음(`PracticePage.tsx`)이 웹 표준 API 위에 구축되어 있습니다.

### 1.2 Capacitor (WebView 기반) vs React Native (네이티브 렌더링) 정밀 비교

AI 생성형 코딩을 활용하면 이미 명세와 원본 React 코드가 있을 때 UI 컴포넌트(`<div className>` → `<View style>`)를 번역하는 작업 자체는 매우 빠릅니다. 그럼에도 두 기술 중 무엇을 선택하느냐에 따라 **비표준 웹 API(Web Audio, YouTube IFrame, 동적 SVG) 이식 난이도**와 **실제 앱 사용감(조작감·레이턴시·메모리)**에서 뚜렷한 차이가 발생합니다.

#### A. Capacitor (WebView 기반)의 작동 원리와 진짜 장단점

Capacitor는 네이티브 앱 안에 OS의 브라우저 엔진(iOS는 `WKWebView`, Android는 `Android System WebView`)을 전체화면으로 띄우고, 그 안에서 지금의 Vite 빌드 결과물(`dist/`)을 로컬 파일로 실행하면서 알람·캘린더·결제만 네이티브 브리지로 호출하는 방식입니다.

| 구분 | 구체적 내용 (`ULeveLP` 기준 체감 포인트) |
| :--- | :--- |
| **핵심 장점 1: 비표준 미디어·그래픽 엔진 100% 무수정 동작** | • `musicEngine.ts`의 **Web Audio API**(`AudioContext`, `OscillatorNode`, 배음 합성, 시퀀서 타이머)가 코드 한 줄 수정 없이 그대로 소리 남<br>• `ChordDiagrams.tsx`와 서버 `GuitarSvgRenderer.kt`가 만드는 **SVG 문자열 및 CSS 변수(`var(--root)`, `var(--orange-terra)`)**가 1픽셀 오차 없이 동일하게 렌더링됨 |
| **핵심 장점 2: 유튜브 플레이어와의 직결성** | • 유튜브는 공식 iOS/Android 네이티브 SDK 지원을 종료했기 때문에 어떤 프레임워크를 쓰든 **유튜브 영상 재생은 반드시 WebView(IFrame)를 거쳐야 함**<br>• Capacitor는 앱 자체가 WebView이므로 `PracticePage.tsx`에서 브리지 통신 지연 없이 `0.1초` 단위 A-B 구간 루프와 배속 제어가 가장 빠르고 정확하게 동작함 |
| **핵심 장점 3: 단일 코드베이스 & E2E 테스트 속도** | • 웹 배포와 앱 빌드가 완전히 같은 파일을 쓰며, 현재 구축된 Playwright 테스트(`test/e2e/*.spec.js` 52개)로 몇 초 만에 레이아웃·기능 검증이 끝남 |
| **명확한 단점 1: 스크롤·화면 전환의 '웹스러운' 질감** | • 네이티브 앱 특유의 쫀득한 물리 스크롤이나 화면 가장자리를 쓸어 넘기는(Swipe-back) 60fps/120fps 화면 전환 애니메이션이 기본 제공되지 않아, 세밀하게 다듬지 않으면 "모바일 웹사이트를 전체화면으로 띄워놓은 느낌"이 날 수 있음 |
| **명확한 단점 2: Android 구형 기기에서의 터치-오디오 레이턴시** | • 지판 다이어그램을 손가락으로 빠르게 연타할 때, iOS(`WKWebView`)는 반응이 빠르지만(약 20ms) 일부 Android WebView에서는 터치 이벤트 → Web Audio 발음까지 **40~80ms가량의 미세한 소리 지연**이 느껴질 수 있음 |
| **명확한 단점 3: 메모리 제한 및 백그라운드 프로세스 킬(Kill)** | • OS가 네이티브 UI보다 WebView 프로세스의 메모리를 더 엄격하게 관리함. 유튜브 영상 재생 + 마이크 녹음을 동시에 켜둔 채 카카오톡이나 다른 앱으로 나갔다 오면 OS가 WebView를 새로고침(Reload)시켜 버릴 확률이 네이티브보다 높음 |

#### B. AI 코딩 시대에 React Native (Expo)로 갈 경우 실제로 추가되는 작업의 실체

AI가 React DOM 코드를 React Native(`View`, `Text`, `StyleSheet`)로 변환해 주는 것은 하루면 충분합니다. 하지만 실제로 시간을 잡아먹는 구간은 **"단순 번역이 불가능한 브라우저 전용 API 대체"**와 **"두 벌의 프로젝트를 굴리는 검증 루프"**입니다.

| 병목 구간 | 현재 웹 코드 (`frontend/src`) | React Native 전환 시 실제로 해야 하는 추가 작업 | AI 코딩 활용 시 체감 난이도 |
| :--- | :--- | :--- | :--- |
| **1. 오디오 합성 엔진 재구축** | `musicEngine.ts`: 브라우저 내장 `window.AudioContext`로 실시간 주파수·배음 합성 (외부 의존성 0개) | RN에는 `AudioContext`가 없음. ① C++ JSI 기반 `react-native-audio-api`를 네이티브 빌드(Xcode/Gradle)에 붙이거나, ② 기타/건반 음정별 `.mp3`/`.wav` 샘플 오디오 파일 수십 개를 번들에 넣고 `expo-av`로 재생하도록 오디오 엔진을 새로 짜야 함 | **높음** (코드 작성보다 iOS/Android 네이티브 오디오 모듈 빌드·동시발음 지연 디버깅이 까다로움) |
| **2. 유튜브 구간 플레이어 이중 브리지** | `PracticePage.tsx`: 같은 DOM 안의 `YT.Player` 객체를 직접 호출해 A-B 구간 반복 | RN에서는 결국 **`react-native-webview` 안에 유튜브 IFrame을 띄우는 구조**가 됨. 즉 RN(네이티브) ↔ WebView(내부 IFrame) 사이에 `postMessage` 브리지를 만들어 0.1초마다 현재 재생 시각(`pos`)을 주고받아야 하며, 전체화면 회전·오디오 포커스 충돌을 별도로 잡아야 함 | **중~높음** (유튜브 플레이어만큼은 RN으로 가도 결국 WebView를 또 써야 하는 모순 발생) |
| **3. 동적 SVG 및 CSS 토큰 이식** | `ChordDiagrams.tsx` + 서버 `GuitarSvgRenderer.kt`: SVG 내부에서 CSS 클래스와 `var(--bg)` 등 CSS 변수를 직접 참조 | `react-native-svg`는 CSS 변수(`var(--*)`)와 CSS 클래스 선택자를 인식하지 못함. 따라서 ① 프런트엔드 SVG 컴포넌트를 모두 Props 기반 인라인 색상 주입으로 바꾸고, ② **Kotlin 서버(`GuitarSvgRenderer.kt`, `KeyboardSvgRenderer.kt`)가 내려주는 SVG 문자열도 CSS 변수 대신 Hex 색상값을 직접 박아 넣도록 백엔드까지 수정**해야 함 | **중간** (AI가 코드는 빠르게 짜주나, 라이트/다크 모드 전환 시 서버 SVG 색상을 치환하는 로직 추가 필요) |
| **4. 웹과 앱의 영구적 이중 작업** | 기능 수정 시 `frontend/src` 한 곳만 고치고 `npm test` 실행 | 앞으로 `CHORDS(코드 진행 모음)` 페이지 추가, 분류 폴더 수정 등을 할 때마다 **① 웹용 React 코드 수정 + ② 앱용 RN 코드 수정**을 매번 두 번씩 지시하고, RN은 Playwright 대신 Android 에뮬레이터/iOS 시뮬레이터를 띄워 눈으로 확인해야 함 | **지속적 발생** (초기 개발보다 향후 기능 추가마다 세션 수가 2배로 늘어남) |

#### C. 최종 기술 선택 가이드 (투트랙 의사결정)

- **추천안 (Capacitor 6+ 채택):** 현재 `ULeveLP`는 리듬 게임처럼 10ms 단위의 초저지연 타격감을 요구하는 앱이 아니라 **유튜브 구간 반복 + 지판 보이싱 확인 + AI 학습 노트 열람**이 핵심입니다. 특히 핵심 기능인 유튜브 플레이어가 RN에서도 어차피 WebView로 돌아간다는 점을 고려하면, **Capacitor로 기존 UI와 엔진을 100% 재사용**하고 부족한 네이티브 감성(하단 탭 바, 햅틱 진동, 오버스크롤 방지, 네이티브 녹음/알림/위젯)만 플러그인으로 보강하는 것이 가장 합리적입니다.
- **대안 (React Native + Expo 채택 시):** 만약 웹 서비스(`run.app`)를 더 이상 주력으로 업데이트하지 않고 **모바일 앱으로만 서비스를 완전히 이주(Migration)**할 계획이거나, 화면 전환 애니메이션과 네이티브 제스처 품질이 최우선이라면 **Expo (React Native) 모노레포**로 전환하는 것도 충분히 가능합니다(이 경우 `musicEngine.ts`의 순수 계산 로직과 `apiClient.ts`는 공유하고 UI·오디오만 RN으로 재작성). 본 명세서의 백엔드(Phase M1~M2)와 네이티브 기능·과금 설계는 두 방식 모두 동일하게 적용됩니다.

### 1.3 모바일 앱 전환 시 핵심 기술 변경 명세 (UI 비파괴 원칙)

1. **API Origin 분리 및 CORS 허용 (`apiClient.ts`, `Main.kt`)**
   - 웹에서는 Same-Origin 상대 경로(`/api/v1/...`)로 호출하지만, 앱 내부에서는 로컬 에셋(`capacitor://localhost` [iOS], `https://localhost` [Android])으로 실행됩니다.
   - `frontend/src/lib/apiClient.ts`에 `VITE_API_BASE_URL` 환경변수 분기를 추가하여 앱 빌드 시 운영 Cloud Run 주소(`https://ulevelp-d5ympfsmfq-du.a.run.app`)를 바라보게 하고, Ktor 서버 `Main.kt`의 `ALLOWED_ORIGINS`에 모바일 Origin을 추가합니다.
2. **모바일 네이티브 레이아웃 및 웹뷰 질감 개선 (`AppShell.tsx`, `tokens.css`)**
   - 기존 색상·곡률 토큰(`--radius-pill: 9999px`, `--radius-card: 0px`, 웜 뉴트럴 배경)은 그대로 유지합니다.
   - 웹페이지 같은 이질감을 없애기 위해 앱 빌드에서는 `user-select: none`(텍스트 드래그 선택 방지), `overscroll-behavior-y: none`(바운스 여백 차단), `-webkit-tap-highlight-color: transparent`를 전역 적용하고, 버튼·지판 터치 시 `@capacitor/haptics`로 미세한 진동 피드백을 줍니다.
   - iOS 노치/Dynamic Island 및 하단 홈 인디케이터 영역 침범을 막기 위해 `viewport-fit=cover` 및 `env(safe-area-inset-top/bottom)` 패딩을 반영하고, 상단 메뉴(`LEARN · PLAY · TRAILS · CHORDS · NOTES`)를 엄지손가락 조작이 편한 **하단 고정 네비게이션 바(직각 `0px` 상단 보더 + `--surface` 배경)**로 반응형 전환합니다.
3. **인앱 Google OAuth 및 Apple 로그인 (`auth.ts`, `drive.ts`)**
   - 임베디드 WebView 내 Google OAuth 차단(`403 disallowed_useragent`)을 피하기 위해 `@capacitor/browser`(iOS `SFSafariViewController` / Android `Chrome Custom Tabs`) + Custom URL Scheme(`ulevelp://auth/callback`) 딥링크로 세션을 주입하며, iOS 심사 필수 요건인 **Sign in with Apple**을 Supabase Auth에 함께 연동합니다.
4. **오디오 합성·녹음 및 YouTube 플레이어 네이티브 보정**
   - **iOS 무음 모드 오디오 출력:** 아이폰 측면 무음 스위치가 켜져 있을 때도 코드 연습실(`musicEngine.ts`)과 녹음 재생 소리가 나도록 `AVAudioSession.sharedInstance().setCategory(.playback, mode: .default)`를 설정합니다.
   - **YouTube IFrame 인라인 재생:** iOS에서 유튜브 재생 시 전체화면 플레이어로 강제 이탈하지 않도록 `playsinline: 1` 파라미터와 `origin` 헤더를 고정합니다.

## 2. 앱 전용 추가 기능 및 수익화·티어별 세부 제약 명세 (요구사항 3 & 3-1)

### 2.1 모바일 앱에서만 제공 가능한 네이티브 특화 기능 (결제 유인 & 심사 통과용)

단순히 웹사이트를 앱으로 감싼 형태를 넘어, **연습 습관 형성(Habit Loop)**과 **모바일 휴대성**을 결합한 5가지 앱 전용 기능을 탑재합니다.

| 구분 | 기능명 | 상세 동작 및 기존 기능과의 시너지 | 무료 / 유료 구분 |
| :--- | :--- | :--- | :--- |
| **습관·일정** | **1. 스마트 연습 루틴 알림 & 원탭 구간 진입** | • 요일·시간별 맞춤형 로컬 알림 (예: *"어제 연습한 Autumn Leaves 0:38–0:55 구간(0.75x), 오늘 10분만 이어서 쳐볼까요?"*)<br>• 알림 터치 시 딥링크(`ulevelp://practice?v=...&a=38&b=55.2&r=0.75`)로 플레이어가 즉시 세팅되어 열림<br>• 저녁 9시 기준 당일 `sessions` 기록이 0초이면 **주간 스트릭 방어 리마인더** 자동 발송 | 기본 알림 1개 무료 / 곡·구간 직행 및 다중 루틴은 **유료 전용** |
| **습관·일정** | **2. OS 기본 캘린더(Apple/Google) 연습 기록 자동 연동** | • `POST /api/v1/practice/save`로 당일 연습 시간이 설정 기준(예: 15분)에 도달하면 기기 기본 캘린더의 `[ULeveLP 연습]` 전용 캘린더에 오늘 연습한 곡명·시간·반복 횟수·구간을 일정으로 자동 기록 | **유료 전용** |
| **바탕화면** | **3. 홈 화면 스트릭 히트맵 & 최근 곡 위젯** | • `HomePage.tsx`의 핵심 시각 요소인 **12주 연습 스트릭 달력(`--orange-terra` 농도 4단계)**과 **최근 연습 곡 1클릭 실행 카드**를 iOS(`WidgetKit`)/Android(`Glance`) 홈 화면 위젯으로 제공<br>• `tokens.css`의 웜 뉴트럴(`#F0EEEA`)과 직각 디자인을 위젯에도 동일하게 적용 | **유료 전용** (무료 회원은 위젯 배치 시 업그레이드 안내 표시) |
| **모바일 입력** | **4. OS 공유 시트(Share Extension) 즉시 연동** | • 스마트폰 **유튜브 앱**에서 영상을 보다가 **[공유] → [ULeveLP]** 선택 시 앱을 따로 켜서 링크를 복사·붙여넣을 필요 없이 즉시 **① 연습 곡으로 열기** 또는 **② AI 학습 노트 분석 요청** 실행 | 곡 열기는 전체 제공 (무료 10곡 한도 내) / AI 노트 요청은 **크레딧 보유 시** |
| **연습 유틸** | **5. 오프라인 코드 연습실·노트 캐싱 & 화면 꺼짐 방지** | • 악기를 들고 연습하는 동안 화면이 꺼지지 않도록 플레이어·코드 연습실 진입 시 **Wake Lock(화면 켜짐 유지)** 자동 활성화<br>• 생성된 학습 노트(`NoteDetailDto` + `diagramsSvg`)와 오디오 테이크를 기기 로컬 파일시스템에 캐싱하여 오프라인에서도 열람 가능 | 화면 켜짐 유지는 전체 제공 / 노트 오프라인 캐싱은 **유료 전용** |

### 2.2 수익화 방식 비교: 유료 앱 출시(Paid Upfront) vs 인앱 구독·크레딧(Freemium + IAP)

현재 프로젝트는 서버 스토리지(`takes`)와 건당 원가가 발생하는 `Gemini API`를 포함하므로, 일시불 유료 앱으로 출시하면 헤비 유저의 반복 사용 시 역마진이 확정적으로 발생합니다. 또한 **"유튜브 재생목록에 연주할 곡들을 담아두면 막상 치려고 찾다가 한 세월 걸려 연습을 안 하고 꺼버리는 문제를 해결한다"**는 핵심 광고 셀링 포인트를 사용자가 직접 체감하려면, 처음에 무료로 앱을 깔아 **최소 10곡 정도를 분류별로 담아보고 바로 구간 연습을 해보는 경험**을 주어야 전환율이 극대화됩니다. 따라서 **무료 다운로드(Freemium) + [유료 구독 2단계(Pro / Pro+) + 사용량 기반 AI 크레딧 과금]** 모델을 채택합니다.

### 2.3 무료 vs 유료(Pro / Pro+ 업그레이드) 기능별 상세 제약 규격

현재 DB 스키마(`profiles`, `songs`, `categories`, `takes`)와 서버 검증 로직(`SongService`, `CategoryService`, `TakeService`, `NoteService`)에 아래 한도 수치를 정확히 반영합니다.

| 기능 영역 | 무료 플랜 (`Free`) | 유료 기본 플랜 (`Pro`) | 유료 업그레이드 플랜 (`Pro+`) | 서버 강제 및 검증 방식 (구현 명세) |
| :--- | :--- | :--- | :--- | :--- |
| **플레이어 곡 등록 (`songs`)** | 최대 **10곡** | 최대 **100곡** | 최대 **150곡** | • `POST /api/v1/songs` 및 `migrate-local` 시 `SELECT COUNT(*) FROM songs WHERE user_id = :uid` 검사<br>• 한도 초과 시 `403 SONG_LIMIT_EXCEEDED` 반환 및 업그레이드 모달 노출 |
| **곡 분류 폴더 (`categories`)** | 최대 **2개** | 최대 **7개** | 최대 **10개** | • 현재 `CategoryService.kt`의 하드코딩 한도(50개)를 `profiles.tier`별 한도(`2` / `7` / `10`)로 변경<br>• 한도 초과 시 `403 CATEGORY_LIMIT_EXCEEDED` 반환 |
| **녹음 저장소 (`takes`)** | • **최대 2곡까지만** 녹음 저장 가능<br>• 총 용량 **5MB** 제약 (`take_quota_bytes = 5,242,880`)<br>• 10분 장시간 녹음 방지를 위해 단일 녹음 최대 **2분(또는 2.5MB)** 제한<br>• Google Drive 연동 **불가** | **본인 선택 (택 1 또는 병행):**<br>① **Google Drive 연동:** 본인 구글 드라이브 여유 공간 내에서 **곡 수·용량 무제한**<br>② **앱 기본 DB(Supabase Storage):** 총 용량 **100MB** 제공 (`104,857,600 bytes`), **녹음 가능 곡 수 제한 완전 해제** (오직 용량 기준으로만 관리) | Pro와 동일 (필요 시 앱 기본 DB 용량 **200MB~500MB**로 차등 부여 가능) | • 무료 유저가 3번째 다른 곡(`DISTINCT song_id`)에 녹음 업로드 시도 시 `403 FREE_TAKE_SONG_LIMIT_EXCEEDED` 거부<br>• 무료 유저가 `PATCH /api/v1/me`로 `storageProvider = "drive"` 변경 시도 시 `403 TIER_UPGRADE_REQUIRED` 거부<br>• 유료 전환 시 `take_quota_bytes`를 `104857600`(100MB)으로 자동 상향 |
| **AI 학습 노트 & 크레딧 (`notes`)** | **사용 불가**<br>(생성 요청 전면 차단, 샘플 노트 열람만 허용) | **크레딧 형태 제공**<br>• 월 기본 크레딧 지급 + 부족 시 단건 충전 가능<br>• **실제 찍히는 사용량(토큰·매체)에 따라 크레딧 사후 정산 징수** | **크레딧 형태 제공**<br>• Pro 대비 월 기본 지급 크레딧 증량 (할인율 적용) | • 무료 유저(`tier == 'free'` 및 `credit_balance == 0`) 호출 시 `403 TIER_UPGRADE_REQUIRED` 차단<br>• 보유 크레딧 초과 요청 시 **3단계 사전·중도 차단**(3.2절) 작동 |

> **다운그레이드(구독 해지 후 무료 전환) 시 데이터 보존 정책:** 유료 구독자가 80곡·7개 분류·80MB 녹음을 쓰다가 구독을 해지하더라도 기존 곡·분류·녹음·노트 데이터를 강제로 삭제하지 않습니다(**열람 및 기존 곡 재생은 유지, 신규 곡 추가·신규 녹음 업로드만 무료 한도 이하로 내려갈 때까지 잠금**). 이렇게 해야 재구독 전환율이 높아지고 데이터 유실 민원이 발생하지 않습니다.

## 3. 단일 비즈니스 Gemini API 전환 및 크레딧 과금·중도 차단 설계 (요구사항 3-2)

### 3.1 사용자 개별 API 키(BYOK) → 중앙 비즈니스 API 키 전환 아키텍처

현재 `NoteService.kt`는 사용자가 직접 등록한 Gemini 키를 복호화해 호출합니다. 상용 앱에서는 서버가 단일 비즈니스 API 키(`SYSTEM_GEMINI_API_KEY`, GCP Secret Manager 주입)로 모든 분석을 대행하고, 사용자의 보유 크레딧(`credit_balance`)을 실제 사용량만큼 차감합니다.

- **모바일 앱 UI에서의 BYOK 입력란 제거:** 애플 App Store(Guideline 3.1.1) 및 Google Play 결제 정책상, 유료 기능을 인앱 결제 대신 외부 API 키 입력으로 우회하게 안내하면 심사 거절 사유가 될 수 있으므로 모바일 앱 빌드에서는 Gemini API 키 직접 입력 UI를 숨기고 크레딧 지갑 UI로 대체합니다.
- **실제 사용량(`usageMetadata`) 정밀 계량:** 현재 `HttpGeminiClient.kt:178`에서 문자열로만 받고 버리는 `root["usageMetadata"]`에서 아래 3가지 토큰 수치를 정수로 추출해 과금 공식에 반영합니다.
  - `promptTokenCount` (입력 토큰: 비디오 프레임 + 오디오 + 문서 텍스트 + 프롬프트)
  - `candidatesTokenCount` (출력 토큰: 생성된 JSON 본문)
  - `thoughtsTokenCount` (추론 토큰: Gemini 2.5 Thinking 과정에서 소모된 토큰 — 출력 토큰과 동일 단가로 과금되므로 반드시 합산해야 함)

### 3.2 핵심 과제: 보유 크레딧보다 많은 사용량을 요구하는 요청의 사전·중도 차단 메커니즘

사용자가 예를 들어 **잔여 10 크레딧**만 보유한 상태에서 **45분짜리 장시간 영상 + 6개 전체 태그** 분석(실제 비용 약 40 크레딧 상당)을 요청했을 때, 끝까지 다 돌려놓고 보니 크레딧이 부족하면 개발자가 그 차액(API 원가)을 고스란히 손해 보게 됩니다. 반대로 무조건 넉넉한 크레딧이 있을 때만 시작하게 막으면 잔여 크레딧이 애매하게 남은 유저가 기능을 못 쓰게 됩니다.

이를 해결하기 위해 **① 요청 전 하한선 차단(Pre-flight Gate) → ② 잔액 맞춤형 출력 토큰 캡핑(Dynamic Token Clamp) → ③ 실시간 스트리밍 감시 및 중도 강제 차단(Mid-Stream Cutoff)**의 3단계 방어선을 구축합니다.

```
[분석 요청]
   │
   ▼
[1단계: Pre-flight 입력 원가 계산]
유튜브 길이(durationSec) 또는 문서 바이트/페이지 수 조회
예상 입력 크레딧(InputCost) + 최소 출력 크레딧(MinOutputCost) 산출
   │
   ├─► (보유 크레딧 < InputCost + MinOutputCost) ──► [즉시 402 차단] Gemini 호출 안 함 (원가 0원)
   │                                                  "보유 크레딧(10)이 부족합니다(최소 28 필요).
   │                                                   분석 구간(시작~끝 시간)을 줄이거나 충전해 주세요."
   ▼
[2단계: 잔여 크레딧 기반 maxOutputTokens 동적 제한]
남은 가용 크레딧 = 보유 크레딧 - InputCost
허용 가능한 최대 출력 토큰 수(AllowedOutputTokens) 계산 후 generationConfig.maxOutputTokens에 주입
   │
   ▼
[3단계: SSE 스트리밍 수신 및 실시간 토큰/바이트 카운터 감시]
HttpGeminiClient가 :streamGenerateContent(SSE)로 청크 수신
   │
   ├─► 스트림 도중 누적 비용이 보유 크레딧을 초과하려는 순간:
   │     1) HTTP 스트림 즉시 강제 종료 (httpRequest.cancel())
   │     2) 보유 크레딧은 0으로 차감 (마이너스 잔액 방지)
   │     3) 작업 상태: status = 'failed', error = 'CREDIT_EXHAUSTED_MID_STREAM' 반환
   ▼
[정상 완료 시: 실제 찍힌 usageMetadata로 최종 정산]
실제 소모 크레딧(ActualCredits) 확정 차감 (선점 예약분 중 남은 차액은 즉시 반환)
```

#### 단계별 상세 구현 명세

1. **1단계 — Pre-flight 입력 원가 산출 및 시작 전 하드 블록 (가장 중요한 방어선)**
   - Gemini API에서 가장 큰 비용 비중을 차지하는 것은 **입력 토큰(특히 영상 프레임과 긴 PDF)**이며, 입력 토큰은 API를 호출하는 순간 100% 과금됩니다.
   - 다행히 입력 토큰 수는 호출 전에 매우 정확하게 계산할 수 있습니다:
     - **YouTube 영상:** YouTube Data API(`videos.list?part=contentDetails`)로 영상 총 길이(`durationSec`)를 먼저 가져옵니다. `fps=0.2`, `MEDIA_RESOLUTION_LOW` 설정 시 Gemini는 **영상 1초당 약 65~70 토큰**을 고정 소비합니다(즉, 10분 = 600초 ≈ 40,000 입력 토큰).
     - **문서(PDF / 텍스트):** 업로드된 텍스트 글자 수 및 PDF 페이지 수를 서버에서 즉시 계산합니다(또는 Gemini 무료 엔드포인트인 `models/{model}:countTokens`를 먼저 호출해 정확한 입력 토큰 수를 0원에 조회).
   - **차단 기준:** `예상 입력 크레딧 + 최소 스키마 출력 크레딧(예: 2,000 토큰분)`이 사용자의 현재 `credit_balance`보다 크면, **`analysis_jobs`를 만들지 않고 즉시 `402 PAYMENT_REQUIRED` (`code: "INSUFFICIENT_CREDITS"`, `{ requiredMinCredits, currentBalance }`)를 반환**합니다. 이때 프런트엔드는 *"보유 크레딧으로 전체 영상을 분석하기 어렵습니다. ① 크레딧을 충전하거나, ② 원하는 구간(예: 03:00~10:00)만 지정해서 분석해 보세요"* 모달을 띄웁니다.
2. **2단계 — 보유 크레딧 한도에 맞춘 `maxOutputTokens` & `thinkingBudget` 동적 캡핑**
   - 입력 원가를 통과했더라도, AI가 응답(JSON + 추론 토큰)을 예상보다 길게 생성하면 보유 크레딧을 초과할 수 있습니다.
   - 이를 막기 위해 `NoteService`가 `HttpGeminiClient`를 호출할 때 사용자의 남은 크레딧(`remainingCredits = credit_balance - estimatedInputCredits`)으로 살 수 있는 최대 출력 토큰 수를 역산하여 요청 페이로드에 강제 주입합니다:
     - `generationConfig.maxOutputTokens = min(8192, remainingCreditsToOutputTokens(remainingCredits))`
     - `generationConfig.thinkingConfig.thinkingBudget = min(1024, ...)` (추론 토큰 폭주 방지)
3. **3단계 — 스트리밍(`streamGenerateContent`) 중도 차단 및 파산 방지**
   - 현재 `HttpGeminiClient.kt`는 응답이 끝날 때까지 기다리는 단건 `:generateContent`를 사용합니다. 이를 **Server-Sent Events(SSE) 스트리밍(`:streamGenerateContent?alt=sse`)**으로 변경합니다.
   - 스트리밍 중 청크마다 내려오는 `usageMetadata` 또는 누적 수신 바이트가 사용자의 예약 크레딧 한도를 넘는 즉시 **코루틴/HTTP 스트림을 `cancel()`하여 연결을 끊고**, 작업을 `CREDIT_EXHAUSTED_MID_STREAM`으로 종료합니다.
   - **동시 실행 원천 차단 유지:** 현재 `NoteService.kt:181`에 이미 구현된 **사용자당 동시 실행 1건 제한(`MAX_CONCURRENT_JOBS_PER_USER = 1` + `ProfilesTable FOR UPDATE` 행 잠금)**을 그대로 유지하여, 10 크레딧만 가진 유저가 동시에 5개 요청을 던져 크레딧을 중복 사용하는 Race Condition을 완벽히 막습니다.

### 3.3 영상 vs 문서 요약 고도화 시 매체·길이 변수 통제 규격

유튜브 영상과 문서(PDF 악보/교본, 웹 이론 칼럼, 마크다운/텍스트)는 토큰 밀도가 다르므로 아래와 같이 **통일된 크레딧 환산표**와 **구간 지정(Range Clipping)**으로 변수를 통제합니다.

- **크레딧 기준 단가 설계 예시:** `1 크레딧 ≈ 입력 4,000 토큰 (또는 출력+추론 1,000 토큰)`
  - 이 공식에 따르면 10분짜리 유튜브 영상(입력 약 40,000 토큰 + 출력 약 3,000 토큰)은 약 **13 크레딧**이 찍히고, 10페이지 텍스트 위주 PDF 문서(입력 약 8,000 토큰 + 출력 약 2,000 토큰)는 약 **4 크레딧**이 찍힙니다.
  - 즉, 영상이든 문서든 길이가 길든 짧든 서버가 별도의 복잡한 분기 없이 **실제 찍힌 `(promptTokenCount / 4000) + ((candidatesTokenCount + thoughtsTokenCount) / 1000)` (올림)** 공식 하나로 공정하고 일관되게 크레딧을 징수할 수 있습니다.
- **부분 구간 지정(Range Clipping) 기본 제공:**
  - 유튜브 영상 요청 시 `startSec` ~ `endSec` (예: `02:30` ~ `08:00`)를 지정하면 Gemini `video_metadata`에 `start_offset`, `end_offset`을 전달해 해당 구간만 분석합니다(크레딧 소모량 70% 이상 절감).
  - PDF 문서 요청 시 `startPage` ~ `endPage` (최대 20페이지 범위)를 지정해 목차나 불필요한 서문을 빼고 핵심 챕터만 분석할 수 있게 제어합니다.
- **글로벌 콘텐츠 해시 캐시 (`shared_analysis_cache`):**
  - 이미 다른 유료 사용자가 분석해 둔 유명 기타 강의 영상(`videoId` + 동일 `tags` + 동일 구간)은 캐시된 JSON과 SVG 다이어그램을 재사용합니다. 이 경우 서버 원가는 0원이므로 사용자에게도 **할인된 크레딧(예: 기본의 30% 또는 고정 2 크레딧)**만 징수하여 플랫폼 마진과 사용자 만족도를 동시에 높입니다.

## 4. 코드 연습실(`chords.html`)의 저작권 및 도의적 리스크 검토 (요구사항 4)

### 4.1 법적 검토 결론: 저작권 침해 가능성 매우 낮음 (아이디어·표현 이분법)

현재 코드 연습실(`ChordsPage.tsx`, `musicEngine.ts`, `ChordTheory.kt`, `VoicingEngine.kt`)의 7개 탭 기능을 전수 확인한 결과, 유료 앱 출시 시 **법적 저작권 침해로 인정될 가능성은 극히 낮습니다.**

1. **음악 이론·화성 규칙·연습 방법론은 저작권 비보호 대상 (Idea-Expression Dichotomy)**
   - 저작권법상 **'아이디어(Idea)', '이론(Theory)', '체계(System)', '연습 방법(Method of Operation)'** 자체는 저작권의 보호 대상이 아니며, 창작자의 구체적인 **'표현(영상 화면 자체, 녹음된 음성, 고유한 문장 서술)'**만 보호됩니다.
   - 코드 연습실의 7개 탭(① 스케일 CAGED 5블럭·5도권, ② `maj7 → 7 → m7 → m7(b5) → dim7` 반음 변환 코드톤 지도, ③ Drop 2/3/2&4 보이싱 매트릭스, ④ 탑노트 고정 5도권, ⑤ 코드 재해석, ⑥ 가이드톤 최소 이동 2-5-1 탐색, ⑦ 3도·6도·4도 더블 스탑)은 재즈 화성학과 버클리 화성학에서 수십 년간 통용되어 온 **보편적 음악 이론 및 수학적 음정 계산 공식**입니다.
   - 특정 기타 유튜브 강의를 AI로 분석해 커리큘럼 아이디어를 얻었더라도, 이를 **자체 작성한 TypeScript/Kotlin 알고리즘(`musicEngine.ts`, `VoicingEngine.kt`)과 자체 SVG 지판 UI로 구현**했으므로 원 저작물의 복제나 2차적저작물 작성에 해당하지 않습니다.

## 5. 노션(Notion) 연동 기능 유지 여부 판단 및 개편안 (요구사항 5)

### 5.1 냉정한 진단: 모바일 유료 앱 관점에서 노션 실시간 연동은 왜 '계륵'인가?

결론부터 말씀드리면, **"노션 실시간 양방향 동기화(`NotionSyncService`, `NotionPushWorker`)는 모바일 앱에서 전면 노출을 중단(고급 설정으로 은닉)하고, 신규 기능의 노션 동기화 매핑은 지금부터 완전히 동결(Feature Freeze)하는 것"**이 맞습니다.

1. **모바일 앱 사용자에게 불가능에 가까운 온보딩 장벽:** 노션 개발자 센터에서 통합 토큰(`ntn_...`)을 발급받고 공식 템플릿을 복제한 뒤 3개 DB ID(32자리)를 발췌해 입력하는 과정은 스마트폰 환경에서 일반 유저의 99%가 이탈하는 장벽입니다.
2. **인앱 UI 고도화로 인한 역할 중복:** 이미 PostgreSQL DB + 12주 히트맵 달력 및 A/B 녹음 비교(`LogPage.tsx`) + SVG 지판이 포함된 전용 노트 뷰어(`NoteDetailPage.tsx`)가 앱 안에 완비되어 있습니다.
3. **Google Drive 무제한 저장소와의 충돌 및 신규 개발 발목 잡기:** 노션 워커 제약 때문에 노션 연동을 켜면 유료 핵심 혜택인 **Google Drive 무제한 녹음 저장을 못 쓰게 막아야 하는 모순(`FR-SYNC-5`)**이 발생하며, 분류(`categories`)나 `CHORDS` 등 신규 기능을 만들 때마다 노션 DB 스키마를 맞춰야 하는 부채가 생깁니다.

> **2026-11-05 사용자 결정 — 노션 연동 기능 중단.** 앞으로 모든 계획·명세에서 노션 연동을 새로 구현하지 않는다(신규 도메인의 노션 매핑·push·pull 없음, 코드 진행 모음 CH-7 노션 push 폐기). 이미 만든 기능은 아래 원칙 1(백엔드 동결)·원칙 2(설정 화면 고급 접이식 은닉)대로 둔다 — 웹·앱 모두. 숨김은 코드 진행 모음 작업의 CH-7b에서 먼저 했다(`개발산출물/진행_코드진행모음.md`)
