## 0. 작업 우선순위 결정: 모바일 앱·Pro 기능·AI 노트 UX 개편 선행 → 다국어(`묶음 L`) 일괄 마감

### 0.1 왜 '기능·UI 개편(Phase M)'을 먼저 하고 '다국어(`묶음 L`)'를 뒤에 해야 하는가?

결론부터 말씀드리면 **① `GA-3`(실영상 분석 확인) 마무리 → ② 모바일 앱·Pro 핵심 기능·AI 노트 Beta/UX 최적화·커뮤니티/큐레이션 구현 → ③ 출시 직전 다국어(`L1-1` → `L1-2`) 일괄 적용** 순서로 진행하는 것이 압도적으로 유리합니다.

| 판단 기준 | 다국어(`묶음 L`)를 먼저 할 경우의 문제점 | 기능·UI 개편(Phase M) 선행 후 다국어를 할 경우의 이점 |
| :--- | :--- | :--- |
| **1. UI·문구 변경에 따른 이중 작업 방지** | AI 노트 UX 개편(Beta 명시·입력 폼 경량화), 유튜브 재생목록 일괄 추가, 공유 커뮤니티·유명인 쇼케이스·스포티파이형 큐레이션 UI를 만들면서 **이미 번역해 둔 `ko·en·ja` 사전(`DICT`)과 컴포넌트를 또 뜯어고쳐야 함** | 한국어 기준으로 신규 Pro 기능과 최적화된 UI·문구를 먼저 100% 확정한 뒤, 마지막에 `i18n.ts`로 **단 한 번에 3개 국어 번역**을 입혀 재작업이 0건임 |
| **2. 모바일 폭(390px) 레이아웃·정렬 검증 비용** | 기능 추가 전 다국어 줄바꿈 검사를 통과시켜도, 하단 탭 바(`M0-2`)·큐레이션 카드·Beta 배지가 들어오면 3개 언어 레이아웃을 처음부터 다시 측정해야 함 | 모바일 네이티브 레이아웃(`M0-2`)과 신규 화면이 모두 자리 잡은 상태에서 영어·일본어 장문 줄바꿈을 한 번만 검증하면 끝남 |

## 1. 모바일 앱 크로스플랫폼 아키텍처 심층 비교 및 전략 (요구사항 1 & 2)

### 1.1 현재 코드베이스 진단 (2026-11-05 기준)

현재 `ULeveLP`는 단일 Google Cloud Run 컨테이너(`Ktor`)가 정적 빌드 산출물(`spa.html` 및 번들)과 REST API(`/api/v1/*`, `/api/*`)를 함께 서빙하는 구조이며, 프런트엔드는 레거시(`public/*.html`, 롤백용 동결)에서 **React 18 + TypeScript + Vite (`frontend/src/`, 9개 화면)** 전환을 마친 상태입니다.

- **디자인 토큰(`frontend/src/styles/tokens.css`):** 순백(`#FFFFFF`) 사용 금지 및 웜 뉴트럴 배경(`#F0EEEA`, 다크 `#171716`), 컨트롤은 `9999px` 필 버튼(`--radius-pill`), 카드·패널·모달은 `0px` 직각(`--radius-card`), 중간 곡률(`3~16px`) 전면 금지 규칙이 엄격하게 적용되어 있습니다.
- **클라이언트 핵심 엔진:** 음악 이론·보이싱·정석 코드 폼 계산(`frontend/src/lib/musicEngine.ts`, `frontend/src/lib/engine/{theory,voicing,chordShapes,progressionPath}.mjs`, `chordForms.json`), 코드 심볼·로마숫자·키 추정 파서(`frontend/src/lib/chords/*.mts`), Web Audio API 기반 실시간 음 합성, SVG 지판·건반 다이어그램(`ChordDiagrams.tsx`, `SanitizedSvg.tsx`), YouTube IFrame 구간 반복 및 `MediaRecorder` 녹음(`PracticePage.tsx`)이 웹 표준 API 위에 구축되어 있습니다.
- **현재 반영된 백엔드·DB 스키마(`V1`~`V4`):**
  - `V1__init.sql`: 기본 12개 테이블(`users`, `profiles`, `songs`, `sessions`, `takes`, `notes`, `analysis_jobs`, `integrations`, `notion_sync`, `notion_links`, `sync_outbox`, `storage_trash`)
  - `V2__categories.sql`: 사용자 정의 곡 분류(`categories`, `song_categories`)
  - `V3__progressions.sql`: 코드 진행 모음(`progressions`, `notes.collect_progressions`, `analysis_jobs.kind` — **100% 개인 전용 보관함**)
  - `V4__analysis_job_options.sql`: 영상 분석 구간(`start_sec`, `end_sec`) 및 코드 변화 속도(`pace`: `slow` 0.5fps / `normal` 1.0fps / `fast` 3.0fps)

### 1.2 Capacitor (WebView 기반) vs React Native (네이티브 렌더링) 정밀 비교

AI 생성형 코딩을 활용하면 이미 명세와 원본 React 코드가 있을 때 UI 컴포넌트(`<div className>` → `<View style>`)를 번역하는 작업 자체는 매우 빠릅니다. 그럼에도 두 기술 중 무엇을 선택하느냐에 따라 **비표준 웹 API(Web Audio, YouTube IFrame, 동적 SVG) 이식 난이도**와 **실제 앱 사용감(조작감·레이턴시·메모리)**에서 뚜렷한 차이가 발생합니다.

#### A. Capacitor (WebView 기반)의 작동 원리와 진짜 장단점

Capacitor는 네이티브 앱 안에 OS의 브라우저 엔진(iOS는 `WKWebView`, Android는 `Android System WebView`)을 전체화면으로 띄우고, 그 안에서 지금의 Vite 빌드 결과물(`dist/`)을 로컬 파일로 실행하면서 알람·캘린더·결제만 네이티브 브리지로 호출하는 방식입니다.

| 구분 | 구체적 내용 (`ULeveLP` 기준 체감 포인트) |
| :--- | :--- |
| **핵심 장점 1: 비표준 미디어·그래픽 엔진 100% 무수정 동작** | • `musicEngine.ts`의 **Web Audio API**(`AudioContext`, `OscillatorNode`, 배음 합성, 시퀀서 타이머)가 코드 한 줄 수정 없이 그대로 소리 남<br>• `ChordDiagrams.tsx`와 서버 `GuitarSvgRenderer.kt`가 만드는 **SVG 문자열 및 CSS 변수(`var(--root)`, `var(--orange-terra)`)**가 1픽셀 오차 없이 동일하게 렌더링됨 |
| **핵심 장점 2: 유튜브 플레이어와의 직결성** | • 유튜브는 공식 iOS/Android 네이티브 SDK 지원을 종료했기 때문에 어떤 프레임워크를 쓰든 **유튜브 영상 재생은 반드시 WebView(IFrame)를 거쳐야 함**<br>• Capacitor는 앱 자체가 WebView이므로 `PracticePage.tsx`에서 브리지 통신 지연 없이 `0.1초` 단위 A-B 구간 루프와 배속 제어가 가장 빠르고 정확하게 동작함 |
| **핵심 장점 3: 단일 코드베이스 & E2E 테스트 속도** | • 웹 배포와 앱 빌드가 완전히 같은 파일을 쓰며, 현재 구축된 Playwright 테스트(`test/e2e/*.spec.js` 75개)로 몇 초 만에 레이아웃·기능 검증이 끝남 |
| **명확한 단점 1: 스크롤·화면 전환의 '웹스러운' 질감** | • 네이티브 앱 특유의 쫀득한 물리 스크롤이나 화면 가장자리를 쓸어 넘기는(Swipe-back) 60fps/120fps 화면 전환 애니메이션이 기본 제공되지 않아, 세밀하게 다듬지 않으면 "모바일 웹사이트를 전체화면으로 띄워놓은 느낌"이 날 수 있음 |
| **명확한 단점 2: Android 구형 기기에서의 터치-오디오 레이턴시** | • 지판 다이어그램을 손가락으로 빠르게 연타할 때, iOS(`WKWebView`)는 반응이 빠르지만(약 20ms) 일부 Android WebView에서는 터치 이벤트 → Web Audio 발음까지 **40~80ms가량의 미세한 소리 지연**이 느껴질 수 있음 |
| **명확한 단점 3: 메모리 제한 및 백그라운드 프로세스 킬(Kill)** | • OS가 네이티브 UI보다 WebView 프로세스의 메모리를 더 엄격하게 관리함. 유튜브 영상 재생 + 마이크 녹음을 동시에 켜둔 채 카카오톡이나 다른 앱으로 나갔다 오면 OS가 WebView를 새로고침(Reload)시켜 버릴 확률이 네이티브보다 높음 |

#### B. AI 코딩 시대에 React Native (Expo)로 갈 경우 실제로 추가되는 작업의 실체

| 병목 구간 | 현재 웹 코드 (`frontend/src`) | React Native 전환 시 실제로 해야 하는 추가 작업 | AI 코딩 활용 시 체감 난이도 |
| :--- | :--- | :--- | :--- |
| **1. 오디오 합성 엔진 재구축** | `musicEngine.ts`: 브라우저 내장 `window.AudioContext`로 실시간 주파수·배음 합성 (외부 의존성 0개) | RN에는 `AudioContext`가 없음. ① C++ JSI 기반 `react-native-audio-api`를 네이티브 빌드(Xcode/Gradle)에 붙이거나, ② 기타/건반 음정별 `.mp3`/`.wav` 샘플 오디오 파일 수십 개를 번들에 넣고 `expo-av`로 재생하도록 오디오 엔진을 새로 짜야 함 | **높음** (코드 작성보다 iOS/Android 네이티브 오디오 모듈 빌드·동시발음 지연 디버깅이 까다로움) |
| **2. 유튜브 구간 플레이어 이중 브리지** | `PracticePage.tsx`: 같은 DOM 안의 `YT.Player` 객체를 직접 호출해 A-B 구간 반복 | RN에서는 결국 **`react-native-webview` 안에 유튜브 IFrame을 띄우는 구조**가 됨. 즉 RN(네이티브) ↔ WebView(내부 IFrame) 사이에 `postMessage` 브리지를 만들어 0.1초마다 현재 재생 시각(`pos`)을 주고받아야 하며, 전체화면 회전·오디오 포커스 충돌을 별도로 잡아야 함 | **중~높음** (유튜브 플레이어만큼은 RN으로 가도 결국 WebView를 또 써야 하는 모순 발생) |
| **3. 동적 SVG 및 CSS 토큰 이식** | `ChordDiagrams.tsx` + 서버 `GuitarSvgRenderer.kt`: SVG 내부에서 CSS 클래스와 `var(--bg)` 등 CSS 변수를 직접 참조 | `react-native-svg`는 CSS 변수(`var(--*)`)와 CSS 클래스 선택자를 인식하지 못함. 따라서 ① 프런트엔드 SVG 컴포넌트를 모두 Props 기반 인라인 색상 주입으로 바꾸고, ② **Kotlin 서버(`GuitarSvgRenderer.kt`, `KeyboardSvgRenderer.kt`)가 내려주는 SVG 문자열도 CSS 변수 대신 Hex 색상값을 직접 박아 넣도록 백엔드까지 수정**해야 함 | **중간** (AI가 코드는 빠르게 짜주나, 라이트/다크 모드 전환 시 서버 SVG 색상을 치환하는 로직 추가 필요) |
| **4. 웹과 앱의 영구적 이중 작업** | 기능 수정 시 `frontend/src` 한 곳만 고치고 `npm test` 실행 | 앞으로 큐레이션·커뮤니티·문서 요약·다국어 사전을 추가·수정할 때마다 **① 웹용 React 코드 수정 + ② 앱용 RN 코드 수정**을 매번 두 번씩 지시하고, RN은 Playwright 대신 에뮬레이터를 띄워 확인해야 함 | **지속적 발생** (초기 개발보다 향후 기능 추가마다 세션 수가 2배로 늘어남) |

#### C. 최종 기술 선택 가이드

- **추천안 (Capacitor 6+ 채택):** **유튜브 구간 반복 + 큐레이션/커뮤니티 탐색 + 지판 보이싱 확인 + AI 학습 노트(Beta)**가 핵심인 `ULeveLP` 특성상, 유튜브 플레이어가 RN에서도 어차피 WebView로 돌아간다는 점을 고려하면 **Capacitor로 기존 React UI와 엔진을 100% 재사용**하고 네이티브 감성(하단 탭 바, 햅틱 진동, 오버스크롤 방지, 네이티브 녹음/알림/위젯)만 플러그인으로 보강하는 것이 가장 합리적입니다.

### 1.3 모바일 앱 전환 시 핵심 기술 변경 명세 (UI 비파괴 원칙)

1. **API Origin 분리 및 CORS·로케일 헤더 허용 (`apiClient.ts`, `auth.ts`, `Main.kt`)**
   - 앱 내부에서는 로컬 에셋(`capacitor://localhost` [iOS], `https://localhost` [Android])으로 실행되므로 `VITE_API_BASE_URL` 환경변수 분기를 추가해 운영 Cloud Run 주소(`https://ulevelp-d5ympfsmfq-du.a.run.app`)를 바라보게 하고, Ktor `Main.kt`의 `ALLOWED_ORIGINS`에 모바일 Origin을 추가합니다.
2. **모바일 네이티브 레이아웃 및 웹뷰 질감 개선 (`AppShell.tsx`, `tokens.css`)**
   - 기존 색상·곡률 토큰(`--radius-pill: 9999px`, `--radius-card: 0px`, 웜 뉴트럴 배경)은 그대로 유지합니다.
   - 앱 빌드에서는 `user-select: none`, `overscroll-behavior-y: none`, `-webkit-tap-highlight-color: transparent`를 전역 적용하고, 버튼·지판 터치 시 `@capacitor/haptics`로 미세한 진동 피드백을 줍니다.
   - `viewport-fit=cover` 및 `env(safe-area-inset-top/bottom)` 패딩을 반영하고, 상단 메뉴(`LEARN · PLAY · TRAILS · CHORDS · NOTES`)를 엄지손가락 조작이 편한 **하단 고정 네비게이션 바(직각 `0px` 상단 보더 + `--surface` 배경)**로 반응형 전환합니다.
3. **인앱 Google OAuth 및 Apple 로그인 (`auth.ts`, `drive.ts`)**
   - `@capacitor/browser` + Custom URL Scheme(`ulevelp://auth/callback`) 딥링크로 세션을 주입하며, iOS 심사 필수 요건인 **Sign in with Apple**을 Supabase Auth에 함께 연동합니다.
4. **오디오 합성·녹음 및 YouTube 플레이어 네이티브 보정**
   - iOS 무음 스위치가 켜져 있을 때도 소리가 나도록 `AVAudioSession` `.playback` 카테고리를 설정하고, YouTube IFrame `playsinline: 1` 파라미터를 고정합니다.

### 2.2 재생목록 · 커뮤니티 · 큐레이션 상세

#### A. 유튜브 재생목록 가져오기 (모든 티어)
- 화면이 URL에서 `list=`를 찾으면 `GET /api/v1/songs/import-playlist/preview?url=`로 재생목록 제목·곡 수·남은 곡/분류 칸을 받아 **"기존 분류에 넣기 / 재생목록 이름으로 새 분류 만들기"**를 묻는다(미리보기 체크박스 없음)
- `POST /api/v1/songs/import-playlist` `{url, categoryId}` 또는 `{url, newCategory: true}` → 서버가 YouTube Data API `playlistItems.list`로 재생목록 순서대로 읽어 **남은 곡 칸까지** 등록(비공개·삭제 영상 제외, 이미 있는 곡은 칸을 쓰지 않고 분류에만 넣음). 응답 `imported`·`alreadyInLibrary`·`skippedLimit`·`skippedUnavailable`·`categoryCreated`
- 새 분류인데 분류 칸이 없으면 `403 CATEGORY_LIMIT_EXCEEDED`(아무것도 등록 안 함). 단순 오류로 끝내지 않는다: 무료·Pro는 *"더 많은 분류 칸을 쓰려면 업그레이드"* + "기존 분류에 넣기", Pro+는 "기존 분류에 넣기"만(에러 `detail.nextTier`로 구분)
- 안내 문구: *"Free 플랜 사용자는 10곡 이상 가져올 수 없습니다. 가져오기 기준은 재생목록 정렬을 따릅니다."*

#### B. 곡 목록 폴더 공유 — 공개용 사본 + 한정적 자동 연동 (학습 노트·코드 진행·녹음은 제외)
- **공개용 사본(`shared_folders`·`shared_folder_items`):** 내 분류를 "게시"하면 서버가 곡 목록을 복사한다(`video_id`·`title`·`artist`·추천 구간 `a`~`b`·`rate`·순서). 메모·상태는 복사하지 않는다. 원본을 고친 뒤 "다시 게시"해야 반영된다. 공개 API는 공개본만 읽는다(개인 `songs` 직접 조회 금지). 원본 분류를 지우면 공개본도 지워진다
- **자동 연동 폴더:** 설정 "연습 리스트 공유 자동 연동"(`profiles.share_autosync`, 기본 꺼짐)을 켜면 공개 폴더마다 자동 연동(`shared_folders.auto_sync`)을 켤 수 있다. 원본 분류가 바뀌면(곡 추가·삭제, 구간·배속·제목 수정) 같은 트랜잭션에서 공개본을 다시 복사 → 보는 사람에게 실시간. 설정을 끄면 모두 멈추고 마지막 공개본이 남는다
- **소통은 "좋아요"만(2026-11-05 사용자 결정):** 공개 폴더 좋아요(무료 포함, 개수만 공개). 댓글·곡 코멘트·폴더 설명 등 **사용자가 쓰는 공개 글자는 만들지 않는다** — 1인 운영으로 언어 폭력·비방을 검토·모니터링할 수 없다. 공개 폴더 이름·공개 이름·공개본 곡 제목의 비방 방지는 **2026-11-06 결정(N1~N3)**: 공개 제목 = 게시 때 자유 입력 + 금칙어 + 신고·owner 숨김, 공개 이름 = 커뮤니티 처음 쓸 때 직접 정함(`display_name`과 별개, 7일에 한 번 변경, 중복·띄어쓰기 금지, owner 초기화), 공개본 곡 제목·아티스트 = YouTube 원래 값(`결과/M1-4a_공유API.md`)
- **학습 기록 공유:** 선택 동의(`profiles.share_practice_log`, 켜기는 유료 + 커뮤니티 이름 필요). 12주 날짜별 연습 시간, 연속 일수, 이번 주(월요일 시작) 합계, 오늘 곡·시간(`seconds`)·반복 수(`loops`)만(날짜 기준 KST). **오늘 곡 제목·아티스트는 YouTube 원래 값**(사용자 곡 제목은 고칠 수 있어 비방 글자가 샐 수 있다 — N3와 같은 이유, M1-4b). 공개 이름은 `profiles.public_name`(N2, 이메일·`display_name` 비노출). 별도 테이블 없이 동의한 유료 사용자의 `sessions`를 집계 — `GET /api/v1/community/logs?scope=following|all`
- **팔로우(`follows`):** 무료도 가능 — 팔로우 목록과 커뮤니티 메인의 "팔로잉한 사람의 연습 목록"만. 알림 등 부가 기능은 유료
- **공유 절대 금지 (원천 차단, 그대로):**
  1. **AI 학습 노트(`notes`):** 강의 요약·채보를 공개하면 원작 강사·음악저작권(KOMCA) 분쟁 소지 → 본인만
  2. **코드 진행 모음(`progressions`):** 공유 기능 전면 폐기, 개인 보관함만
  3. **녹음 파일(`takes`):** 배경 원곡 소리가 섞이므로 본인만
- 공개 폴더 숨김(owner)·신고(`folder_reports`, 무료도 가능)

#### C. 크리에이터 쇼케이스 ("지금 연습 중인 곡")
- owner가 크리에이터를 지정한다(`profiles.is_creator`·`creator_badge`·`creator_bio`)
- 홈·플레이어 탐색의 **[🔥 지금 크리에이터가 연습 중인 곡]** 은 **크리에이터 + 팔로워 상위 사용자의 공개 자동 연동 폴더**를 보여 준다(원안의 `share_practicing`·`songs` 실시간 조회는 없앰). 20칸, 크리에이터 몫·인기 사용자 몫·한 사람 최대 칸은 서버 상수(`CurationPolicy`)로 화면을 보며 조절
- 카드에서 **[이 구간 그대로 연습하기]**(곡 1개 담기, 무료 가능) 또는 **[폴더 통째로 내 보관함에 담기]**(유료)

#### D. 운영자 큐레이션 · 이달의 곡
- **운영자 플레이리스트**(`shared_folders.kind = 'curated'`, 예: *"네오소울 입문 필수 5곡"*): 곡마다 추천 구간(`a`~`b`)·시작 배속이 들어 있어 원탭으로 구간 반복 시작
- **이달의 곡 5개**(`kind = 'monthly_pick'`, 달마다 하나): 운영자가 대형 유튜브·인스타그램 연주 채널을 보고 최근 한 달 인기곡을 직접 고른다. 이번 달 것이 아직 없으면 홈은 가장 최근 지난 달 것을 보인다(M1-4b E4)
- 운영자 작성 제목·설명·곡 설명은 다국어 대비 `*_i18n` JSONB(`{"ko": …}`) — owner가 쓰므로 둔다. **곡 제목·아티스트는 운영자도 입력하지 않고 YouTube 값**을 쓴다(`video_titles`는 전역 캐시라 덮으면 다른 폴더 제목까지 바뀐다, M1-4b E1)
- **자동 인기곡 집계(`GET /curation/popular`)는 없앤다**(익명 집계 개인 노출 문제도 사라짐)
- 홈 묶음 응답: `GET /api/v1/curation/home` → 운영자 큐레이션·이달의 곡·쇼케이스·팔로잉. 경로·응답 필드는 `개발산출물/결과/M1-4b_큐레이션API.md`

#### E. 커뮤니티 화면 방향 (2026-11-06 사용자 — M2-2 입력)
- **큰 틀은 스포티파이·애플뮤직 홈**에 **SNS 공간(학습 기록 공유)이 약간 끼어드는 느낌.** 공개 폴더는 **플레이리스트처럼** 보인다
- 사용자가 보여 준 와이어프레임(스포티파이 홈 화면)에서 가져갈 것:
  - 맨 위 **필터 칩**(예: `모두` · `LOG`) — `LOG`를 누르면 학습 기록 피드(`/community/logs`)만
  - 섹션마다 **제목 + 오른쪽 "모두 표시"** + **가로로 넘기는 정사각 카드 줄**(예: "○○ 님을 위한 연습 플레이리스트", "이달의 곡", "지금 크리에이터가 연습 중", "팔로잉")
  - 카드 = **정사각 표지**(앞 곡 썸네일, 여러 장이면 모자이크) + 표지 위 **폴더 이름 띠** + 아래 **부제 "아티스트 A, B, C 등"** 두 줄 말줄임
  - 오른쪽 패널 탭(**"목록 채우기 / 최근 열어본 내용"**) — 넓은 화면의 연습 대기열·최근 연 폴더. 좁은 화면은 하단 탭(W-1)과 겹치지 않게 M2-2에서 정한다
- 서버가 이미 주는 것: 카드 표지 `coverVideoIds`(앞 4곡, 썸네일 URL은 화면의 `thumb(videoId)` — `frontend/src/lib/security.ts`), 부제 `artists`(앞 곡들의 YouTube 채널명 최대 3개), 운영자 폴더 `titleI18n`·`descriptionI18n`, 곡 `title`(YouTube 원래 영상 제목). **곡 이름·아티스트 분리는 하지 않는다**(영상 제목 그대로 — 파싱이 복잡해 보류, 나중에 개선 후보)

### 3.1 AI 노트 관련 핵심 개편 사항 (Beta 명시 · UI/UX 최적화 · 캐시/공유 폐기)

2. **AI 노트 UI·UX 최적화 (`NotesPage.tsx`, `NoteDetailPage.tsx`):**
   - **요청 폼 단순화 (Progressive Disclosure):** 첫 진입 시 **[유튜브 링크 입력 + 태그 선택 칩(기본 `화성` 선택됨) + 예상 소모 크레딧 배지 + `분석 요청` 버튼]**만 한눈에 보이게 배치하고, `분석 구간 지정(시작~끝 시간)`과 `집중 메모`는 `[+ 구간 지정 · 메모 옵션]` 토글로 접어 모바일 첫 화면에서 스크롤 없이 바로 요청할 수 있게 개선합니다.
   - **실시간 진행 단계 표시 & 원탭 복구:** 분석 중(`queued`/`running`)일 때 막연한 대기 대신 경과 시간과 단계 안내를 표시하고, 실패 시 `GA-1`(`jobError.mts`) 원인 안내와 함께 **[구간을 줄여서 다시 시도]** 버튼을 제공해 입력했던 URL·태그·메모가 날아가지 않고 바로 수정 재요청되게 합니다.
   - **노트 상세(`NoteDetailPage.tsx`) 액션 바 정리:** 상단 액션 바에 **[▶ 이 영상 플레이어로 열기]**, **[마크다운 복사]**, **[코드 진행 수집에 넣기]**를 한 줄로 배치하고, 각 코드 진행의 타임스탬프(`01:24`)를 누르면 해당 초(`t=84`)로 플레이어가 즉시 열리도록 연결합니다.
3. **글로벌 분석 캐시(`shared_analysis_cache`) 및 코드 진행 공유 전면 폐기:**
   - 초기 계획에 있었던 `shared_analysis_cache`(다른 사용자가 분석한 노트 결과를 해시로 공유 재사용하는 테이블)와 코드 진행 공개 공유 기능은 **사용자 메모/분석 이력 노출(개인정보 문제) 및 채보 데이터 타인 배포(저작권 문제)를 원천 차단하기 위해 완전 폐기**합니다.

### 3.2 사용자 키(BYOK) 제거 → 서버 키 + 선불 크레딧

> **2026-11-05 정정(M1-1):** 원안의 스트리밍 중도 차단(3단계)·`maxOutputTokens` 동적 캡핑은 하지 않는다 — 잘린 JSON은 쓸 수 없고 입력 비용은 이미 청구된다. 대신 **예약 → 정산**. 세부는 `개발산출물/결과/M1-1_스키마설계.md` §3.

### 3.3 크레딧 — 버킷 2개, 예약 → 정산

- **단위:** `크레딧 = ceil(입력 토큰 / 4000 + (출력 + 추론 토큰) / 1000)`
- **버킷:** 월 지급분(`profiles.monthly_credits`, 다음 지급 때 소멸)과 구매·보상분(`purchased_credits`, 소멸 없음). 차감은 월 지급분부터. 해지 후 구매분은 남고 재구독 때 쓴다(환불·유효기간은 B-0)
- **월 지급:** 유료 전환 시점에 즉시 지급하고 그 시점부터 30일(720시간)마다 충전, 충전 때 남은 월 지급분 소멸(M1-3d — 원안 "매월 1일"에서 변경, Cloud Scheduler 매시 확인). Pro → Pro+는 차액만 즉시(주기 유지), 유료 → 무료는 주기 끝까지 유료와 같게 유지(유예, M1-3e) 후 무료 전환·남은 월 지급분 소멸. 양은 **마진 50%** — 월 지급 크레딧 원가 ≤ 플랜 가격 × 0.5, `⌊가격 × 0.5 ÷ 1크레딧 원가⌋`(원가는 M1-3에서 모델 단가·환율로 계산). 결제(M4-2) 뒤엔 결제 갱신일 기준
- **원장:** 잔액은 `credit_ledger` 행으로만 바뀐다(버킷별 합계 = 잔액). owner 본인도 차감한다

```
[분석 요청]
   │  무료 → 403 TIER_UPGRADE_REQUIRED
   ▼
[예약액 계산] 예상 입력(텍스트 ~818 + 구간 초 × 초당 토큰: 보통 ~91, 빠름 2.4배, 노트 0.2fps는 실측)
            + 출력 상한(maxOutputTokens) → 크레딧
   │  잔액(월 + 구매) < 예약액 → 402 INSUFFICIENT_CREDITS {required, balance}  (Gemini 호출 없음)
   ▼
[예약] 프로필 FOR UPDATE 안에서 월 지급분부터 차감 (원장 reserve). 동시 1건 제한 유지
   ▼
[Gemini 호출]
   ├─ 완료 → 실제 usageMetadata로 정산, 차액 반환 (원장 settle)
   └─ 실패(Gemini 오류·시간 초과) → 예약 전액 반환 (원장 refund)
```

- 구간이 없는 요청은 영상 길이가 필요해 YouTube Data API(`videos.list?part=contentDetails`)를 쓴다
- 화면의 "예상 소모 크레딧" 배지는 `POST /api/v1/credits/estimate`, 잔액·내역은 `GET /api/v1/credits`·`/credits/ledger`. `GET /credits` 응답 = `{monthly, purchased, total, monthlyGrant, nextGrantAt, monthlyExpiresAt}` — `monthlyGrant`·`nextGrantAt`은 다음 충전 기준(무료·유예 중 0·null), `monthlyExpiresAt`은 유예 중일 때 유예 끝 시각(그때 무료 전환·남은 월 지급분 소멸), 아니면 null(M1-3e)
