## 2. 순서를 이렇게 잡은 이유

- **FT 먼저:** M2·W-1·L1-2b의 완료 기준이 정렬 검사다. M1(백엔드)은 검사와 무관해 병행
- **M0-0 먼저:** 앱 안 유튜브 임베드·녹음이 안 되면 앱 계획 전체가 바뀐다. 실기기 확인은 싸고 빨리 끝난다
- **M4-1을 번역 전으로:** 프리셋 문구를 번역한 뒤 바꾸면 3개 언어를 두 번 고친다
- **W-1(하단 탭 바)을 M2 전으로:** M2 화면을 390px에서 검사할 때 최종 셸이 있어야 한다. 앱 전용 질감은 M0-1에 남긴다
- **L0을 M2 전으로:** 새 화면을 처음부터 `t('키')`로 쓰면 마지막엔 영어·일본어 사전만 채운다. "번역 이중 작업 방지"라는 원래 목적과 같다
- **M1-2를 a·b로 나눔:** b는 사람이 YouTube API 키를 발급해야 하는 대기 지점이 있다
- **M3를 넷으로 나눔:** 기능마다 실기기 4대 확인이 필요하다(검증 단위)

## 3. 결정 기록

### 3-1. 티어·사용자 (사용자 결정 2026-11-05)

- 기존 사용자는 본인뿐 → 이전 처리 없음. 본인 계정은 pro로 지정(M1-2a), 무료 플랜은 다른 계정으로 가입해 시험
- **테스트·운영용 티어 설정 = owner 전용 관리 API** (`/api/v1/admin/*`). 근거:
  - 유지보수: 결제(M4-2) 뒤에도 보상 크레딧·환불·크리에이터 인증·월간 큐레이션 편집에 계속 필요하다. SQL 직접 수정은 원장(`credit_ledger`)을 거치지 않아 잔액과 원장이 어긋나기 쉽다
  - 우선순위: 실제 티어 = `tier_override`(기한 `tier_override_until`)가 유효하면 그것, 아니면 결제 티어. 결제 웹훅은 override를 덮지 않는다
- **보안 검토 (관리 API가 늘리는 위험과 막는 방법):**
  | 위험 | 막는 방법 |
  | --- | --- |
  | 권한 확인 누락으로 일반 사용자가 호출 | `/api/v1/admin` 라우트 한 곳에서만 owner 확인(라우트별 확인 금지). 테스트: 토큰 없음 401, 일반 사용자 403, owner 200 |
  | role 위조 | role은 **DB `profiles.role`에서만** 읽는다. Supabase JWT의 `user_metadata`는 사용자가 직접 바꿀 수 있으므로 쓰지 않는다. role을 바꾸는 API는 만들지 않는다(SQL로만) |
  | owner 세션 탈취 시 크레딧 무한 발급 | 1회 지급 상한, 모든 관리 작업을 `admin_audit`(누가·대상·전후 값·사유)에 기록, 크레딧은 반드시 원장 행으로 |
  | CSRF | Bearer 토큰 방식이라 해당 없음(쿠키 인증 추가 금지) |
- 무료: 곡 10·분류 2·녹음 2곡/5MB, Drive 불가, **AI 사용 불가**

### 3-2. 크레딧 (사용자 결정: 선불 필수)

- 무료는 AI 불가(`403 TIER_UPGRADE_REQUIRED`). **사용자 키(BYOK) 경로는 제거**(M1-3, 저장된 Gemini 키 삭제)
- 유료: 월 지급 크레딧 + 추가 구매 크레딧. 잔액이 모자라면 유료 사용자도 구매해야 한다
- (PM 결정) 버킷 두 개: 월 지급분은 다음 지급 때 소멸, 구매분은 소멸 없음. 차감은 월 지급분부터. 해지 후 구매분은 남고 재구독 시 사용(환불·유효기간은 B-0에서 법 규정 확인)
- (PM 결정) 과금 흐름: 작업 생성 시 `FOR UPDATE` 안에서 "예상 입력 + 출력 상한" **예약** → 완료 시 실제 `usageMetadata`로 **정산**·차액 반환 → Gemini 오류로 실패하면 **전액 반환**. 잔액 < 예약액이면 `402 INSUFFICIENT_CREDITS`. 스트리밍 중도 차단은 하지 않는다(잘린 JSON은 쓸 수 없고 입력 비용은 이미 청구됨)
- 예상치는 실측값 사용: 보통 ~91 토큰/초, 빠름 = 보통의 2.4배(`결과/GA-3_실영상확인.md`). 노트(0.2fps)는 M1-3에서 실측
- 모델은 `gemini-flash-latest` 별칭 대신 버전 고정(별칭이 바뀌면 원가가 바뀐다). 설정은 지금 코드의 `thinkingLevel` 기준

### 3-3. 커뮤니티·큐레이션

- **인기곡 = 운영자 선정**(사용자 결정): 대형 유튜브·인스타그램 연주 채널을 보고 최근 한 달 인기곡 **5곡**을 직접 고른다. 자동 집계(`GET /curation/popular`)는 없앤다 → 익명 집계 개인 노출 문제도 사라진다
- **재생목록 가져오기 = 모든 티어 허용**(사용자 결정): 남은 곡 칸까지 재생목록 순서대로 등록하고 나머지는 건너뛴다. 안내 문구: "Free 플랜 사용자는 10곡 이상 가져올 수 없습니다. 가져오기 기준은 재생목록 정렬을 따릅니다." 응답에 등록 수·건너뛴 수
- **D-1 공유 방식 = B(공개용 사본) + 한정적 자동 연동**(사용자 결정 2026-11-05)
  - 기본: 공개용 사본 `shared_folders`·`shared_folder_items`. "게시"할 때 복사, 원본을 고친 뒤 "다시 게시"해야 반영. 운영자 큐레이션·이달의 곡도 같은 테이블(`kind` = `user`·`curated`·`monthly_pick`). 운영자 작성 제목·설명은 다국어 대비 `title_i18n` JSONB(`{"ko": …}`)로 V5부터 둔다
  - **자동 연동 폴더**("요즘 연습하는 곡" 같은 공유): 원본 분류가 바뀌면(곡 추가·삭제, 구간·배속·제목 수정) 서버가 **같은 트랜잭션 안에서 그 폴더의 공개본을 다시 복사**한다. 보는 사람에게는 실시간, 공유하는 사람은 손댈 것이 없다. 공개 API는 여전히 공개본만 읽으므로 B의 보안 경계(개인 `songs` 직접 조회 금지)는 그대로다
  - 켜는 법: 설정 "연습 리스트 공유 자동 연동"(기본 꺼짐, `profiles.share_autosync`) → 켜면 분류 선택 창의 폴더별 공개/비공개 아래에 자동 연동 on/off(`shared_folders.auto_sync`)가 보인다. 공개(Pro)인 폴더만 켤 수 있다. 설정을 끄면 모든 폴더의 자동 연동이 멈추고 마지막 공개본이 남는다
  - 복사하는 열: `video_id`·`title`·`artist`·`a`·`b`·`rate`·순서. 메모는 복사하지 않는다. ~~곡 코멘트는 공개본에서 따로 쓴다~~ → **코멘트 폐기, 소통은 좋아요만**(2026-11-05 M1-1 승인, 사용자가 쓰는 공개 글자 없음 — `결과/M1-1_스키마설계.md` §0-1)
- 쇼케이스("지금 연습 중인 곡"): 크리에이터(`is_creator`, owner 지정) 또는 팔로워 상위 사용자의 **자동 연동 폴더**를 보여 준다. 그래서 `profiles.share_practicing`과 `songs` 실시간 조회는 없앤다. 팔로우는 `follows`(팔로우하는 사람·받는 사람) 테이블
- 학습 기록 공유는 선택 동의(`profiles.share_practice_log`), 공개 이름은 `display_name`(이메일 비노출)
- 공개 폴더 숨김(owner)·신고는 M1-4에 포함

### 3-4. 다국어

- IP 국가 감지는 하지 않는다(Cloud Run `*.run.app`에는 국가 헤더가 없다). 자동 언어 = 저장된 선택 → `navigator.languages`/`Accept-Language` → 타임존 → `ko`
- `profiles.locale`은 V5에 포함(L1-1은 마이그레이션 없음)
- **D-2 = 화면 사전이 번역**(사용자 결정 2026-11-05): 서버는 코드값(`statusCode` 등)만 주고 API 응답은 언어와 무관. 서버가 언어를 쓰는 곳은 Gemini 프롬프트와 운영자 작성 데이터(`title_i18n`)뿐. `l1_1.md`의 `SongService` 다국어 라벨·`GET /api/v1/locale`·GeoIP는 L1-1에서 뺀다
- `window.ULI18n` 전역 노출 없음. `l1_1.md`·`l1_2.md`의 깨진 링크(`google.com/search?q=…`)는 L1-1 직전에 정리
