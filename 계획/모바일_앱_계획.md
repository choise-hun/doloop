요청하신 세부 제약 조건(녹음·플레이어·AI 크레딧·위젯)과 **Capacitor(WebView) vs React Native 심층 비교**, **보유 크레딧 초과 요청의 중도 차단 메커니즘**을 반영하여 Canvas의 `ULeveLP_모바일앱_개발계획_및_상위명세.md` 문서를 업데이트했습니다. 핵심 보강 내용은 다음과 같습니다.

### 1. AI 코딩 시대 기준: Capacitor(WebView) vs React Native 체감 차이 (1.2절)

말씀하신 대로 이미 명세와 원본 React 코드가 있을 때 `<div className>`을 `<View style>`로 바꾸는 단순 UI 번역은 AI로 하루면 끝납니다. 진짜 차이는 **단순 번역이 불가능한 브라우저 전용 API 3가지**와 **런타임 특성**에 있습니다.

| 비교 포인트 | Capacitor (WebView 기반) | React Native (네이티브 렌더링) |
| --- | --- | --- |
| **유튜브 구간 플레이어 (`PracticePage`)** | 앱 자체가 WebView이므로 `YT.Player`를 같은 메모리 안에서 직접 호출해 `0.1초` 단위 A-B 루프·배속 제어가 즉각 동작 | 유튜브는 공식 네이티브 SDK가 없어 **RN에서도 결국 내부적으로 `react-native-webview`를 띄워 유튜브 IFrame을 돌림** (네이티브 ↔ 내부 WebView 간 `postMessage` 이중 통신 필요) |
| **오디오 합성 (`musicEngine.ts`)** | 브라우저 내장 `window.AudioContext`(오실레이터·배음 합성)가 수정 없이 그대로 작동 | RN에는 `AudioContext`가 없음. C++ JSI 네이티브 오디오 모듈을 네이티브 빌드(Xcode/Gradle)에 붙이거나 음정별 `.wav`/`.mp3` 샘플 파일 재생 방식으로 엔진을 새로 구축해야 함 |
| **지판·건반 SVG (`ChordDiagrams` & 서버 `GuitarSvgRenderer.kt`)** | CSS 변수(`var(--root)`, `var(--orange-terra)`)와 서버 생성 SVG 문자열이 그대로 렌더링됨 | `react-native-svg`는 CSS 변수(`var(--*)`)와 클래스를 지원하지 않아, **백엔드 Kotlin 서버(`GuitarSvgRenderer.kt`)가 내려주는 SVG까지 Hex 색상 주입 방식으로 함께 고쳐야 함** |
| **실제 사용감 (조작감·레이턴시·메모리)** | • **단점:** 스크롤/화면 전환에서 미세한 웹 브라우저 질감이 남을 수 있고, 저가형 Android에서 지판 빠른 연타 시 40~80ms 오디오 지연 발생 가능<br>

<br>• 유튜브+녹음 동시 실행 중 다른 무거운 앱으로 나갔다 오면 OS가 WebView를 새로고침(Reload)시킬 확률이 네이티브보다 높음 | • **장점:** 120fps 물리 스크롤, 스와이프 뒤로 가기 등 완벽한 네이티브 질감 제공<br>

<br>• 백그라운드 전환 시 메모리 생존율이 높고 오디오 모듈 최적화 시 터치 지연이 적음 |
| **향후 유지보수 루프** | 웹과 앱이 **100% 같은 코드**를 쓰고 Playwright로 몇 초 만에 검증 완료 | 기능 하나(`CHORDS` 등)를 추가할 때마다 **웹용 React + 앱용 RN 두 벌**을 각각 수정하고 에뮬레이터 빌드로 따로 검증해야 함 |

* **판단 기준:** 웹 서비스를 함께 유지하면서 빠르게 출시하려면 **Capacitor**가 유리하고, 반대로 웹은 보조로 두고 "모바일에서 웹 느낌을 완전히 지운 네이티브 조작감과 백그라운드 안정성"에 집중하고 싶다면 `musicEngine`의 계산 로직과 `apiClient`만 공유하는 React Native(Expo)로 가는 것도 충분히 좋은 선택입니다.

### 3. 보유 크레딧 초과 요청 시 사전·중도 차단 3단계 설계 (3.2절)

Gemini API는 호출이 시작되는 순간 입력 토큰(영상 프레임·문서) 비용이 확정 과금되고, 생성 도중 출력+추론(`thoughtsTokenCount`) 토큰이 늘어납니다. 따라서 서버가 손해를 보지 않도록 3단계로 차단합니다.

1. **1차 (요청 전 Pre-flight 하드 블록 — 원가 0원 차단):** Gemini를 부르기 전에 유튜브 영상 길이(`durationSec`, 초당 약 65~70 토큰)나 문서 글자/페이지 수를 먼저 조회해 `예상 입력 크레딧 + 최소 출력 크레딧`을 계산합니다. 현재 보유 크레딧이 이 값보다 적으면 아예 Job을 실행하지 않고 `402 INSUFFICIENT_CREDITS`로 즉시 막은 뒤 *"보유 크레딧이 부족합니다. 분석 구간(시작~끝 시간/페이지)을 줄이거나 충전해 주세요"*를 안내합니다.
2. **2차 (남은 크레딧에 맞춘 `maxOutputTokens` 동적 캡핑):** 입력 비용은 통과했지만 잔여 크레딧이 빠듯한 경우, `남은 크레딧 = 보유 크레딧 - 입력 크레딧`으로 살 수 있는 최대 출력 토큰 수를 역산해 Gemini 호출 시 `generationConfig.maxOutputTokens`와 `thinkingBudget`에 상한선(Clamp)으로 걸어버립니다.
3. **3차 (SSE 스트리밍 실시간 감시 및 강제 종료):** `HttpGeminiClient.kt`를 단건 호출 대신 스트리밍(`:streamGenerateContent?alt=sse`)으로 전환해, 스트림 도중 누적 토큰이 보유 크레딧에 도달하는 순간 HTTP 연결을 즉시 `cancel()`(강제 중단)하고 보유 크레딧을 0으로 정산합니다.

Capacitor와 React Native 중 마음이 기울어지는 방향이 있으신지, 혹은 바로 첫 단계(예: 백엔드 티어·크레딧 스키마 설계 `M1-1` 또는 앱 기반 구축 `M0-1`)의 세부 진행 파일 작성을 시작할지 알려주세요.
